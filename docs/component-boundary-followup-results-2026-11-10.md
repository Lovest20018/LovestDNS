# 组件性能与容量边界补测结果

基线 `43373a8`，执行条件见[补充方案](component-boundary-followup-plan-2026-11-10.md)。本轮完成了有界补测及证据复核：**Unbound 仍未建立满足原门槛的旧版性能对照；Redis 淘汰强度 30 在固定容量负载下通过，但观察到更高的写入尾延迟，保留为候选设置。** 默认组件、内存模板与在用实例未调整，现有组合包继续用于评审和隔离试用。

## 工具与测量条件

`benchmark-dns.py` 增加可选的角色 CPU 分配。受控上游使用独立 Python 进程；控制器、上游、Redis、Unbound、抓包器和发生器分别使用不重叠的允许 CPU 集合。准备 Redis 种子、重启组件及正式测量沿用同一分配，报告要求真实 affinity 采样齐全；双 CPU 发生器另核对线程允许 CPU 集合。该模式只用于 Unbound 测量入口。

先冻结每轮源码和普通制品，在 Linux 上运行 **58 项定向测试，全部通过**；再对新旧 Unbound 的热缓存、Redis 命中路径各做一次三秒功能检查，共四组，检查答案、路径、内核配对、零丢失和实际 CPU 分配。两次工具版本均分别完成这些检查。短测不用于性能批准。Windows 同组曾出现两项本地 UDP 夹具超时，另有一项 Linux affinity 测试跳过，未记为 Windows 全通过。

普通 Redis 固定为 7.2.17，Unbound 旧版为 1.21.1，负载为 500 QPS、q64、串行上游。控制器、上游、Redis、Unbound、抓包器依次使用 CPU 8–12。服务有私有网络、内存和时间上限；未修改宿主或在用服务的 CPU 分配。固定 affinity 也不表示独占宿主物理 CPU。

## Unbound 校准停止结果

第一轮把发生器限制到单 CPU 13。首对旧版热缓存各运行 60 秒，实际完成 29,792／30,000 条查询，全部已发送查询回答正确、零丢失，测量计数和资源条件有效，但 P99 为 **4.090／0.955 ms**，相差 3.135 ms，立即停止。首组内核最大发包间隔为 416.768 ms；完整输出保留，不能仅凭此确定停顿来源。

随后核对 [DNS-OARC 官方说明](https://www.dns-oarc.net/tools/dnsperf)，将发生器改为 CPU 13、14，其他角色与全部门槛保持。该轮使用新冻结源码和新目录，周期性采样观察到三个发生器线程，允许 CPU 集合均为 13、14。

| 修正后首对旧版 A/A | 第一组 | 第二组 |
| --- | ---: | ---: |
| 完成且答案正确的查询 | 30,000 | 30,000 |
| 用户态 P95 | 0.494 ms | 0.506 ms |
| 用户态 P99 | 1.612 ms | 1.128 ms |
| 内核往返 P99 | 0.486 ms | 0.864 ms |
| 内核最大发包间隔 | 3.698 ms | 3.263 ms |

答案、逐请求时序、内核配对、socket／抓包零丢失、角色 affinity 和资源条件通过；每组 CPU 配额限流与 memory max／OOM 计数均无增量。但用户态 P99 差仍为 **0.484 ms**，超过固定 **0.2 ms** 门槛。按预案在首对失败后停止，没有运行 Redis 命中校准或四场景四十组新旧矩阵，也未追加同条件试验挑选结果。

发生器获得两个 CPU 后仍未满足旧版重复性，不能据此认定新版 Unbound 回归，也不能签署无回归；内核分位数不替换用户态验收指标。两轮源码、原始逐请求输出、资源事件和失败结果分别保留。后续如继续性能接受工作，需要先确定能满足旧版重复性的测量条件。

## Redis 淘汰强度对照

在另一测试机的隔离 Redis 上，分别从同一份既有准备副本开始。两次加载均全量核对键、值、类型、DB 和绝对截止时刻的摘要；原文件只读，不传输原始缓存或历史问题。预算保持 **1,500 MiB**、策略 `allkeys-lru`，先默认 10、后候选 30，各执行一次 **700 次 1 MiB** 固定载荷写入，全部成功；每次写入时长及每十次的容量、淘汰和 Redis 自报峰值均保留。未使用方案中的同机替代路径。

| 指标 | 默认 10 | 候选 30 |
| --- | ---: | ---: |
| 采样最高 `used_memory` | 1,618,410,165 B | 1,572,952,941 B |
| Redis 自报 `used_memory_peak` | 1,618,496,973 B | 1,573,672,002 B |
| 自报峰值高于预算 | 43.52 MiB | 0.77 MiB |
| 写入 P50 | 3.165 ms | 2.402 ms |
| 写入 P95 | 10.966 ms | 14.980 ms |
| 写入 P99 | 13.410 ms | 22.530 ms |
| 最慢写入 | 20.127 ms | 39.950 ms |
| 预算加 4 MiB 的固定容量门槛 | 未通过 | 通过 |

两组均发生至少 1,000 次淘汰，无 memory max／OOM 计数增量。默认组在包含加载、全量扫描和压力写入的整个阶段有两次 CPU 配额限流，共 4.391 ms；候选组无增量。记录的写入时长不能作无配额干扰的性能验收，也不用于推算普通 DNS 延迟。

候选写入 P99 比默认组高 **9.120 ms**，约 **68.0%**；这是一次固定顺序和负载下的观察，不将差异全部归因于单个参数。Redis [同版淘汰实现](https://github.com/redis/redis/blob/7.2.17/src/evict.c)对更大的 tenacity 提供更长的淘汰时间预算，因此容量与延迟需一起评估。本轮没有修改产品默认值，也未将候选设置装入已有组合包。

随后在 **tenacity=30、同一内存预算**下，用旧版 Unbound 生成受控小快照，完成 **七个功能阶段**：新版和回退旧版均真实读取旧缓存，两数据库返回各自答案；两秒 TTL 过期后刷新、负应答、CNAME、TCP 查询、新缓存保存及重启重载通过，原小快照摘要保持。该结果限定为受控数据；本轮没有对 tenacity=30 执行压力后全量快照保存／重载，先前默认设置下的大快照证据仍按原配置解释。
