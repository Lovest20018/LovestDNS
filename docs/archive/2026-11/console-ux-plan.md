# LovestDNS 控制台优化方案

本方案面向家庭和小型局域网中负责 DNS 的管理员，以 Debian 原生部署为主要使用场景。评审依据为项目当前的产品说明、集成版前端、维护任务与配置记录实现，以及一次生产环境的配置应用过程。以下界面和验收条件均为建议。

## 用户需要完成的三件事

| 使用时机 | 打开面板要回答的问题 | 做完的标志 |
| --- | --- | --- |
| 平时巡检 | 这台 DNS 最近一次检查能应答吗？现在有事需要我处理吗？ | 首页直接给出检查结果、时间和待处理项 |
| 修改配置 | 刚改了什么，如何加载，会影响谁？ | 在编辑处看到保存、加载、样本查询各自的结果 |
| 家中设备打不开域名 | 是设备没用这台 DNS，还是这台 DNS 解析这个域名有问题？ | 能从目标域名和设备接入两个方向取证，必要时定位到相关组件日志 |

沿用 LovestDNS 品牌、组件诊断和高级编辑能力。优先投入集成版。冻结的独立 WebUI 维持兼容维护。网关联动保留按启用情况展示，产品范围继续以单台 DNS 实例为中心。

## 先统一状态和操作反馈

首页、编辑器和维护页共享同一套判定。DNS 进程、协议应答、配置版本、任务进度和客户端接入分别取证。状态要携带实例、观测时间和证据范围。缺少新鲜数据时展示上次观察时间，允许重新检查。操作进度只取自对应任务，无法确认的阶段只写“处理中”。

| 已掌握的证据 | 建议文案 | 用户可以做什么 |
| --- | --- | --- |
| 进程正常，尚无近期探测 | DNS 进程运行中 · 上次应答检查〔时间〕，或“尚未检查应答” | 测试解析 |
| 已有本机 UDP、TCP 探测成功 | 本机 DNS 应答正常 ·〔时间〕 | 需要时检查设备接入 |
| 新进程没有匹配的配置记录 | 本次启动后还没有配置应用记录 | 查看记录或验证域名。仅此情况不产生待重启计数 |
| 文件与同一进程的成功记录有差异 | 〔配置名称〕已修改 ·〔对应加载方式〕 | 查看差异，处理这一组修改 |
| 已点击提交，尚未拿到任务回执 | 正在提交重启请求… | 禁止重复点击。超过等待时间后核对原请求 |
| 客户端在发请求前出错 | 重启请求未发出 | 就地重试，展开查看技术详情 |
| 请求已发出，响应丢失 | 暂时无法确认是否已受理，正在核对 | 复用原请求编号查询或幂等重试。只读核对可以自动执行 |
| 已有执行中的重启任务 | 正在重启 DNS，期间解析可能短暂中断 | 显示任务进度、更新时间，恢复后自动更新 |
| 任务结束，协议检查已通过 | 重启完成 · DNS 已恢复应答 | 验证目标域名。单列配置记录与本次任务的对应情况 |
| 管理服务确实不可达 | 暂时无法提交维护操作 ·〔最近 DNS 检查结果及时间〕 | 重新连接，查看管理服务日志 |
| 任务失败 | 显示失败步骤、现有服务状态、恢复结果 | 根据后端证据给出修正配置、重新检查或恢复入口 |

有活动任务时优先显示任务上下文。若此时失联，应写“连接中断，上次看到任务正在执行”，并保留任务编号和上次更新时间。有真实故障证据时仍需显示。任务执行、刷新暂停、数据过期和权限不足分别给出原因。结构化原因码可以逐项补充，在前端统一翻译；旧接口缺少原因时保留“不确定”和可用的检查动作。

## 页面和导航

| 一级入口 | 默认内容和主操作 | 展开或二级入口 |
| --- | --- | --- |
| 概览 | 实例、最近一次 DNS 应答、需要处理的变更、当前或最近任务。主操作随状态切换为测试解析、处理变更或查看进度 | 核心进程、递归与转发统计、趋势、缓存与持久化 |
| 解析配置 | 基础设置、域名分流、TTL 规则。编辑区显示影响范围和唯一的下一步 | 原始文件、高级配置、版本差异、恢复历史 |
| 查询与诊断 | 输入域名，显示回答、响应码、耗时、探测发起位置。提供设备接入检查 | UDP/TCP 对比、近期查询、报告、启用后的网关观测 |
| 维护 | 当前任务和结果、软件更新、组件与日志。由任务直接打开对应组件 | 缓存快照、构建来源、主机命令和恢复指引 |
| 设置 | 实例标识、账户、更新通道与代理、可选网关联动、外部接入 | API 与 Token 等高级项目 |

TTL 的编辑始终归在“解析配置”；“缓存”详情可以链接到它。查询记录关闭时显示“未开启查询记录”并说明开启的作用，零条记录单独展示。直接访问旧地址应定位到新页面内的相同内容，并保留文件、组件、选项卡参数。更新设置归“设置”，安装和查看升级结果归“维护”。

## 完成一次配置变更

1. 用户保存时显示本次文件与差异摘要。草稿、文件落盘、已执行加载、目标域名查询四种结果使用不同词语。
2. 按现有保存结果分流。基础设置或 Unbound 配置显示“查看并重启 DNS”；自定义分流显示“预览并校验”，校验通过再应用；满足文件监听条件的规则显示“验证域名”。条件未知时显示需核对的具体设置。容器部署按实际能力跳转主机操作说明。
3. 确认区列出本次操作实际会覆盖的已保存配置、解析中断影响及失败后的恢复方式。跨文件草稿阻塞操作时，列出文件和“返回编辑”。只读用户看到状态与可执行的检查。
4. 点击确认后，按钮所在区域立即显示提交结果，再就地更新任务进度。切换页面或重新打开后通过服务端任务恢复展示，所有入口引用同一条任务。短暂断网和重复点击都不能创建第二次重启。
5. 完成后就地展示任务结果、协议应答检查及时间，再提供“验证刚改的域名”。有明确目标域名时预填；规则路径或命中证据不足时只展示实际回答。若执行失败，分开报告磁盘上的编辑文件、运行配置回退和服务探测结果。

## 视觉与交互

- 沿用现有视觉基础，先调整阅读顺序。正常时首屏突出最新检查，处理中突出任务，失败时突出影响和下一步。相同实例的运行状态保留一个主要展示位置。
- 蓝色配进度文字表示处理中，黄色配具体行动表示需处理，红色配故障对象表示已确认失败，灰色用于尚未检查或历史快照。文字、图标和时间共同表达含义。
- 操作结果紧贴触发按钮，并通过可访问的状态区域播报。确认动作写明对象，例如“确认重启 DNS”。禁用时在旁边写明原因，提供可用的下一步。
- 桌面将当前工作区与辅助详情分层；手机改成“结论 → 主操作 → 详情”的单列顺序。长配置编辑页保留可见的保存入口和草稿状态，确认后焦点移到反馈区域。键盘、窄屏和深色模式使用相同流程。

## 实施顺序与验收

| 优先级 | 最小交付 | 放行条件 |
| --- | --- | --- |
| P0 纠正误报和无反馈 | 合并已有维护能力修复；在按钮旁显示请求、回执、进行中、失败和成功；任务完成后联动刷新能力、运行快照和配置记录 | 普通 LAN HTTP 下可提交；活动重启时无虚假的管理服务故障；响应丢失后仅一条任务；真实管理故障仍有明确提示；恢复后无需手动刷新 |
| P1 接通配置流程 | 编辑器共享保存后的主操作，首页区分缺记录和确有改动，任务结果关联域名验证；修复 TTL 导航归属 | 新装或升级后缺记录不会引导无意义重启；三种加载方式各自走通；刷新、跨页、草稿、只读权限和容器能力分别覆盖 |
| P2 调整全站层级 | 概览首屏改版，归并缓存、维护和设置，整理诊断入口，补齐手机和键盘操作 | 给首次使用者“判断服务健康”“改一条规则并验证”“找出失败任务原因”三个任务，记录完成率、误判及卡住位置；旧深链可达；手机可在原操作处看到反馈 |

实现可从现有的 `integrated/runtime/manager.py`、`SuiteMaintenance`、`ConfigState`、`ConfigFeedback`、`ConfigVerification` 和 `App.tsx` 演进，保留维护任务编号、幂等提交和样本关联逻辑。先在隔离实例演练重启、失败、断线重连和回退，再安排生产维护窗口。发布后分别核对实际版本、DNS 应答、任务记录与配置状态。

## v0.1.1 实施

常用操作已按概览、解析配置、查询与诊断、维护和设置组织。三个配置加载路径、普通 HTTP 维护提交、丢失回执恢复和窄屏布局均有隔离回归。首页解析探测显示每个样本的结果与时间，配置加载前的结果会标为历史。首次使用者的实际完成率、误判和卡点仍待采集。[发行说明](../../releases/v0.1.1.md)
