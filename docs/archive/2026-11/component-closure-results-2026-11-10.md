# 组件收尾记录

按用户要求，先处理组件更新，功能扩展后移。执行范围和性能协议见 [本轮方案](component-closure-plan-2026-11-10.md)。本轮使用已有测试环境和隔离实例，未升级正式实例、推送或公开发布。

## Unbound 离线缓存兼容

新增 [离线准备工具](../../cachedb-offline-upgrade.md)，针对 `1.21.1 → 1.26.2` 的问题名大小写键变化，只在副本增加可确认的缺失目标，不改查询热路径或撤销上游大小写修复。

真实旧版生成两数据库的受控 RDB，准备后所有 **42 个原键**的类型、值与 Redis 绝对过期时刻完整保留；增加 **18 个小写别名**。两组相互冲突的历史答案、两组已有小写目标和两组 CNAME 中间项均保留原状；未知报文、非 DNS 键及种子不符单独报告。

新版本重载、旧版本读取准备后的副本、旧版本恢复原快照三阶段均通过。覆盖 A/AAAA/TXT、完整 CNAME、NXDOMAIN/NODATA、短 TTL、DB 0/1 和 UDP/TCP。混合大小写 A/AAAA/TXT 真实 Redis 命中，完整 CNAME 链能返回最终地址；跳过的 CNAME 中间项在新版自然查询补齐，旧版仍可观察到原有的仅别名应答，未将其强行等同于最终地址。

真实 RSA DNSSEC 夹具验证有效签名的 AD 应答、错误签名的 SERVFAIL，以及曾有效但已过期的签名不能重新成为可信新鲜答案。两版夹具均显式设置零签名时钟容差；初轮默认容差下短期过期仍被接受，已保存该结果，不认定为组件回归。默认容差语义见 [Unbound 官方文档](https://unbound.docs.nlnetlabs.nl/en/latest/manpages/unbound.conf.html#term-val-sig-skew-min)。签名缓存命中时允许独立的 trust-anchor DNSKEY 检查，并按逐问题账本核对，未把它算作原 A 记录重新查询。

随后对实际历史大快照运行同一份交付工具的计划和准备入口，并分别用新旧 Redis 加载输出。逐个别名核对源值、目标值和绝对截止时刻，再计算全量键／类型／值／DB／截止时刻摘要；结果恰好等于全部原数据加计划别名，两版重载均通过，淘汰数为零。实际数据中的既有小写目标、冲突组、CNAME 中间项、无法识别的报文及种子不匹配条目保留原状，计数和摘要保存在私有证据中。

输入 RDB 摘要在全部阶段保持不变。该补充验证了实际快照的可加性与隔离配置下的加载，尚未完成完整历史缓存的 DNS 应答回放、无法识别条目的语义验证，以及正式配置下的新增别名容量／淘汰压力验收；默认升级限制继续保留。

## Redis 持久化和回退

`7.2.5 → 7.2.17` 的六阶段通过：旧版保存、新版加载旧快照、新版修改并 BGSAVE、新版重载、旧版读取新版快照、旧版恢复原快照。

两数据库共 **32,012 个键**，涵盖 binary-safe string、hash、list、set、zset、stream，受控主体值约 31.25 MiB。逐键 DUMP、类型、DB 和绝对截止时刻摘要一致；新版实际增加、覆盖、删除和集合更新后，重载得到修改后摘要；原快照恢复得到修改前摘要。后台快照状态 `ok`，四个绝对截止时刻保持，短期自然过期键未复活，各阶段淘汰数为零。

修复了新工具的就绪判断：自行启动的 Redis 加载较大 RDB 时可暂时返回 `LOADING`，现在仅对此状态进行有界等待，其他命令错误仍拒绝。首轮失败保留。

随后在隔离测试环境补齐**实际历史大快照的六阶段持久化与回退**：旧版加载、新版加载、新版增加两数据库的独立探针并 BGSAVE、新版重载、旧版读取新版快照、旧版恢复原快照，全部通过。对每个键的类型、原始值、DB 和绝对截止时刻计算全量摘要；新版快照恰好多出两个受控探针，回退恢复原摘要，所有阶段淘汰数为零。原文件摘要始终一致，后台保存状态为 `ok`。

该试验禁用 TCP、AOF 和自动保存，受 CPU、内存、时间与磁盘余量限制；只读阶段使用新目录中的硬链接，写阶段先移除新建链接，再生成独立文件。原快照始终保留。加载、写入、重载和回退证据已补齐；AOF、磁盘满、崩溃恢复、全量历史 DNS 应答及正式实例容量压力未覆盖。现场缓存统计和摘要仅留在私有证据中。

## 性能状态

本轮校准已结束，**两项均未建立可用于候选性能验收的原版对照**。没有开始候选初筛或正式性能矩阵，不能据此判断新版回归，也不能签署无回归。普通制品、固定工具和失败记录均保留，未通过重复同条件测试挑选通过结果。

| 组件 | 原版校准结果 | 处理 |
| --- | --- | --- |
| DNSCrypt | HTTP/2 直连三对相邻测试均满足测量与尾延迟重复性要求；SOCKS 第二组全部已发送查询回答正确，但内核最大发包间隔约 197.18 ms，超过固定 50 ms 上限 | 判为测量条件无效并停止；HTTP/1.1、候选初筛及正式矩阵未执行 |
| Redis | 两组缓存命中测量有效，答案、Redis 命中、零上游、内核配对和资源检查通过；原版 P99 为 1.790／2.106 ms，相差 0.316 ms，超过 0.2 ms 重复性门槛 | 原版重复性失败并停止；没有启动新版 Redis 对照 |

DNSCrypt `2.1.20 combined` 已加入普通制品的独立入口和分流链路对照工具；报告同时要求与原版及同工具链 upstream 比较。当前结果不对单个补丁、编译器或 Redis 版本作性能归因。缓存兼容与持久化通过仍单独有效。

随后完成[回环、逐次发送阶段及独立延迟诊断](dns-scheduling-diagnosis-results-2026-11-10.md)。初轮三组原版 DNS 路径均零丢失，内核最大发包间隔为 18.181／19.135／24.553 ms，CPU 内在延迟最高 3.273 ms。补齐线程统计的一组则记录到 **316 ms 发送空档与同时间 312 ms 独立心跳空档**，其 GC、锁等待和发送调用无法独自解释该停顿，节奏检查失败并保留。本次仍未确认宿主侧具体原因；临时统计开关已恢复，诊断结果不计入性能通过。

另按指定执行一次固定原版 A/A，共 13 组测量。Redis 首对 P99 相差 **0.215 ms**，仍超过 0.2 ms；DNSCrypt HTTP/2 直连三对和 SOCKS 前两对通过，但 SOCKS 第三对第一组再次出现 **275.081 ms 发送空档**，同组独立心跳最大间隔 **277.102 ms**，停止该组件，HTTP/1.1 未执行。已发送的查询均正确、零丢失，资源检查有效，测试 VM 启动标识与主服务状态保持；没有追加重跑。两组件仍未建立可供候选验收的完整原版对照，缓存兼容和持久化结论保持独立有效。

其后另经用户批准，转到另一台 Debian 12 / KVM 宿主机执行[独立性能对照](component-crosshost-performance-results-2026-11-10.md)。Redis 三对原版校准及 120 秒、五轮新旧对照通过，599,998 条正式查询全部正确、零丢失，CPU、RSS 和尾延迟符合原门槛，可进入后续最终组合验收。DNSCrypt 六组原版测量均有效，但 HTTP/2 直连第三对 P99 相差 **0.253419 ms**，超过 0.2 ms，按方案停止，候选未测。本轮没有出现前述长发包空档，不能由此确认前轮根因；原失败、默认升级限制及最终组合验收边界继续保留。

## 失败保留与验证范围

Unbound 首轮测试夹具有报文偏移和 TXT 类型选择错误，分别修正后继续；真实 CNAME 中间项返回不完整答案促使离线工具增加保守跳过。默认 DNSSEC 时钟容差、trust-anchor 独立查询两个夹具预期也逐项核实，原始失败日志保留。Redis 首轮的 `LOADING` 失败用于修复就绪等待。性能控制器首轮缺少模块搜索路径，在执行任何性能查询前失败；之后 DNSCrypt 的旧夹具被源码摘要检查拒绝，同样未发起性能查询。改用已经构建且与当前源码一致的夹具后完成上述校准，原版、upstream 和 combined 的普通二进制未因此重新编译。

本轮定向回归 Windows / Linux 各 **75 项通过**，最终离线工具另经过真实新旧组件查询与快照回退检查。此前 console4.1 的两小时负载使用旧组件，不计入本轮新组件验收。默认组件、组件锁和正式实例没有升级；最终组合、原生安装升级与组件持续负载仍须在相应性能和兼容关卡通过后执行。

后续用户决定将 DNSCrypt combined 纳入推荐组合，并继续处理 Unbound；实际历史全量回放、当前模板容量、Unbound 性能停止结果及明确标为候选的原生组合包，另记于 [后续收尾记录](unbound-completion-results-2026-11-10.md)。前述失败与通过均按原范围保留，功能试验不替代性能或默认发布批准。
