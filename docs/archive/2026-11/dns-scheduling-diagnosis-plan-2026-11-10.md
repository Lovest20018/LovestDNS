# 性能校准的调度诊断

基线为 `ab9781a`。继续处理组件性能校准，复用现有测试环境，不拓展功能。此前 Redis 原版 A/A 的 P99 差 0.316 ms；DNSCrypt 原版 HTTP/2 SOCKS 的发送器及内核同时记录约 197 ms 空档，且没有并发上限跳过。原因尚未定位，原失败保留。

## 有界诊断

先核对二进制、源码、CPU 拓扑、可用内存和磁盘。仅重建带可选发送记录的测试发生器，不重编译 DNS 组件。逐次记录计划、唤醒、取得锁、发送调用开始及结束时间；记录保存在有界内存中，在测量结束后写入新文件。GC 记录与发送记录用于归因，不能据此签署组件性能通过。

使用新目录，串行各执行一次：

1. 原测试发生器直接访问串行回环夹具，60 秒、100 QPS、q64。
2. 带发送记录的发生器执行同一回环路径，60 秒、100 QPS、q64。
3. 带记录的发生器访问原版 DNSCrypt 的 HTTP/2 SOCKS 夹具，60 秒、100 QPS、q64。
4. 原版 `redis-cli --intrinsic-latency 60` 单独执行，期间不运行 DNS 负载；此模式不连接 Redis，只测本进程获得 CPU 的停顿。

每个阶段采集测试 cgroup 的线程调度等待、CPU 时间、CPU 压力、限流、内存事件及主机 CPU 计数。另启独立的 10 ms 心跳，放在不同测试 CPU 范围，保留全部间隔。实验使用 CPU 4–7、配额 400%、内存 1 GiB、Nice 10、独立网络命名空间；心跳 CPU 0–3、配额 50%、内存 64 MiB。所有进程有总时限。双端答案、socket 和抓包丢包检查继续保留；诊断测量无效也保留记录，停止对应路径，不删去慢查询。

## 归因和后续

- 发送空档落在唤醒前，结合线程等待与独立心跳检查局部 CPU 竞争或更广停顿；两个进程同时延迟仍不能独自证明虚拟机宿主为根因。
- 锁或发送系统调用阶段突出时，先处理发生器自身问题；GC 暂停只在时间和持续时长可对应时作为解释。
- 回环路径异常时先校准测量链路。只有 DNS 路径异常时，再定位组件或夹具。
- 明确并记录条件修正后，才在同一新条件重新执行固定原版 A/A；通过后恢复候选初筛与正式矩阵。原 CPU、RSS、尾延迟及发送节奏门槛保持，不通过则停止，不能重复到偶然通过。

Redis 内在延迟诊断是 CPU 密集任务，必须与性能对照错开，参考 [Redis 官方延迟诊断](https://redis.io/docs/latest/management/optimization/latency/)。调度等待字段参考 [Linux 调度统计](https://www.kernel.org/doc/html/latest/scheduler/sched-stats.html)。诊断工具 `scripts/diagnose-dns-scheduling.py` 明确输出 `diagnostic_only=true`、`performance_accepted=false`；原版单组诊断不能替代版本对照。

初轮四项已按顺序完成；后续补充统计捕获到新的大停顿，指定的一次 A/A 复测也再次超限，详见[实际结果和证据缺口](dns-scheduling-diagnosis-results-2026-11-10.md)。

## 补充线程等待证据

前四项完成后，因详细统计未启用，再预先限定执行一次 60 秒、相同原版 HTTP/2 SOCKS 路径的诊断。仅在确认原值为 0 后临时启用 sched_schedstats，以服务退出清理和控制器双重恢复，保留修改前后值、逐线程运行／等待计数和同期开启的独立心跳。各测试单元有总时限；恢复检查失败即停止，不进入性能对照。这是不同采样条件下的归因补充，不能替代已失败的原版 A/A，也不能作为组件通过记录。

## 用户指定的一次复测

用户随后提示可能存在重启或操作干扰，并明确要求重新测试一次。该线索暂不作为已证实根因；保留全部旧失败，在新目录串行重做一轮固定原版 A/A：先 Redis，再 DNSCrypt，沿用组件收尾方案的时长、次数、输入、制品和门槛。复用上一轮摘要一致的普通发生器及对应冻结源码，不在性能进程中启用逐次发送记录或详细调度统计。独立心跳只作环境旁证，不用于删去慢查询。每个组件首次测量无效或重复性超限即停止该组件；此次复测不自动计作候选性能通过。
