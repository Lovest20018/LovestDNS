# DNS 组件更新与性能优化实施方案

日期：2026-11-07。状态：实施中；已固化 UI/网关联动基线并创建性能分支，独立组件构建和首轮缓存/容器验证已完成，性能对照进行中。最新证据与未完成关卡见 [实施记录](component-upgrade-performance-report-2026-11-07.md)。

2026-11-11 范围调整：用户明确用途为不超过十台终端的家用，后续按[家用验收范围](home-use-acceptance-2026-11-11.md)推进，优先解析正确、持续运行、缓存与配置恢复、资源占用和回退。微秒级排名与发生器调度研究暂停；下文原性能门槛及已有失败记录保留，未完成项目不自动阻塞独立的家用候选功能验证。默认组件升级和正式发布仍需另行确定。

实施复核发现新版 Unbound 的旧混合大小写缓存键复用边界，组合候选的纯 Redis 命中 P99 也未通过。依下文历史缓存与性能门槛，暂缓 Unbound 默认升级，Redis、DNSCrypt 继续独立候选验证；定制 MosDNS 仍冻结，41 在用实例保持原版本。详见 [大小写兼容记录](unbound-cachedb-case-compatibility-2026-11-07.md)。

## 1. 目标与边界

提升 DNS 分流后端的解析、转发、缓存访问和异常恢复表现，同时保持现有规则、自定义配置、历史持久化缓存和升级回退能力。

- 第一轮固定定制 MosDNS 的二进制及分流行为，记录其 SHA-256 和实际依赖；原有模板、规则优先级和默认参数作为对照基准。
- 独立更新 Redis、Unbound、DNSCrypt-proxy，先验证版本升级，再单独测试配置调优。
- 原生包与集成容器消费同一份组件清单；原生包首轮维持现有 Debian 12/13 amd64 范围。
- paopaogw API 继续作为可选观测来源，记录开启观测的开销；本轮保持现有联动功能范围。
- 普通 DNS 请求继续由现有核心处理。Go/Rust 重写、全量查询日志、新设备策略及 UI 重做另行评估。

## 2. 分支与当前成果基线

计划分支：`codex/dns-core-upgrade-perf`。

当前本地分支为 `codex/publish-lovestdns`，HEAD 为 `5baf9ca`，还有未提交的 UI、网关联动、API 契约和文档变更。HEAD 本身不能代表当前全部成果。

实施顺序：

1. 审阅已有变更范围，核对 41 当前安装包、版本与源码来源，记录尚未完成的验证。
2. 运行与已有改动有关的后端、前端、契约及构建检查，修复阻断问题。
3. 按可独立验证的功能整理提交；相互依赖的 API、前端与契约一起提交，记录可恢复的基线 commit 和安装包摘要。
4. 从该基线创建新分支，组件构建、单组件升级、参数优化分别提交。回退组件实验时保留已完成的 UI 和网关联动。

本轮先交付方案。上述基线提交和分支创建属于实施的第 0 阶段。

## 3. 组件候选与维护策略

版本基准来自此前对 41 运行二进制的核查；实施前再次采集核对。候选采用固定版本，执行时记录来源、提交或发行包摘要。

| 组件 | 当前基准 | 第一轮候选 | 验证重点 |
|---|---|---|---|
| 定制 MosDNS | `kkkgo/mosdns:240822.1` | 保持原二进制 | 分流优先级、缓存入口、定制插件、规则重载与当前结果一致 |
| Redis | 7.2.5，libc 分配器 | 7.2.17，同 7.2 系列 | RDB 加载、DB 0/1 隔离、淘汰、快照、内存及尾延迟 |
| Unbound | 1.21.1 | 1.26.2 | cachedb 读写、递归/转发、Redis 超时、预取、过期应答、用户配置 |
| DNSCrypt-proxy | 2.1.5 | 2.1.20 | 现有 TOML 与解析器目录、实际上游协议、SOCKS 路径、连接复用与故障恢复 |
| OpenSSL | Unbound 链接 3.3.1 | 3.5 LTS 系列的受维护补丁 | 固定具体补丁后构建，核对证书、TLS 与所需 ABI |
| musl、libevent、hiredis、Go 工具链 | 随旧镜像提供，尚需补全版本信息 | 按组件需要固定 | 编译参数、动态依赖闭包与运行兼容；保留冻结组件所需的原始依赖 |

Redis 首轮保持分配器和持久化策略，DNSCrypt 首轮保持协议和解析器选择配置。依赖或新版默认值发生变化时逐项列出，避免将功能变化误算为性能收益。

主线 MosDNS v5.3.4 的 UDP 重发等变化仅作为后续补丁参考。本轮不进行主线替换或定制分支重编译；未来依据具体缺陷、热点和兼容证据决定是否回移修复。

## 5. 构建改造

现状：`packaging/upstream.lock.json` 固定 PaoPaoDNS 镜像和脚本摘要；`scripts/build-native-package.py` 从该镜像提取所有二进制和共享库；集成 Dockerfile 直接继承同一镜像。

计划：

1. 保留 `upstream.lock.json` 作为原有模板、脚本和冻结组件来源，新增 `packaging/components.lock.json` 管理独立组件。
2. 每个组件锁记录版本、源码 URL/提交、校验摘要、工具链、构建参数、架构、依赖、静态/动态启动方式和产物摘要。构建基础镜像也固定 digest。
3. 在 `packaging/components/` 建立构建入口，生成一次组件产物，由两种发行方式复用。构建需要的网络访问留在构建阶段。
4. 按实际 ELF 依赖生成包装器：静态程序直接运行；动态程序使用经验证的私有加载器与库。冻结 MosDNS 所需依赖保留独立副本，避免被其他组件的库升级隐式替换。
5. 在包 manifest、build-info 中分别记录旧上游来源和实际组件来源，安装时校验全部载荷摘要。
6. 首轮原生验证 amd64；集成容器逐架构构建、运行验证。上游镜像含 arm64 清单不等于新组件已验证 arm64，模拟运行结果也不作为性能证据。

## 6. 历史缓存兼容与回退

保护对象包括完整 DNS 数据目录、用户规则与引用文件、`redis_dns_v2.rdb`、面板状态和服务参数。备份采用停止写入后的一致副本，或已完成且确认成功的快照；记录最后快照时间及未落盘增量的处理结果。

| 检查 | 具体方法与验收 |
|---|---|
| 文件读取 | 新 Redis 在独立副本上加载旧 RDB，核对 DB 0/1、类型、记录数量及加载错误 |
| 真实复用 | 旧 Unbound 向受控域名写入缓存并快照；重启后的新 Unbound 首次查询，从 Redis 读取旧条目；结合 Redis 读取、上游请求计数和 DNS 应答确认 |
| TTL | 比较缓存写入与读取时间，检查 TTL 递减、过期后的刷新及既有 serve-expired 行为；正常命中测试与过期应答测试分开 |
| 隔离 | 保持 DB 0/1 用途、键计算种子及 cachedb 键值语义；用两条路径的受控不同答案验证缓存不会串用 |
| 新写入 | 新版写入、保存、重启后仍可复用，快照失败能报告原因 |
| 用户改动 | 检测并保留自定义配置及引用文件，使用目标版本校验；升级初始化过程不得覆盖用户内容 |
| 回退 | 恢复旧产物、旧配置和升级前原始数据，验证 DNS 与缓存；归档候选产生的数据，回退保留原始快照 |

Redis 7.2.5 与 7.2.17 的 RDB 格式版本均为 11，这仅说明文件格式具备兼容基础。Unbound 的实际读写和命中仍需实测。

MosDNS、Unbound、DNSCrypt 的纯内存缓存按重启机制重建；RDB 不代表完整查询历史或全部内存状态。过期数据仍按 DNS TTL 和过期应答策略处理。

若某候选不能复用历史缓存，先阻止其进入默认升级组合并定位原因；兼容问题可能通过继续固定该组件解决。需要重建缓存时单独说明范围，保留原件，不静默清空现有缓存。

## 7. 性能测试设计

测试由固定版本的负载工具及脚本编排；dnsperf 作为首选负载工具，实施时核对其延迟记录能力。P95/P99 必须来自可核对的逐请求数据或直方图，不能由平均延迟推算。

| 场景 | 要回答的问题 |
|---|---|
| MosDNS 入口热缓存 | 前端缓存命中时，组合升级有无额外开销 |
| Unbound 内存命中 | 排除前置缓存后，内存缓存与线程配置表现如何 |
| Redis 热、进程内存冷 | 历史缓存是否复用，cachedb 访问延迟及重启后恢复如何 |
| 全冷递归/转发 | 在受控权威与上游下，解析正确性和延迟如何 |
| 混合请求 | 固定 A/AAAA/CNAME/NXDOMAIN/短 TTL 数据集，在不同命中比例下比较 |
| 加密转发与 SOCKS | 各自记录直连和实际代理路径，验证连接复用及恢复 |
| 故障 | 在测试网络内模拟 Redis 停止/变慢、上游丢包/超时、UDP 截断转 TCP，观察尾延迟及恢复 |
| 观测开销 | 分别比较面板关闭、普通面板使用、网关观测开启，记录采集与轮询开销 |

执行要求：

- 原始版本与候选使用相同配置、资源限制和数据初始状态。分别测试单组件替换与最终组合，避免混淆收益来源。
- 可控场景采用固定数据和随机种子，每轮恢复相同缓存状态；混合负载建议先用 90%/50%/10% 命中目标，记录实际达到的比例。
- 预热后每个负载档运行至少 120 秒；预先固定重复次数，关键场景至少 5 次，采用 A/B 交错顺序并报告全部结果。
- 记录发送、完成、超时、错误答案、有效 QPS、P50/P95/P99、各进程 CPU/RSS、Redis 内存/淘汰/快照和上游请求量。
- 检查负载发生器与 paopaogw 等共存进程的资源占用。出现资源争用、背景升级或测试端瓶颈时，将该轮标记为不可比较并重跑。
- 公网解析、实际代理与外部线路结果单列；这些结果用于实际体验核查，稳定的性能结论以受控对照为依据。

## 8. 参数优化候选

先使用旧配置完成版本对照，再从下列方向逐项实验：

1. **Redis 访问超时**：利用新 Unbound 的连接/命令独立超时；依据本机 socket 实测和故障恢复选择值，避免直接套用文档示例。
2. **缓存资源分配**：根据进程内存、实际命中率与淘汰率分配 Unbound/Redis 预算，为网关、Web 和采集留余量。现有 prefetch 与 serve-expired 已启用，先评估其实际效果。
3. **Unbound 并发**：检查容器 CPU 配额、线程、缓存 slabs、出站请求容量及文件描述符是否匹配；每项变更分别对照。
4. **DNSCrypt 上游与连接**：评估负载均衡、连接复用、超时及 SOCKS 链路；保持现有安全和协议要求，比较对应配置的实际效果。
5. **缓存留存与持久化**：观察旧记录、LRU 淘汰和快照停顿；TTL、过期应答或持久化语义的变更单独试验，第一轮保留现有行为。
6. **观测采集**：只有测到明显开销时调整采样、批量读取、并发去重和响应缓存。保持采集与 DNS 查询链路解耦。

分配器切换、内核网络参数调整、MosDNS 容量和转发行为变化不作为首轮默认优化。只有实测定位到相关瓶颈后再扩展范围。

## 9. 验收与 41 部署

以下是计划采用的筛选阈值，基线阶段先确认测量噪声；它们不是提速承诺：

- 受控功能测试全部通过；规则、答案、TCP 回退及缓存隔离无新增错误。
- 相同受控负载下，有效吞吐和 CPU 回退原则上不超过 5%；P95/P99 回退不超过 `max(基线的 5%, 0.2ms)`；稳定 RSS 增长超过 10% 时暂停默认纳入并定位。
- 上述性能门槛针对相同资源、相同负载及同一类测试。基线噪声超过阈值时先修正测试条件，不能据此宣称优化。
- 参数进入默认值，需要目标场景的尾延迟、CPU 或可持续吞吐至少一项取得约 10% 的可重复改善，或明确改善故障恢复；其他核心场景和资源预算仍需通过。
- 缓存复用、持久化、升级失败恢复与显式回退全部通过。
- 最终候选进行至少 2 小时持续负载测试及 24 小时测试机观察，记录崩溃、重启、内存趋势、快照失败及网关联动状态。观察未完成时标记候选状态。

41 的原生服务部分内部端口固定为 5301–5304，只有独立数据目录和不同 Web 端口不足以并行隔离。受控测试采用独立网络环境；原生整包升级验收采用备份后的顺序 A/B 切换。故障注入限定在测试网络，现有 paopaogw 保持可用。

先完成基线采集、备份和隔离测试，再升级 41 的 LovestDNS 测试实例。采用已有安装、健康检查与回退入口，保存每次运行的组件清单、配置摘要和结果。既有 UI、网关联动继续执行回归检查。
