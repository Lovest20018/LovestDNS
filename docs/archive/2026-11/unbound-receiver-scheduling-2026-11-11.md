# Unbound 接收侧调度归因

[逐请求试验](unbound-p99-ablation-2026-11-11.md)在旧版 A/A 第二对停止，后组最慢 300 条中 266 条的最长阶段是内核已见应答至客户端读取。这次继续区分该阶段内接收线程的状态，不重做 A/A，也不进入版本性能验收。

## 预定范围

复用原来 SHA-256 为 `11495b62767fca29e1a50e9b7b5b13e04ff3812270c0652ac1f6ff46eb490580` 的实验 dnsperf。固定旧版 Unbound 1.21.1、Redis 7.2.17、内存热缓存、内存记录、过期应答超时 0、相同种子和最多 64 个在途请求。角色继续分别使用 CPU 8 至 14，发生器允许 CPU 13、14，测试网络只含回环接口。

Linux 定向测试后，先执行一次 3 秒、100 QPS 的功能检查，再执行一次 60 秒、500 QPS 的诊断。任一工具、正确性、CPU 分配、限额或保护检查失败即停止；不选择性丢弃样本或反复运行来寻求通过结果。现有服务由独立单元监视，不更换组件或配置，不读取或传输现场查询与缓存快照。

## 观测方法与限制

仅创建和移除本次私有 tracefs 实例，按接收线程 TID 过滤 `sched_switch` 与 `sched_wakeup`。唤醒可以在其他 CPU 发出，因此事件过滤覆盖所有 CPU。缓冲区、时钟及事件开关只写私有实例；不修改全局 tracing 或 sysctl。独立实例、事件字段过滤及 `mono` 时钟的语义见 [Linux ftrace 文档](https://docs.kernel.org/trace/ftrace.html#instances)和[事件过滤说明](https://docs.kernel.org/trace/events.html#event-filtering)。

导出时去掉其他进程的名称和 PID，仅保留目标线程的时间、CPU、切入／切出／唤醒及切出状态。所有 CPU 的丢失计数必须为零。接收线程创建后的发现窗口可能留下未覆盖的启动请求；这些请求继续保留在完整包计时中，调度归因单独报告覆盖范围。同一微秒的事件若不能确定顺序，随后状态保守标为未知。

用全程夹取的实时时钟／单调时钟样本建立对齐范围。对齐不确定度超过 100 μs 则不产出归因。每条内核应答到客户端读取的区间按运行、可运行、睡眠及未知状态求交；只有扣除时钟误差和每个事件的微秒取整余量后，某一状态仍占整个区间一半以上，才认定该状态占多数。其余列为混合或过短。

可运行状态意味着线程等待获得 CPU；运行状态仍可能含中断或虚拟机被宿主暂停的时间，不能视为纯用户态 CPU；睡眠状态本身不能区分内核交付与应用阻塞。只做一次带追踪诊断，不据此量化追踪自身的开销，也不将本轮分位数与无追踪试验当成受控性能对照。

## 本轮结果

2026-11-11 完成一次 60 秒诊断：**在被调度追踪覆盖、内核应答后等待至少 1 ms 的 60 条请求中，58 条（96.7%）的该段时间主要处于可运行、等待 CPU 的状态，另外 2 条主要处于睡眠状态。** 这里的“主要”已扣除对齐不确定度和事件取整余量。它把本轮这些长等待进一步定位到接收线程的调度等待，尚不能区分来宾系统内的 CPU 竞争和宿主机调度影响，也不能认定历史 A/A 波动均由同一原因造成。

30,000 条正式诊断查询全部正确、socket 与抓包均零丢失；客户端 P95／P99 为 0.519／0.875 ms，内核往返 P99 为 0.504 ms，应答后至读取 P99 为 0.373 ms。这些分别是各组分位数，不能相减来拆分整组 P99，也不与前次无追踪结果作优劣比较。

追踪保留 89,137 条事件，覆盖 29,795/30,000 条请求（99.32%），205 条未覆盖请求仍保留在原始包计时中。16 个在线 CPU 的追踪丢失计数全为零；其中有 248 次目标线程唤醒从 CPU 11 发出，证明只记录发生器 CPU 会漏掉事件。全程 123 次夹取时钟样本给出的保守对齐不确定度为 **54 μs**，未超过预定的 100 μs 上限；本轮没有同一微秒的事件顺序歧义。

| 调度覆盖样本 | 数量 | 可运行占多数 | 睡眠占多数 | 混合或过短 |
| --- | ---: | ---: | ---: | ---: |
| 所有已覆盖请求 | 29,795 | 109 | 1,586 | 28,100 |
| 已覆盖请求中客户端最慢 1% | 298 | 80 | 114 | 104 |
| 已覆盖且应答后等待至少 1 ms | 60 | 58 | 2 | 0 |

“最慢 1%”在已覆盖请求中重新选出，不能与完整 30,000 条中的 300 条直接互换。多数短间隔在保守误差下不能确认主导状态；各组均无运行状态占多数的样本，并不意味着实际收包处理时间为零。60 条长应答后等待样本的可运行时间中位估计为 2.335 ms，这仍是估计值，状态占多数的判定使用上述更保守的下界。

热查询期间合成上游请求和 Redis 命中均为零；角色 CPU 分配验证通过，cgroup CPU 限流、memory max、OOM、OOM kill 无增量。Linux 定向测试 70 项通过；Windows 定向测试 67 项通过、1 项 Linux 专用检查跳过，另两项既有本地 UDP 夹具检查未纳入本次 Windows 定向集合。3 秒功能组 300 条查询全部正确，其结果只用于验证工具，不纳入上表。

## 失败记录和收尾

首轮在启动压测进程前因隔离单元缺少 `setpriv` 收缩权限集所需的 `CAP_SETPCAP` 而退出，未产生查询或调度样本。保留该轮完整失败和停止记录，在另一个新目录内修正单元能力后才执行功能检查与上述唯一一次 60 秒诊断。`CAP_NET_ADMIN` 只用于启动私有回环接口，进入压测子进程前从能力边界中移除；未因此扩大到全局网络或内核配置权限。

首轮收尾曾因自动审批接口连续返回 HTTP 409 而延迟；用户确认接口恢复后继续，已完成原收尾动作。首轮和修正轮合计 17 次独立健康探测零失败，两个目录各自的 17 项收尾检查全部通过。所有试验／监视单元已停止，无残留试验进程或私有追踪实例；在用服务、制品、配置、启动标识、调度统计开关和全局追踪设置均未变化。
