# 固定速率 DNS 性能对照的校准方法

日期：2026-11-07。适用于本轮受控 Unbound / Redis 比较。此前失败及 [补发突发的诊断证据](dns-benchmark-loss-diagnosis-2026-11-07.md) 保留；本方法不把旧失败转换成通过。

## 校准内容

此前独立故障注入已证明，dnsperf 暂停后补发可在原版与候选中造成服务端 UDP 队列溢出。第一轮校准只调整负载发生器的最大未完成请求数，从 256 改为 64；保持提供速率 1000 QPS、组件默认参数、四个测试 CPU、数据及答案检查相同。

`scripts/benchmark-dns.py` 新增 `--max-outstanding`，默认仍为 256，实际命令及选定值一并入证据。64 是此测试环境的实验设置，不是运行服务的线程、队列或内核参数建议。它限制停顿后能同时积压的请求数；固定速率对照不等于最大吞吐或突发承受能力测试。

答案抓包仍在独立进程中进行，现在同时保存内核包时间戳的摘要：请求/应答数、最大相邻到达间隔、对齐 1ms 时间桶的峰值和最密集的五个桶。不能把抓包读取线程恢复后的批量读取误判成发送端突发。时间戳使用内核实时时钟，乱序计数随结果保存；到达间隔仅作为诊断，不能单独证明调度停顿的来源。

每 0.5 秒采样客户端和服务端 UDP 收包队列及 socket 累计丢包；服务端另核对测量前后计数差。队列峰值是采样值，可能漏掉更短的峰值。抓包、负载发生器、受控上游的 CPU/RSS 单列，DNS 资源只汇总被测核心。

## 执行与判定

1. 构建与其他压测结束后，等待至少 60 秒没有检测到编译任务，再开始本轮。测试期间出现编译任务，保留整次记录、标注不可比较，使用新目录重跑；不能只丢弃较慢的组件或轮次。
2. 在独立网络命名空间启用 loopback，先以短测确认四组负载、答案核验、到达记录和两端丢包证据有效。短测不能签署性能通过。
3. 默认参数分四组：原版、仅更新 Redis、仅更新 Unbound、组合更新。每组 120 秒，重复五轮，交错顺序；固定数据、资源及最大未完成请求数。20ms 参数调优另行对照。
4. 汇总核对实际时长、发送量、有效 QPS、逐条答案、丢包、全部轮次与资源记录，并核对实际 dnsperf 命令与声明的最大未完成请求数。继续使用既定 CPU、延迟、RSS 筛选阈值。
5. 任何一轮错误或超时都保留并停止复核。部分场景通过不能签署全部性能、MosDNS 分流、加密转发、观测开销或持续运行验收。

在已启用 loopback 的独立网络命名空间中，从仓库根目录运行（目录及工具路径按环境提供）：

```sh
taskset -c 4-7 python3 scripts/benchmark-dns.py \
  --baseline-home /path/to/core-baseline --bundle /path/to/components-bundle \
  --dnsperf /path/to/dnsperf --work /path/to/new-comparison \
  --duration 120 --repeats 5 --qps 1000 --max-outstanding 64 \
  --cases baseline,redis-only,unbound-only,combined --scenarios mixed90
python3 scripts/report-dns-benchmark.py /path/to/new-comparison/results.json \
  --output /path/to/new-comparison/report.json
```

测量需要 Linux `CAP_NET_RAW`；需要创建网络命名空间时另需相应权限。组件与历史缓存兼容说明仍以 [组件构建文档](../../../packaging/components/README.md) 为准。运行实例、缓存和全局内核缓冲参数不参与这些隔离实验。

## 冷查询较多场景的容量校准

原夹具每个 UDP 请求创建一个线程。1000 QPS 全冷短测中，直接访问夹具也出现高尾延迟；增加 `--fixture-udp-mode serial` 后，受控 UDP 应答由常驻线程顺序处理，避免逐包创建线程。默认仍为 `threaded`，旧 hot / mixed90 / MosDNS 记录不改变。TCP 夹具仍按原方式处理，解析、TTL、否定答案及截断应答语义相同。该模式供无人工延迟的基准场景使用，不用于模拟多个并行的慢上游。

顺序模式的 10 秒直连检查完成 10000 条、约 999.99 QPS，P99 1.066ms；经过 Unbound/Redis 后，原版及组合候选分别约 876.18 / 860.47 QPS，仍未达到提供负载。这不足以认定全部瓶颈均在夹具，也不是可比较的 1000 QPS 性能通过记录。

另以 500 QPS 全冷检查，直连、原版、组合候选分别完成 5000 条，无超时或错误；后两组约 499.99 / 499.79 QPS，P99 5.440 / 5.638ms。以此负载继续原版与组合默认参数在 mixed50、mixed10、cold 场景的 120 秒、五轮对照。此比较与既有 1000 QPS threaded 场景分开，不用于宣称最大吞吐，或掩盖原有 1000 QPS 全冷不足负载的记录。

## 区分 DNS 路径与客户端读取延迟

全冷五轮中的候选 P99 轻微超限后，继续增加诊断量 `answer_validation.wire_latency`：用 DNS ID、问题名、类型和类匹配同一抓包流中的请求及应答，以内核时间戳计算往返时间，按微秒向上取整后统计分位数。这个时间包含 DNS 路径及其中的调度等待，但不包含应答已经到达 loopback 后客户端延迟调用 `recv()` 的时间。不能用它替换 dnsperf 的既定验收指标。

记录未完成请求、键冲突、未匹配应答和时钟回退；这些条件异常时诊断量不能标为完整。抓包丢包及答案错误仍按原方法判定。旧测量只有到达摘要，不能追补逐请求往返分位数；新旧方法的数据各自保留摘要。

## Redis 命中专用场景

`--scenarios cachedb` 先使用整份唯一 A/AAAA 问题输入填充 Redis，逐条校验答案、完成数、上游请求数和 DB 条目数，再只重启 Unbound，保留 Redis 进程与数据。正式负载仍使用同一输入，每个问题仅查询一次。每轮记录重启前后进程 PID、输入摘要、完整准备结果和正式负载的 Redis 命中/未命中计数差。

汇总要求每条正式查询恰好增加一次 Redis 命中，未命中和上游请求均为零；没有清空 Unbound 内存、Redis 被重启、准备不完整或输入不同都会拒绝通过。准备阶段不计入正式性能资源，但单独保留记录。该场景只支持直接进入 Unbound，不把 MosDNS 前置命中算作 Redis 收益。

准备速率最高 500 QPS；准备加测量的计划时长不得超过 480 秒，为 600 秒 TTL 留出余量。组件启动后及轮次间不查询测量域名。建议首轮使用 500 QPS、120 秒、q64、串行夹具，约 6 万条缓存记录；这些数量和内存预算属于受控实验，不是修改运行缓存容量的建议。若实际准备期间丢包、容量不足、记录过期或发生上游访问，保留失败，不能换用内存热结果补签。

## Redis 命中比较前的 A/A 重复性检查

组合候选 P99 超限后，先按相同测量方法只运行原版：500 QPS、q64、串行夹具、共享 CPU 4–7、每组 120 秒、固定六组，每组重新填充相同数据并只重启 Unbound。测量前等待编译任务结束及 60 秒冷却；全部结果保留。

预先固定相邻的第 1/2、3/4、5/6 组为三对。每对 P95、P99 的绝对差必须不超过 `max(该对较小值 × 5%, 0.2ms)`，且负载、答案、Redis 路径、socket 及抓包检查均有效，才能标记本次 A/A 稳定。此为测量重复性检查，不是组件性能通过；原版单一组合也不能被普通报告签署组件对照通过。

若未满足重复性，保留失败并先校准测试条件，不直接把同幅度的版本差异归因于组件，也不扩大验收门槛。只有明确记录测试条件变更后，才能在相同新条件下重新比较各组件。

共享 CPU 的首对原版 P99 已出现 0.425ms 差异。下一项条件校准只改变实验进程放置：发生器 CPU 4、受控上游 CPU 5、Redis 与 Unbound CPU 6、抓包 CPU 7，每次准备和正式测量均记录角色实际亲和性；保持原数据、120 秒、六组和三对判定。先完成原条件全部六组，再串行完成缓存重建回归，最后进行该条件下的原版 A/A。若仍不稳定，停止以该机器的小幅尾延迟差异签署版本回归或通过；若稳定，再以相同放置方式比较四种组件。原版与候选的旧记录不与新条件合并。

实际执行中，分配 CPU 的第二组在准备阶段出现上游请求数 60011、唯一输入及缓存键数均为 60010，其他答案和丢包检查通过。该次记录按原工具严格要求停止，未完成三对 A/A，不能称为重复性已通过或已失败。额外的上游抓包和受控延迟诊断不计为组件性能验收；不得将自然重试的推测当作原次逐包证据。

## 准备协议 v2（2026-11-09）

后续使用 `unique-question-coverage-v2`，增加受控上游的逐问题账本：按忽略大小写的问题名、类型和类核对覆盖，分别保存 UDP/TCP 尝试数及账本摘要。准备阶段允许已核对、总量不超过唯一问题数 1% 的额外尝试；缺失或意外问题、错误答案、键数不足及无法解释的计数仍拒绝。正式测量保持零上游、零 Redis 未命中、每条查询一次 Redis 命中的原条件。

新方法在新目录完整执行，旧结果没有该协议声明时继续采用原精确计数检查。它不补签此前中止的 A/A，也不追认原次多出请求的来源。固定轮次、A/A 及分组件执行条件见 [后续验收方案](component-maintenance-next-validation-2026-11-09.md)。
