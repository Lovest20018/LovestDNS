# Unbound P99：逐请求归因试验

基线为 `4a82f86`。此前旧 Unbound 1.21.1 在相同输入下两次客户端 P99 为 1.612／1.128 ms，内核往返 P99 为 0.486／0.864 ms，且都是正确的内存热命中。详细条件和停止结果见[原报告](component-boundary-followup-results-2026-11-10.md)。本试验先确认客户端日志是否影响尾延迟，再按原重复性门槛决定能否进入版本对照。

## 计时和单变量对照

按 [DNS-OARC 发布清单](https://www.dns-oarc.net/tools/dnsperf)的 SHA-256 固定 dnsperf 2.14.0 源码，构建一份专用二进制。两种模式都开启 `-v` 并保持原取时点、收发、匹配、记录分配和释放。`stream` 保留逐条日志的正常输出；`memory` 只跳过成功查询日志的即时写出，两者都把取时结果写入预分配内存，收发线程退出后才导出。使用这同一构建比较模式，不混用前次构建。两种模式保留相同的客户端分位数定义。

在单客户端 IPv4 UDP 回环中，按事务 ID 和可验证的时间顺序将 `gettimeofday` 与 `SO_TIMESTAMPNS` 匹配。每条请求得到三个相加等于客户端延迟的间隔：用户取时至内核查询、内核查询至内核应答、内核应答至用户读取。后两套时钟都是系统实时时钟，配对前将内核时间取整到微秒。完整保留逐请求证据；ID 重用必须可唯一分辨，缺包、重叠或时钟倒序使整组无效。每组记录三个阶段的分位数及客户端最慢 1% 的阶段分解。内核往返仍包含服务端等待，不能视为 Unbound 的纯 CPU 时间。

## 固定执行顺序

测试机 41 沿用独立 CPU 分配、回环网络和串行合成上游。Redis 固定 7.2.17；内存缓存内容、输入种子、500 QPS、最多 64 个在途请求保持固定。正式实例的健康监视独立运行；不切换在用实例、组件或配置，不接触历史 RDB，不传输账户、缓存或现场查询。

1. 先做 Linux 定向测试与四组 3 秒功能检查：旧版两种记录模式的热缓存、旧版和新版各一组 Redis 命中。短测不计入性能结论。
2. 旧版热缓存按 `stream → memory → memory → stream` 执行，每组 60 秒。诊断以两组配对的原始值和最慢 1% 分解为依据，保留所有组。只改变日志方式，不改负载或版本。结果只说明日志路径在本次窗口的可观测影响，不能自动解释历史波动。
3. 固定 `memory` 与 `serve-expired-client-timeout: 0`，对旧版热缓存、Redis 命中各执行三对 A/A，每组 60 秒。P95、P99 成对差值均须不超过 `max(较小值 × 5%, 0.2 ms)`。任一不通过即停止，不删慢样本、不重测挑选，也不改用内核指标替代。
4. A/A 通过后固定 Redis、上游和显式 `serve-expired-client-timeout: 0`，对新版 1.26.2、旧版 1.21.1 做热缓存、Redis 命中、全冷转发、50% 混合四个场景，五对交错，每组 120 秒。沿用既有用户态 P95/P99、CPU、RSS、吞吐和正确性筛选。这一轮的筛选适用于本次固定配置。
5. 在同一新版上比较 `0` 和 `1800 ms`，对 Redis 命中、全冷转发、50% 混合分别做三对交错，每组 60 秒。它评估当前 TTL 和受控上游下的定时器开销；不据此决定生产过期应答策略。

试验执行与结果以独立证据为准；本方案本身不构成性能批准。只有合成查询、试验工具与公开上游构建输入用于此轮，故障和门槛失败均保留。

## 本轮结果

2026-11-11 已在测试机 41 按上述方案完成四组日志诊断和两对旧版热缓存 A/A；第二对旧版 A/A 的 P99 差超门槛，立即停止。**本轮将大量慢查询定位到应答已被内核观察到之后的接收侧等待，但不能把它进一步认定为特定线程、虚拟机或内核调度缺陷。关闭实时日志未改善尾延迟。** 新版正式对照和新版定时器差异试验均未执行。

Linux 定向测试 **64 项通过**，四组 3 秒功能检查也全部通过；短测包含新旧 Redis 命中路径，仅用于证明记录工具、正确性和 CPU 分配可用。Windows 的非回环定向检查 61 项通过、1 项 Linux affinity 跳过；完整检查仍有两项既有本地 UDP 夹具超时，未记为 Windows 全通过。

### 日志方式对照

每组 60 秒、500 QPS，均完成 30,000 条正确查询，socket 与抓包零丢失；8 组长测全部为旧版 Unbound 1.21.1，显式过期应答超时 0，Redis 7.2.17。表中时间均为 ms，后三列来自同一批请求的原始时间戳。

| 顺序／记录方式 | 客户端 P95 | 客户端 P99 | 内核往返 P99 | 内核应答至用户读取 P99 |
| --- | ---: | ---: | ---: | ---: |
| 1：实时日志 | 0.471 | 0.751 | 0.441 | 0.344 |
| 2：内存记录 | 0.509 | 0.960 | 0.454 | 0.544 |
| 3：内存记录 | 0.476 | 0.878 | 0.435 | 0.383 |
| 4：实时日志 | 0.450 | 0.754 | 0.444 | 0.333 |

两个配对中内存记录的客户端 P99 分别高 0.209／0.124 ms，内核往返 P99 仅相差 0.013／0.009 ms。实时日志组的发生器 CPU 时间为 62.28／62.17 秒，内存记录为 61.55／61.28 秒；少量 CPU 降低没有伴随尾延迟改善。只有这四组固定顺序数据，不对日志作普遍的性能优劣推断，也不能据此解释历史窗口。源代码中的实时刷新开销确实存在，但本轮不支持“逐条写日志是旧版尾延迟波动的主要原因”。

### 旧版重复性停止

| 旧版 A/A | 客户端 P95 | 客户端 P99 | P99 差 | 原门槛 | 判定 |
| --- | ---: | ---: | ---: | ---: | --- |
| 第一对 | 0.420／0.485 | 0.692／0.747 | 0.055 | 0.200 | 通过 |
| 第二对 | 0.506／0.594 | 0.926／1.772 | 0.846 | 0.200 | 停止 |

第二对两组的内核往返 P99 为 **0.447／0.570 ms**；应答被内核观察到至客户端读取的 P99 为 **0.483／1.383 ms**。这些是各自的分位数，不能相减或相加来分配整组 P99 的来源。

逐请求选出各组客户端最慢的 300 条，再比较每条的三个阶段：第二对前组 219/300 条、后组 **266/300 条（88.7%）**的最长阶段均是“内核已见应答之后至客户端读取”。后组这 300 条的三个阶段中位数分别为 **0.014／0.168／1.851 ms**，客户端总延迟中位数为 2.066 ms；各列中位数也不必相加等于总量。后组有 316 条请求的应答后等待至少 1 ms，分布在 56 个不同秒桶，而非只有开头的一次停顿。

后组已经停用即时成功日志，所以这段接收侧等待不能简单归因于逐条写日志。抓包点到客户端读取仍包含内核交付、调度与收包执行等因素；缺少线程调度追踪，尚不能在它们之间继续归因。内核往返本身仍有尾部变化，也不能认定服务端完全无抖动。

所有长测都确认在测期间上游请求为 0、Redis 命中计数为 0（512 次 miss 来自测前预热），无 Redis 淘汰／持久化压力参与热查询；CPU affinity、查询正确性与计数有效，cgroup 限流、memory max 和 OOM 均无增量。不会把这些旧版数据用作新版无回归证据，也不替换原验收指标。
