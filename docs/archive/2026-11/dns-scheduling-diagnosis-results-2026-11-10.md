# 性能校准的调度诊断结果

基线为 `ab9781a`，执行范围见[诊断方案](dns-scheduling-diagnosis-plan-2026-11-10.md)。初轮四项未出现大停顿，补充线程统计时记录到新的 **316 ms 发送空档和同一时段 312 ms 独立心跳空档**。随后按指定复测一次原版 A/A，Redis 重复性再次超限，DNSCrypt 再次出现约 275 ms 发送空档。证据将排查重点转向更广的调度或虚拟机停顿，尚未确认宿主侧具体根因。旧失败完整保留，候选性能验收仍未通过。

## 实际执行

复用现有 VMware 测试环境、原版 DNSCrypt 和原版 `redis-cli`，未重编译 DNS 组件。原发生器的二进制摘要与上一轮一致；新增发生器仅增加可选发送阶段记录。固定 60 秒，串行执行以下四项，期间持续采集独立 10 ms 心跳。

| 诊断 | 已发送／完成 | 内核最大发包间隔 | 结果 |
| --- | --- | --- | --- |
| 原发生器直接访问串行回环应答器 | 5,978／5,978 | 18.181 ms | 答案、双端 socket、全量抓包配对及发送节奏有效 |
| 带记录的发生器访问同一回环路径 | 5,979／5,979 | 19.135 ms | 同上，发送记录与查询数一致 |
| 带记录的发生器访问原版 DNSCrypt HTTP/2 SOCKS 路径 | 5,991／5,991 | 24.553 ms | 同上，HTTP/2、ALPN、SOCKS 路由及测量检查有效 |
| 原版 `redis-cli --intrinsic-latency 60` | 不发送 DNS／Redis 请求 | 不适用 | 进程内观察到的最大延迟为 3,273 μs |

三组 DNS 诊断均零丢失、零错误答案，发送间隔在原有 5–50 ms 范围内。它们只有单组原版测量，并增加了诊断采样，不能用于签署组件性能通过，也不能替代固定原版 A/A 或新旧版交错矩阵。

## 发送阶段和调度证据

| 带记录的路径 | 最晚唤醒 | 最大锁等待 | 最大发送调用耗时 | 测量期间 GC |
| --- | --- | --- | --- | --- |
| 回环 | 10.362 ms | 0.045 ms | 1.982 ms | 0 次 |
| DNSCrypt HTTP/2 SOCKS | 14.914 ms | 0.058 ms | 1.789 ms | 0 次 |

DNSCrypt 最长约 24.55 ms 的发送间隔，主要对应计划唤醒到实际唤醒之间的延迟；该条记录的锁等待约 1.34 μs，发送调用约 0.119 ms。当时独立心跳的重叠间隔约为 10.95–11.04 ms。回环最长间隔发生时，独立心跳也保持约 11 ms。这些记录说明本轮最长发送间隔没有对应的同量级跨 CPU 心跳停顿，仍无法解释此前约 197 ms 的空档。

独立心跳共保留 23,572 个样本，整轮最大间隔 33.493 ms。四组测试 cgroup 的 CPU 配额限流增量均为零，内存 `max`／OOM 事件增量均为零；CPU 压力累计值存在增量，其中 DNSCrypt 组 `some` 约 1.969 秒、`full` 约 0.791 秒。这些累计值没有给出原故障发生时各线程的等待原因。

初轮内核 `sched_schedstats=0`，逐线程调度等待字段不可用于归因，零值不代表没有等待 CPU。采样器约每 100 ms 取样，实际最大样本间隔约 179 ms、最大一次采集耗时约 78 ms；记录保留了这些空档。采样的墙钟／单调时钟偏移变化均小于 0.05 ms。CPU 绑定未提供独占 CPU 的保证。

## 补充线程统计：大停顿再次出现

为补齐线程等待证据，预先限定另执行一次相同原版 HTTP/2 SOCKS 路径的 60 秒诊断。通过测试服务的 `ExecStartPre` 临时启用 `sched_schedstats`，退出清理与控制器分别负责恢复。全部采样均记录统计值为 1，结束后核对恢复原值 0。

本组 **5,956 次查询全部正确、零丢失**，双端 socket 和抓包没有丢包，HTTP/2、路由、资源等检查通过；**发送节奏检查失败**，原始记录完整保留。内核最大发包间隔 **316.325 ms**，发生器记录 **316.336 ms**。该次计划唤醒到实际唤醒延迟 **306.601 ms**，锁等待 **1.097 μs**、发送调用 **83.060 μs**，测量期间 GC 为零，也没有并发上限跳过。

另一组 CPU 上的 Python 心跳在同一时段出现 **312.008 ms** 间隔。由于另一个进程和 CPU 范围也同时延迟，单个 DNS 组件、发送锁或发生器 GC 无法独自解释本次现象；这是更广调度或虚拟机暂停方向的证据，尚不足以指定宿主 CPU、内存、存储或 Workstation 为唯一根因。

覆盖该事件的前后采样括号约 **541.885 ms**，观察到的发生器线程等待增量最高约 **9.541 ms**，另一个线程运行时间计数增加约 **309.418 ms**。这些是较宽采样窗口内的线程计数，未对应到发送 goroutine，不能将其直接当成 306 ms 延迟的因果解释。该窗口墙钟／单调时钟偏移变化约 54 ns；CPU 配额限流、内存触顶与 OOM 增量均为零。事后读取的祖先 cgroup 没有 CPU 配额限流记录，相关内核日志窗口无条目，宿主事件日志尚未核对。

本组 P99 仍约 **5.130 ms**：发生器暂停期间没有发包，已完成查询的尾延迟无法呈现完整停顿，所以原有逐包节奏门槛继续生效。该组不计作有效性能对照。

## 当前处理

测试环境已确认为 VMware Workstation。需对照实际宿主的 `vmware.log`、CPU／内存和存储记录；资源检查参考 [Workstation 官方排障入口](https://knowledge.broadcom.com/external/article?legacyId=1008360)。当前缺少宿主对应记录，保留重启或操作干扰等可能因素，不将其写成已确认根因。原有 CPU +5%、RSS +10%、P95/P99 增量 `max(基线×5%, 0.2 ms)` 和逐包节奏门槛保持。

根据可能存在重启或操作干扰的线索，指定在保持宿主和 VM 运行的窗口，**另执行一轮固定原版 A/A**。该复测安排不追认前述失败为无效干扰。先 Redis，再 DNSCrypt；复用上一轮普通二进制、夹具和对应冻结源码，资源限制、单组时长、最多三对及失败即停的规则保持。独立心跳只保留为环境旁证，不据此删掉慢查询。候选初筛和正式矩阵尚未启动。

| 原版复测 | 结果 |
| --- | --- |
| Redis 缓存命中 | 首对测量和资源检查有效，P99 为 1.947／1.732 ms，相差 0.215 ms，超过 0.2 ms，停止该组件；两组心跳最大间隔为 13.402／15.104 ms |
| DNSCrypt | HTTP/2 直连三对、SOCKS 前两对有效且重复性通过；SOCKS 第三对第一组最大发包间隔 275.081 ms，超过 50 ms，停止该组件；HTTP/1.1 未执行 |

本轮共完成 **13 组测量**：Redis 两组、DNSCrypt 十一组。DNSCrypt 最后一组 **2,973／2,973 次查询正确、零丢失**，发生器自身记录发送间隔 **275.079 ms**，没有并发上限跳过、未知报文或 socket／抓包丢包；除节奏外的测量检查与资源检查通过。独立心跳在该组测量期间最大间隔为 **277.102 ms**。普通发生器未记录逐次发送时间，因此本轮不能把心跳空档与最大逐包间隔精确配对；同组观测与此前带记录诊断的结果一并保留。

复测前后测试 VM 的启动标识、主服务 PID／启动时间及重启计数均保持不变，14 个复测相关单元已停止。未观察到完整来宾系统重启，但没有实际宿主记录，仍不能排除挂起、暂停或其他宿主操作。原版复测使用与上一轮一致的普通发生器、夹具和源码；由此也不能将新出现的 275 ms 空档单独归因于逐次记录或详细线程采样。此次指定复测到此结束，没有继续重跑或放宽门槛。

Redis 此前的 0.316 ms P99 差异仍未解释，本轮 3.273 ms 内在延迟样本也不构成因果证明。只有建立有效且可重复的原版对照后，才可恢复候选初筛与正式矩阵。

新增[诊断入口](../../../scripts/diagnose-dns-scheduling.py)提供 `loopback`、`dnscrypt`、`intrinsic` 和 `watch` 模式，要求新目录、有界时长、发生器精确摘要及一次性网络命名空间。逐次发送记录先存在有界内存，测量后才写新文件；所有结果显式标记 `diagnostic_only=true`、`performance_accepted=false`。此次 A/A 使用原发生器和对应冻结源码；若改用当前新增记录功能的发生器源码，须准备并核对其对应清单。

定向单测 Windows / Linux 各 **24 项通过**，带记录的真实路径均核对全部发送记录与抓包查询数一致。诊断的两份私有证据包分别索引 54／34 个文件，第二份完整保留第一份；下载后逐项核对摘要，并核对 100 个输入文件，其中 99 个非 Markdown 源码文件与当前工具一致。指定 A/A 复测另有 **167 个索引文件**，已核对 13 组原始计数、逐组有效性、所有相邻差值、冻结输入、服务及启动标识。

证据包不包含 RDB、生成的 TLS 私钥或实例配置。诊断阶段九个单元、复测阶段十四个单元均停止，临时内核统计开关恢复。复测后再次执行服务、核心文件、规则、身份、账户及回退备份等 **15 项收尾检查，全部通过**。默认组件未升级，候选初筛、正式性能矩阵和最终组合仍等待有效对照。

后续另经批准转到另一台 Debian 12 / KVM 宿主机，完成[独立性能对照](component-crosshost-performance-results-2026-11-10.md)。该窗口的 DNSCrypt 发包节奏有效、没有上述长空档，但第三对原版 P99 相差 0.253419 ms，重复性仍未通过，候选未测。Redis 在该宿主机独立通过三对校准及五轮正式筛选；此结果不追改本页原失败或证明具体宿主原因，默认升级和最终组合验收仍分别判断。
