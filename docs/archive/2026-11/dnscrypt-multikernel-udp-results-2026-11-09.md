# DNSCrypt 双内核 UDP 接收队列补充结果

从 `c3ebbba` 继续，完成 [本轮方案](dnscrypt-multikernel-udp-plan-2026-11-09.md)。**普通三补丁 combined 在 Linux 6.1 与 6.12、NET_ADMIN 有/无、IPv4/IPv6 共八个候选组合中，均保留 128/128 个受控积压问题。** 补足第二套实际内核的接收队列证据；低 rmem_max、持续吞吐、整机资源与尾延迟仍未验收。默认组件及在用服务未升级。

## 队列与丢包的实际结果

沿用原方法：先经实际 HTTP/2、ALPN h2 和直连受控上游预热 A/AAAA，再检查 4095 字节问题；暂停读者后发送 128 个 256 字节问题，每包独立 ID，恢复后核对所有收到答案与 `ss` 内核队列/丢包计数。

下表各行在 IPv4 与 IPv6 一致；combined 一行同时包含两种权限。

| 内核 | 实现 | NET_ADMIN | 内核接收容量 | 收到 / 128 | 内核丢包 |
|---|---|---|---:|---:|---:|
| 6.12 | upstream | 有 | 8192 B | 9 | 119 |
| 6.1 | upstream | 有 | 8192 B | 7 | 121 |
| 6.12 / 6.1 | upstream | 无 | 212992 B | 128 | 0 |
| 6.12 / 6.1 | combined | 有 / 无 | 425984 B | 128 | 0 |

**12 组无丢包，4 组保留原实现的强制小队列缺陷对照。** 共发送 2048 个积压问题，收到 1568 个，其余 480 个全部由解析端 socket 丢包解释；没有未知丢包、客户端丢包、重复或错答，恢复后队列排空。两套内核的小队列能容纳的问题数不同，不能固定假设都是 9 个；本轮要求收到数与实际丢包相加等于发送数，没有改变原缺陷对照的通过条件。

每组还完成 A/AAAA 两个 4095 字节 EDNS padding 问题，共 **32 次最大接收长度查询通过**。最大长度检查及积压查询均为缓存命中、零 DoH 回源；启动/预热期间实际 HTTP/ALPN 单独核对。各响应检查事务 ID、问题名、类型/类、状态、地址及正 TTL。

本轮没有改动发送队列、报文处理或缓存补丁。它证明这两个内核和当前接收上限下的有限积压行为，不代表 DNSCrypt 加密协议、公网解析器、任意突发规模或持续吞吐验收。

## 旧内核参数视图与低上限边界

两台宿主机均为 `rmem_max=rmem_default=212992`。6.12 在新 namespace 内显示只读全局 rmem 参数；6.1 不显示这两个文件。工具新增严格读取路径：两个文件都存在时直接读；都缺失且当前与参考 namespace 不同时，只在短命子进程中执行 `nsenter --net=/proc/1/ns/net -- cat ...`；部分缺失、值非法或读取失败均拒绝通过。DNS 客户端、夹具和解析进程始终留在测试 namespace。

每台主机另外用两种地址族实际申请 4096 / 65536 / 262144 / 1048576 字节 socket 接收缓冲，核对报告值符合当前上限；每个解析进程的队列容量也独立用 `ss` 验证。参数来源、实际内核和 namespace inode 写入结果，前后宿主参数摘要一致；没有通过默认值猜测旧内核容量。

这些观测与上游 [6.1 全局 sysctl 注册](https://raw.githubusercontent.com/torvalds/linux/v6.1/net/core/sysctl_net_core.c) 和 [6.12 对其他 namespace 暴露只读全局参数](https://raw.githubusercontent.com/gregkh/linux/v6.12.74/net/core/sysctl_net_core.c) 的差别一致。**本轮没有写任何 sysctl，也没有覆盖较低 rmem_max 的实机环境。** 已增加低上限导致候选丢包仍不能通过的反例检查；它只验证判定工具，不能冒充低上限实际运行。该关卡继续等待独立内核环境，不借用宿主全局参数做实验。

## 准备失败、回归与收尾

首次输入的两台任务均在完整矩阵前停止，原始日志及失败状态保留：

- Debian 13 的 43 项工具回归已通过，随后夹具身份检查发现复用了旧源码对应的夹具，拒绝启动矩阵。改用上一轮原生检查中已核验、与当前 `main.go` 匹配的夹具；没有修改组件或放宽摘要检查。
- Debian 12 系统 Python 没有 pytest，因此工具回归入口拒绝继续。没有安装依赖；最终工具回归在 Debian 13 完整执行，随后 Debian 12 运行全部八组实际矩阵。未声称在 Debian 12 执行了 pytest，也未跳过任何实际运行组合。

修正后的 Debian 13 **43 项定向回归通过**，包含参数来源、非法/不完整视图、低上限丢包不能误通过、候选身份与实际 SOCKS 夹具检查。本地 UDP 工具 **23 项通过**；扩大的 Windows 三文件检查为 **41 项通过、2 项因 WinError 10013 无法连接 loopback 而失败**，这两项未改判，Linux 中对应检查通过。26 个 API 契约样例检查通过，来源清单仅更新本轮两个 Python 文件的摘要，OpenAPI 与样例内容未变。

两台任务分别限制 CPU 4–7 / 200% 和 CPU 2–3 / 125%，内存上限均 768 MiB、低调度优先级且有总时限。记录到的 cgroup 内存峰值约 62.95 / 38.96 MiB，采样中的 CPU 限流及内存 high/max/OOM/oom_kill 为零；这仍是短功能运行的部分 cgroup 记录，不是完整服务性能对照。

包含准备失败在内，Debian 13 的 12 次、Debian 12 的 7 次在用 DNS 健康探测全部成功，合计 **19 次**。最低主机可用内存约 6053 / 4429 MiB。两台在用服务保持原 PID、零重启及 active，完整发布文件、配置、host resolver 和 rmem 参数与开始前一致；临时组件全部退出，实际测试 namespace 无剩余进程。归档后磁盘剩余约 3.73 / 6.12 GiB。
