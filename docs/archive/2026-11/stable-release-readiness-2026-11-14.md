# 软件更新代理与正式版收尾清单

2026-11-14。以 query1.4 原生预发布和 [query1.5 预发布](native-query15-release-2026-11-14.md)为依据。应用源码固定到 `d232acb3c92d7fef5bc64455e7778025a92e6f20`。建议首个正式版限定 Debian 12/13 amd64 原生部署、十台以内家庭终端；其他平台沿用各自验收范围。正式版不以继续扩充看板或微秒级排名为前提。

## 已实现与验证范围

本轮源码增加软件更新专用代理：直连、HTTP CONNECT、带远端域名解析的 SOCKS5，以及可选账号认证。版本检查、校验文件和包下载共用同一传输设置；保留官方来源、重定向、TLS 和摘要校验。代理失败如实终止，下载与信息读取有体积和时间上限。管理员可保存并检查，密码不回显，改设置使旧检查失效，运行中的任务阻止修改，未保存草稿阻止安装。

本轮验证包括：

- 本地真实 TCP/TLS 代理夹具覆盖认证、远端 DNS、跨 GitHub 下载域名重定向、证书拒绝、认证拒绝、无直连回退，以及生产下载函数的包和校验文件路径；管理接口覆盖会话、CSRF、字段校验、凭据保存和任务互斥。
- 合成网页覆盖保存后检查、密码不回显、草稿阻止检查与安装、还原，以及桌面/窄屏和明暗主题。合成任务没有安装软件。
- 新应用代码已在独立目录通过真实 SOCKS5 出口完成认证、远端 DNS、GitHub TLS 访问、官方发行包下载及包内文件校验；错误认证被拒绝。
- 固定候选在标记的原生测试实例完成官方 query1.4 安装、query1.5 升级、经真实网页接口和代理应用官方 query1.4、回退到 query1.5；配置、登录会话、实例身份、合成 Redis 数据和代理设置保留。代理离线和错误密码均在安装前失败，测试 DNS 继续运行。此流程使用已公开的旧发行版验证下载安装，尚未验证从官方发布渠道获取 query1.5。
- Debian 12 Python 3.11.2 的集成版/工具回归与独立版回归分别通过，前端固定依赖构建、审计和 ESLint 通过。此前发现的旧 Python 解压 API 与测试夹具兼容问题已修复；独立版按项目 CI 方式单独运行。

query1.5 形成已验收候选；query1.4 的既有完整 Linux CI、隔离安装/更新/回退和规则加载证据，仍按[该次发行范围](native-query14-release-2026-11-14.md)解释。本轮原生测试使用合成数据和回环监听，未改变在用实例；其结果不证明完整终端路径、Debian 13 新包验收或长期稳定性。

## 必须收尾的项目

| 优先级 | 当前依据与问题 | 完成条件 |
| --- | --- | --- |
| P1 | query1.5 已形成固定候选，原生安装、代理网页接口下载安装和回退通过；在用实例迁移与持续试用按实际部署记录确认 | 明确迁移旧版的方式，在选定试用实例确认版本、代理、配置/缓存保留及健康状态。证书拒绝已有真实 TLS 夹具覆盖，代理离线和错误密码已有原生任务覆盖 |
| P1 | 规则加载失败已有异常恢复，但多文件替换时的旧数据主要保存在内存；强制终止或断电不执行异常处理 | 先持久保存所有旧活动数据与事务阶段；启动时识别未完成事务并恢复或完成一致状态；在各替换点、加载前后注入进程终止和重启，核对规则、监听器、配置和 DNS 应答 |
| P1 | 软件安装已有备份、空间预检和中断状态核对；断电各阶段的真实恢复证据尚未完整 | 覆盖备份中、版本链接切换后、健康检查前后的中断，重新启动后能识别当前制品并恢复可用服务；旧版和新版数据均有明确处理结果，不自动重复安装 |
| P1 | 升级备份会持续增长，现有空间不足保护会拒绝安装，保留策略仍需主机管理 | 明确保留最近两代完整回退材料，保护当前与 rollback 引用；仅在新版本健康且备份完整后清理符合策略的旧材料。页面显示空间与备份占用，低空间先拒绝，清理失败可见且不损坏回退 |
| P1 | 更新器目前选择最近 20 个完整发行版中最新者，包含预发布 | 提供稳定/预览通道，正式安装默认稳定，预发布须显式选择；按发行标记过滤完整资产，防止稳定版自动推荐开发版；验证“无稳定更新”、过期检查及通道切换 |
| P1 | 已有短时、合成负载与旧候选观察；最终候选及实际客户端的连续验收需重新绑定 | 固定提交、依赖锁、组件及制品摘要；至少一台真实终端覆盖 IPv4/IPv6、UDP/TCP、A/AAAA、DNS 分流及缓存恢复。建议先 72 小时，再累计 7 天正常使用，记录异常与恢复；这是本项目建议的发布门槛，不是通用标准 |

针对最终候选，持续验收应记录 DNS 查询成功率和应用使用结果、进程重启、OOM、丢弃、查询队列、规则更新周期、缓存快照恢复、磁盘趋势及代理不可用时的行为。有问题先解释和复现，再决定修复与重新冻结，不能拿旧版本观察补足新版本的时长。

Unbound 原先的严格新旧 P99 对照未能通过旧版重复性校准，相关失败仍见[组件边界补测](component-boundary-followup-results-2026-11-10.md)。它不证明新版性能退化，也不支持“已提升/无回归”的宣传。正式版可以定位为限定范围内的功能与稳定性发布，但需明确停止宣称未验收的性能收益，并对实际资源上限和持续负载给出证据；不应仅把候选标记改为批准。

## 可随后完善

设备命名与分组、查询记录筛选、缓存层证据补充、规则命中说明和趋势图可继续迭代。逐请求缓存或上游分支缺乏证据时保持未知，不能为了展示完整而推断。当前没有因单次健康检查正常而提高缓存、线程或主机资源上限的理由。

建议顺序：本轮代理功能形成可追溯预发布 → 中断恢复和备份/通道收尾 → 冻结 RC → 真实终端连续验收 → 确认发布范围后标记正式版。每个阶段都保留失败记录和可用回退点。
