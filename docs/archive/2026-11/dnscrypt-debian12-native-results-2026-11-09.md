# DNSCrypt Debian 12 原生整包隔离验收结果

从 `cea0748` 继续，执行 [本轮方案](dnscrypt-debian12-native-plan-2026-11-09.md)。**Debian 12 实际宿主机上的原生 systemd 测试包，完成 17 个检查点、434 次被计数查询；新装、升级、缓存复用、显式回退及启动失败自动恢复通过。** 在用实例未升级，默认组件未晋升；本轮没有通过性能或持续运行验收。

## 环境、上传与匹配制品

实际环境为 Debian 12 amd64、内核 `6.1.0-43-amd64`、Python 3.11.2、systemd 252。该轮补足了此前 Debian 12 容器用户态检查的原生宿主机覆盖，与 [Debian 13 原生结果](dnscrypt-native-trial-results-2026-11-09.md) 分别记录。两套已测试内核仍不代表任意内核和接收上限都已验收。

用户授权本轮必要的源码工具修正、测试包传输和全新隔离实例验收。最终 114 个源码输入文件上传后逐项核对大小及 SHA-256；两份原生包由构建机生成并核验后传入 Debian 12。control/combined 共用当前 backend/runtime/installer，保留已校验旧归档的前端、wheels、模板和其他核心；combined 才增加普通三补丁 DNSCrypt 及来源清单。因此 control 是匹配的测试对照，不能称为历史应用代码原封不动的对照。

两包共有文件的差异只有版本常量所在文件、`build-info.json`、DNSCrypt 包装器及 `native-trial-provenance.json`；combined 另外增加 DNSCrypt 二进制、源码清单和源码锁，共 3 个文件。control 的 125 个内部文件、combined 的 128 个内部文件均再次按清单核对。两路实际运行的候选 DNSCrypt 摘要与普通 combined 制品一致。

## 隔离方式与功能结果

使用全新 `dnstrial-*` 实例、独立 data/state/config/备份和仅 loopback 的 network namespace，真实安装器与 systemd 单元共同参与。服务限定 CPU 2–3、125% 配额、768 MiB 内存上限和低调度优先级；控制程序另限 50% CPU、512 MiB 内存和总运行时间。依赖只读预检齐全，未执行 apt，没有向测试实例挂载生产数据。

首次成功完整矩阵如下；准备失败另列，没有反复重跑矩阵。

| 检查类别 | 被计数查询 | 结果 |
|---|---:|---|
| 新装非分流模式 | 2 | UDP/TCP 返回受控本地记录 |
| control 冷缓存及候选新增缓存 | 72 | Redis 全 miss，两数据库分别到预定本地上游 |
| 六个保存、升级或恢复后的缓存复用检查点 | 264 | Redis 全 hit、零 miss、零上游访问，TTL 为正 |
| control/combined 两路 DNSCrypt | 32 | UDP/TCP、直连/实际 SOCKS、HTTP/2 与 ALPN h2 均正确 |
| control/combined 经冻结 MosDNS 分流 | 64 | 冷阶段分别到本地和 DoH；热阶段后端增量为零 |
| 合计 | **434** | **17 个检查点通过** |

完整缓存检查点包含 12 个名称的 A/AAAA 与大小写变化，DB 0/1 对相同 A 名称给出不同受控地址，核对数据库隔离。每次重启后先查原记录，再核对 Redis hit/miss 和上游请求计数，避免把进程内热缓存或仅有 RDB 文件误认为旧缓存复用。五个完整复用点各 48 次，候选新增条目复用点 24 次，合计 264 次。

升级后原实例身份、自定义配置和两库标记保留；生成 TOML 继续保留 `pqdnscrypt=false`、`lb_strategy='p2'`。管理/观测接口的 native 身份、运行健康和两层 Unbound 可用性均核对。本轮没有连接网关 API，也没有新增逐设备 DNS 历史。

## 回退、故障与备份

显式回退恢复 control、原服务配置和升级前 RDB；候选新增标记从恢复后的数据库消失，候选数据另外归档。收尾在私有副本上用旧 Redis 读取两份合成回退快照：一份保留原标记及候选新增的 DB 0/1 标记，另一份只有原标记；原快照摘要均未变。没有读取或复制生产 Redis 数据作为该轮测试输入。

损坏测试包的外层归档摘要正确，内部包装器摘要错误，真实升级入口在停止/切换服务前拒绝，测试服务 PID 和当前发布不变。另一故障包的内部校验正确，仅在实际 DNSCrypt `-config` 启动时返回 77；切换后 bootstrap 失败，安装器自动恢复旧发布、配置、数据及健康服务。恢复后 48 次缓存查询全部命中 Redis、零回源。两次故障是预先安排的测试，不与准备工具失败混记。

## 工具修正、回归与资源限制

首轮在正式安装测试实例前，触发 Python 3.11.2 的 `TarFile.extractall(..., filter='data')` 不支持该参数。原输入、异常日志和失败状态保留。修正仅作用于验收脚本：先验证所有 tar 成员，拒绝路径穿越、绝对路径、反斜杠/冒号、链接、特殊文件、重复路径、多个根和文件/目录冲突，再逐个写普通文件；不恢复所有权、ACL 或 setuid/setgid。新增检查覆盖这些拒绝路径及不依赖 `extractall` 的解包行为。

验收脚本还支持指定 CPU、配额和内存，验证参数范围及实际 affinity，并将真实系统环境写入结果。首套输入 **222 项 Linux 定向回归通过**；修正后 **233 项通过**，包括 DNSCrypt 工具、维护/配置、原生包/重启和抓包/基准校验。Windows 的原生工具与 provider baseline 定向复核 **54 项通过**。26 个 API 契约样例检查通过；刷新的是源码来源清单，OpenAPI 和样例内容没有变化。

收尾程序最初要求全部 `memory.events` 为零，因控制程序的 `max=659` 中止归档。原收尾方法和失败说明保留，修正后的收尾如实记录压力，不修改原矩阵或重跑组件：

| 资源记录 | 控制程序 | 独立 DNS 服务 |
|---|---:|---:|
| cgroup 采样数 | 31 | 25 |
| 记录到的 cgroup 内存峰值 | 512 MiB | 151.32 MiB |
| 内存上限 | 512 MiB | 768 MiB |
| `memory.events` 的 max 最大值 | 659 | 0 |
| high / OOM / OOM kill | 0 / 0 / 0 | 0 / 0 / 0 |

控制程序触及其预设上限；连续同 PID 采样对记录到约 42.30 秒 CPU 限流时间。独立服务启动阶段的 CPU 统计也有配额限流，不能因后续采样对增量为零便称全程零限流。这些是约十秒一次的部分 cgroup 记录，包含安装器与子进程，不是完整 RSS 曲线。**本轮确认有限功能通过，没有签署资源余量、CPU、RSS、吞吐或尾延迟验收。**
