# 组件性能与容量边界补充验证

基线 `43373a8`。用户要求继续补齐 Unbound 性能和 Redis 容量边界，继续使用现有环境。此前失败与组合候选的未批准状态保持；本轮不升级在用实例、不推送、不扩展界面功能。

## Unbound 对照的条件修正

前轮发生器、Python 上游、抓包器、Redis 和 Unbound 共用两个 CPU，30 秒旧版 A/A 的 P99 差为 0.297 ms。该证据不足以确定干扰来源。本轮增加可复核的角色 CPU 分配，并将上游移入独立 Python 进程，避免上游和控制器共享解释器锁。实际条件不同，原失败不被覆盖。

测试机 A 使用控制器 CPU 8、上游 9、Redis 10、Unbound 11、抓包器 12、发生器 13；六个角色均记录实际 affinity，组件重启及 Redis 种子准备也沿用同一分配。独立健康与资源监视使用 CPU 0–3。测试服务拥有仅 loopback 的独立网络命名空间、CPU 8–13、600% 配额、1 GiB 内存上限、Nice 10，最长 12,000 秒。先检查可用 CPU、固定制品和来源，不更改宿主或在用服务的 affinity。

固定 Redis 7.2.17 和普通 dnsperf，只改变 Unbound 1.21.1／1.26.2。负载仍为 500 QPS、q64、串行上游。先对内存热缓存和 Redis 命中各执行三对旧版 A/A，每组 60 秒；全部 P95/P99 差须不超过 `max(较小值×5%, 0.2ms)`，任一失效立即停止性能分支。通过后，对热缓存、Redis 命中、全冷转发、50% 混合各执行五轮、每组 120 秒的新旧交错，共四十组。CPU +5%、RSS +10%、QPS -5% 和 P95/P99 原门槛不变。每组保留完整逐查询输出、内核配对、正确答案、socket／抓包丢失、种子与 Redis 路径及资源证据。任何组缺失、限流、OOM、错误或 affinity 不符均不能接受。单组最长 540 秒；不删慢样本，不追加同条件试验以求通过。

## Redis 淘汰诊断

Redis 7.2.17 的默认 `maxmemory-eviction-tenacity=10` 每轮淘汰约有 500 µs 时间预算，余下工作可交回事件循环；设为 100 则取消这项时间限制。[官方实现](https://github.com/redis/redis/blob/7.2.17/src/evict.c)及[同版配置说明](https://github.com/redis/redis/blob/7.2.17/redis.conf)表明，收紧占用需同时检查延迟。

测试机 B 仅在原历史准备副本的独立 Redis 进程上，串行比较默认 10 和候选 30。预算仍为 1,500 MiB、`allkeys-lru`；原输入字节及两个数据库的准备后内容在写入前核对。每个设置仅执行一次固定的 700 次 1 MiB 写入，使用同一固定载荷，保留每次写入时长、每十次内存与淘汰数、Redis 自报峰值、进程及 cgroup 资源。严格门槛仍为预算加 4 MiB，不把稳定后的占用当作峰值。候选需满足容量门槛、全部写入成功、至少 1,000 次淘汰、无 OOM 和服务变化；写入延迟完整报告，不能据此补签普通 DNS 性能。

两组均结束后才判断是否需要产品配置修改。若候选有明显延迟代价，保留诊断结论而不直接改默认值。容量候选通过后，使用同设置的小型受控 DNS 缓存验证保存、重载、两数据库刷新和原快照恢复；既有全量保存／重载证据仍按原设置解释。只有与实际配置相符的证据可用于后续组合包。

## 保护与收尾

每个测试进程有时间、CPU 和内存上限；原始历史输入不向测试机 A 或公网发送。独立监视记录完整在用 DNS 健康输出；连续两次失败、服务或启动标识改变、可用内存低于 1 GiB、磁盘余量低于 2 GiB时停止。两条分支在不同测试机各自串行，互不混入测量。

结束后停止新进程和监视器，核对在用制品、配置、规则、身份账户、备份、resolver、内核参数与原始快照；逐文件下载复核证据。正式升级、默认提升、性能接受与有限诊断结果分别记载。若仍未满足原门槛，如实说明剩余阻碍，不自动重试。

## 发生器 CPU 分配修正

第一对已结束，两组测量与资源条件有效，但旧版 P99 为 4.090／0.955 ms，重复性失败，立即停止，原始输入和输出保留。首组 dnsperf 在 60 秒内消耗约 58.75 CPU 秒，内核往返 P99 为 0.623 ms，用户态与内核记录明显不同；发送中仍有约 417 ms 空档，原因不能仅按 CPU 分配解释。

核对 [DNS-OARC 官方说明](https://www.dns-oarc.net/tools/dnsperf)后，确认 dnsperf 客户端使用收发线程且应提供两个 CPU。前述将发生器限制在单 CPU 的设置不足，本轮据此只修正发生器的可用 CPU 为 13、14，其他角色分配不变。使用新的冻结源码目录和输出目录，记录发生器各线程的实际允许 CPU 集合；测试服务上限改为 CPU 8–14、700% 配额，内存、负载、60 秒三对 A/A、正式矩阵与全部门槛保持。先完成新增工具检查和相同四组短测，再执行一次修正后的固定 A/A；失败仍立即停止，不用内核分位数替换原用户态验收指标。

## 容量验证的同机替代路径

若测试机 B 的脚本上传未获明确授权，容量分支可在已授权的测试机 A 上串行完成，须等性能进程全部退出。A 已有摘要相同的原始历史副本；仅在新建的私有 Redis 内存中按原算法添加 3,504 个别名，再以全量键、值、类型、数据库及绝对截止时间的两个摘要核对准备后的逻辑内容与 B 既有副本一致。不开启自动保存，不新增历史数据传输，不因磁盘余量不足生成另一份大快照。两个淘汰设置均从同一原始副本和同一内存准备过程开始，仍各执行一次固定的 700 MiB 写入及原容量门槛。

此替代任务使用 CPU 4–7、150% 配额、2,560 MiB 内存上限、Nice 10、2,400 秒总时限、仅 loopback 的私有网络；独立监视仍在 CPU 0–3。该结果只能关闭相应的容量诊断范围，不能代替未执行的压力快照保存或生产负载验收。
