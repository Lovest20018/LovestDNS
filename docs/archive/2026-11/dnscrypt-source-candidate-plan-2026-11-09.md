# DNSCrypt 普通源码候选验证

承接 `4db8dbb` 的诊断结果。本阶段在 41 的新目录和独立网络命名空间执行，不更改在用服务或默认组件锁。暂不向 PaoPaoDNS 提交 PR。Redis、Unbound 与 MosDNS 沿用现有判定，不追加原条件长测。

## 构建

`packaging/dnscrypt-source.lock.json` 固定 2.1.20 源码、Go 1.27.3 Linux amd64 工具链和两个补丁摘要。新的 `build-dnscrypt-source.py` 从校验后的归档分别构建原实现、仅接收队列补丁和双补丁；全部使用同一编译器、vendor、CGO=0 和编译参数，不加入采样入口。产物仍为未批准候选，不能冒充已经通过的默认组件。

另以同一工具链构建仅监听 loopback 的 Go TLS DoH 夹具。它实际支持 HTTP/1.1 或 HTTP/2，并在请求处理时核对协议和 ALPN；拒绝协议回退和错误直连/代理来源。只返回受控 cache.test A/AAAA 与 DNSCrypt 初始化 NS 探测，不向公网查询。

## 固定新条件

- 100 QPS、q64、唯一问题、20% AAAA、600 秒 TTL、512 条 DNSCrypt 缓存，保留逐答案、路由、TLS、内核往返和 socket 丢包检查。
- SOCKS 夹具两端均开启 TCP_NODELAY；DNSCrypt 子进程均去掉 NET_ADMIN、固定 GOMAXPROCS=2，记录实际接收队列。这些条件及 Go DoH 夹具构成新基线，不与此前 Python HTTP/1.1 夹具结果合并。
- 基于内核逐包时间检查发送节奏：100 QPS 时相邻请求最小间隔至少 5ms、最大间隔最多 50ms、每个 1ms 桶至多一包、时间顺序正确、查询计数完整。任何一项失败就保存并中止，不能用平均 QPS 掩盖补发。这个检查判定测量条件，不将失败自动归因于解析器。
- 首次新夹具短测捕获 dnsperf 补发：双补丁组最小间隔约 4.296ms，按上述门槛停止。后续新增独立 Go UDP 发生器：使用单调时钟计划，落后超过半个周期时重新安排下一周期，并保证前一次发送完成后至少半周期间隔；不追发错过的时隙。仍沿用同一逐包和有效负载门槛，记录发生器源码、制品摘要及调度计数。新发生器结果另存，不追认原短测。
- 测试阶段串行执行，不与编译并行。使用 CPU 4–7、低优先级、1 GiB 内存上限和限时临时 systemd 任务；检查现有服务 PID/重启数、可用内存和 DNS 健康。资源限流单独记录。
- 初版 CPU 配额 200% 在短测阶段出现额外限流，定速发送器同时记录一次约 263ms 空档；现有证据不能把该空档全部归因于配额。下一次复核只将配额改为 400%（仍限制在 CPU 4–7），消除该任务自身两核配额的已知干扰，其他逐组条件和门槛保持；新目录单独保存。如仍出现空档或条件无效，停止本轮性能签署，不在同条件下反复尝试。

## 有限推进

1. 校验构建输入、普通/诊断产物隔离及反例测试；提取真实 udpListener 做并发所有权和 `-benchmem` 检查，覆盖 32、63、255、512、4095 字节。此微基准包含网络与调度，只用于核对入口分配，不作为完整 DNS CPU 或吞吐提升证据。
2. 旧镜像二进制、同工具链新版原实现和双补丁候选在 HTTP/1.1、HTTP/2 的直连/实际 SOCKS 路径各做 5 秒容量与协议检查。
3. 前项有效后，对 HTTP/2 先做每组 30 秒、三轮、三种实现、两条路径的初筛，轮换执行顺序。保留所有组；初筛不能签署正式性能通过。
4. 只有测量条件有效、初筛未出现既定 CPU/RSS/延迟筛选失败，才进入相同条件下旧版/补丁版每组 120 秒、五轮交错验收。CPU +5%、峰值 RSS +10%、P95/P99 允许 `max(原版×5%, 0.2ms)` 的原门槛保持。初筛失败则先解释证据，不盲目追加相同长测。

HTTP/3、DNSCrypt 加密协议、公网解析器和完整分流链路仍须分别验证，不能由本阶段 DoH 结果代替。最终发布组合、升级回退和持续运行关卡继续保留。
