## 1. 当前判断

现有控制台、原生安装和组件验证已经构成可继续试用的基础。当前最需要补齐的是三个用户能确认的结果：**正在运行哪个制品、设备查询是否经过这个实例、保存的配置是否按预期工作。**

后续以十台以内终端的实际使用为主线。先冻结一套可识别的候选，完成单设备接入，同时整理现有 UI；逐请求观测随后独立交付。微秒级 P99 排名暂不继续扩展，已有性能失败和未验收项保留。

## 2. 后续顺序和完成条件

### A. 固定候选身份并打通单设备接入

最小交付：建立一份实例状态摘要，将应用版本、源码提交/来源、包摘要、组件版本、实际进程文件、配置摘要和探测时间对应起来。历史包可能含基础包与覆盖文件，应如实显示来源构成，不能补写为单一提交全新构建。

1. 从主机侧核对 UDP/TCP 53 和当前高位端口的监听进程、服务单元、转发/接管规则及活动配置。
2. 选定已有验收证据的包，核对备份、缓存恢复和回退点后，按现有原生升级路径安装到明确实例。
3. 为一台终端记录原 IPv4/IPv6 DNS、接口和 DHCP/静态方式，确认标准端口后接入。检查浏览器加密 DNS、VPN、多接口和 IPv6 下发造成的绕行。
4. 从该设备进行 UDP/TCP、A/AAAA 查询和常用应用试用；至少用服务端入口证据配对一次受控查询。仅“网页能打开”或“DNS 有答案”不足以证明接入本实例。
5. 演练设备 DNS 恢复；实例回退继续采用已有流程，并保留候选期间产生的数据。

完成条件：版本和进程对应；标准端口归属清楚；样本请求能归属本实例；预期记录/分流和实际应用使用结果有记录；能恢复原设置。没有 AAAA 记录与查询超时分别记录，不能把 NOERROR 无记录自动归为 IPv6 故障。

上一轮远端预检受到审批接口 HTTP 409 阻塞；这是执行通道问题，不能记作 DNS 故障。未核对端口前不覆盖已有监听者。

### B. 首页重排与配置操作整合（可与 A 的准备并行）

最小交付：复用已有接口调整首页、缓存和诊断展示；补只读运行摘要；将编辑、应用计划、任务结果及查询验证留在同一工作流。

完成条件：独立部署且未连接 Gateway 时功能完整；核心组件默认可见；两次以内操作能到相关日志/配置；保存、应用记录、样本验证三种结果不混淆；旧链接、草稿、版本冲突与认证恢复行为保持；桌面/手机、明暗主题和键盘操作通过检查。

### C. 小范围真实查询观测

先验证入口能取得的客户端地址、请求范围和分支证据，再决定存储与页面。先做可开关、有容量上限的短期采集，不直接建设长期全量日志平台。

建议初始试用边界：最多保留 24 小时、100,000 条或 64 MiB，先触及任一上限即清理最旧记录；这些是待实测的产品起点，不是已经测得的安全容量。采集采用有界队列，溢出计数可见；采集失败不能阻断 DNS 应答。

最小事件包含时间、实例/启动标识、请求关联标识、入口、来源 IP、域名、记录类型、传输、结果码、耗时及计时位置、返回地址（有数量上限）。规则标识、实际分支、上游及缓存层只有在取得该次请求的证据时填写，否则明确为未知。重试、TCP 回退、内部子查询需区分，不能重复计为客户端请求。

设备视图先按“观察到的来源 IP”聚合，支持用户备注及可追溯名称来源。经过路由器转发时可能只见路由器；DHCP 租约变化、IPv6 临时地址可能让一台设备出现多个地址。不能从 IP 数量直接计算物理设备数或在线设备数。

完成条件：可复现受控请求与事件一一对应；采样/丢弃/重启缺口可见；在既定家用负载中比较采集开关前后的正确性、响应和资源；保留和关闭功能生效；原始日志导出需显式操作。满足这些条件后，再开放“查询记录”和设备聚合视图。

### D. 原生候选发布收口

完成 A、B 后可发布范围明确的试用候选；C 可以独立后续交付，不阻塞基本控制台和真实接入。先准备新候选版本、统一来源清单、校验和、安装/升级/回退说明和实际使用记录，再按用户已有授权范围执行发布。

完成条件：文档、界面、包和实际部署指向同一候选；升级与回退在该包上验证；公开内容不含现场配置、账户、缓存和真实查询记录。既有包不覆盖，新的 UI 或组件改动使用新版本。候选验收不自动更改默认 `.11` 下载入口。

## 3. UI 信息结构

保留六个入口及深链接，不重写已具备的页面和共享壳。新增功能继续放在 `integrated/`，冻结的 `web/` 不改。

| 页面 | 默认展示 | 主要调整 |
| --- | --- | --- |
| 运行概览 | 核心状态、接入/配置摘要、两路查询指标、缓存摘要 | 待处理项置顶；核心组件紧凑常驻，辅助服务折叠；刷新与更新时间只保留一处 |
| 解析配置 | 基础/上游、分流、目标配置 | 当前值的证据和来源就近显示；保存后原位显示下一步，不要求跳到维护页找入口 |
| 缓存 | Redis 使用量/上限、DB0/1 键数、Unbound 分通道命中、持久化 | 来源分列；快照和 TTL 规则保留；危险动作不占首页主操作位置 |
| 查询与诊断 | 域名、类型、目标、协议；结果和耗时 | 提供实例入口/递归通道/转发通道预设，使用真实可用目标；先展示记录，再展开技术字段 |
| 维护与日志 | 失败任务、组件日志、维护动作、配置历史 | 作为排障和历史中心；配置页可复用同一任务组件和任务 ID |
| 设置 | 实例/版本、账户/API、外观、可选集成 | 显示应用和组件来源；Gateway 未启用时不轮询、不占首页空间 |

### 首页建议排列

1. 标题、实例、采集时间；只保留一处暂停/刷新。
2. 有问题时出现一条可操作摘要：配置待处理、入口待确认或组件异常，能直接到处理位置。
3. 三个摘要区：核心进程状态；入口与最近探测；缓存与保存状态。避免把“核心进程运行中”简写成“所有设备 DNS 正常”。
4. 六个核心组件的紧凑状态行：MosDNS、unbound-raw、unbound-forward、dnscrypt、dnscrypt-socks、Redis。点击/展开显示 PID、启动时间、退出码和日志链接。可选组件只有得到配置依据才能标“未启用”。
5. 两路 QPS/命中率集中一处；图表折叠或下移，避免组件卡、指标卡、趋势图重复同一数值。
6. 辅助服务、最近任务和详细来源放下方；异常辅助任务提升到顶部摘要。

入口卡需区分“配置期望地址”“进程监听”“从服务端探测”“从终端确认”。`0.0.0.0`/`::` 是监听范围，不能当成可复制的客户端 DNS。多网卡时显示地址来源，不能从浏览器 URL 或诊断默认目标猜局域网接入地址。

### 配置操作：保存 → 处理 → 验证

所有编辑页共用一处动作区。保持现有 API 和任务保护，根据配置类型显示正确的下一步，不为所有文件统一增加重启：

- 草稿：显示“有未保存修改”；保存成功后更新版本。失败或结果不明保留草稿，不显示已生效。
- 已保存：显示“已保存，待处理/确认”；按后端能力区分监听自动加载、生成并应用、需要重启。自动加载只在有读回/确认依据后更新状态。
- 应用计划：展示文件差异、作用范围和短暂影响。`custom_mod` 应用会重启 MosDNS，复用现有预览摘要、输入版本核对与维护任务。
- 处理中：原位显示任务 ID 与阶段；离开再回来可恢复进度，重复点击不产生第二次任务。
- 任务完成：显示“与成功任务记录一致”或“任务完成，待样本验证”。组件启动、本地健康探测与规则命中验证分别记录。
- 查询验证：保留域名、目标、时间、配置版本/启动标识和结果。只有具备逐请求证据时才能显示实际规则/分支；否则显示“取得目标记录，分流未核对”。旧配置或旧进程的验证不沿用为当前通过。
- 异常：分别呈现版本冲突、保存未确认、任务失败、回退结果、服务恢复但样本失败。提供对应动作，不把所有异常归为“请重试”。

只读用户仍可查看；写入与维护按权限显示。维护页继续保留集中操作和历史，两处复用同一实现，避免产生不同逻辑。

## 4. 数据来源决定展示方式

| 用户想知道 | 当前可用程度 | 展示规则 / 补充内容 |
| --- | --- | --- |
| 哪个组件在运行 | 已有 runtime 进程状态 | 不等同于端到端 DNS 可用；停止与未启用分开 |
| QPS、缓存命中率 | 已有两路 Unbound 计数 | 标“按通道”；不相加冒充入口总量；重启和缺口断开趋势 |
| 缓存有多少 | 已有 Redis 内存/上限、键数与持久化 | 键数不叫域名数；Redis 与 Unbound 内存不直接合并；无上限显示实际状态 |
| 应用/组件版本 | 已有 capabilities 版本、来源和组件元数据 | 包元数据与实际进程核验分开；缺失摘要不补写 |
| 接入 IP/端口、运行结构 | 现有诊断默认目标不足 | 新增只读、脱敏运行摘要，带来源、时间、启动标识和确认范围 |
| 保存是否生效 | 已有配置版本和成功任务记录 | 记录一致不等于所有规则已验证；验证结果另存 |
| 某次域名解析速度 | 已有主动查询耗时 | 标查询目标/协议/时间；不能当作所有客户端延迟 |
| 全入口 P50/P95/P99 | 尚无完整入口请求样本 | 采集完善后再展示窗口、样本数、采样与缺口；零样本显示无数据 |
| 哪台设备查了哪个域名 | 尚无真实 DNS 事件接口 | 从入口采集来源 IP 开始；Gateway 连接不代替 DNS 请求 |
| 是否分流、命中哪个缓存层 | 需要该请求的明确证据 | 配置推导标“预计”；实际字段有来源才显示，无证据为未知 |

只读运行摘要建议至少含：实例/启动标识、采集时间、字段来源、配置期望入口、观测监听、最近探测与可核对的通道关系；不返回密码、Token、完整私有配置。前端在字段缺失时回到现有组件展示。具体 API 路径和兼容策略在实施时随契约一起确定。

## 5. 视觉和交互规范

延续现有 LovestGateway 风格：橙色主操作，深蓝灰/浅灰背景，统一侧栏、页签、表格、圆角和明暗主题。优先整理共享样式变量及重复覆盖，不继续逐页堆叠 CSS。

正文以 14px 为基准，次要信息 12px；技术字段可紧凑，但核心状态和数值不缩成小字。绿色只用于已知正常的具体对象，未知/过期显示中性状态，警告与失败各有短文案和动作。状态不只靠颜色识别。

手机端改为纵向摘要与组件列表，保留触控和键盘可达的详情。长域名/IP/版本允许换行或在本地表格滚动，不造成整页横向溢出。正常页减少解释段落，来源和口径放帮助/详情，影响操作的提示就地保留。

## 6. 下一轮具体改动范围

建议下一次开发只交付 A 的身份/接入准备与 B，不把 C 的存储、长期统计和设备策略一并塞入：

1. `SuiteDashboard.tsx`、共享布局/样式：合并状态区、单一刷新、紧凑组件、辅助服务折叠。
2. `ConfigState.tsx`、`SuiteConfig.tsx` 与现有维护组件：共享保存后动作区和任务状态，保留文件类型差异及并发保护。
3. `SuiteDiagnostics.tsx`：目标预设、结果优先、样本验证的版本和来源信息。
4. 后端/runtime：新增最小只读身份/运行摘要及相应契约；未核对字段返回明确未知。
5. 有针对性的检查：状态/错误语义、权限、版本冲突、重试幂等、任务恢复、来源缺失，以及桌面/手机明暗主题；随后用实际候选和一台终端走完整流程。

默认内存和缓存预算不因小型合成试验峰值约 115 MiB 就直接下调。先收集实际缓存规模、持久化峰值与长期使用，再单独确定家用档位。网关联动和微秒排名均不作为这批 UI 与接入交付的前置条件。
