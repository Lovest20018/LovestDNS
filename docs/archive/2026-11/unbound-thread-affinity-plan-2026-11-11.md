# Unbound：发生器线程分配与重复性验证

基线为 `d6b373f`，继续[接收线程调度归因](unbound-receiver-scheduling-2026-11-11.md)。本轮先验证将发生器发送、接收线程分开固定是否改善长等待，再用固定方式校准旧版；旧版校准通过后恢复先前被停止的版本对照。未通过时不重复测量选择有利结果。

## 固定方法

只重建实验 dnsperf 2.14.0，不修改 DNS 组件。公开源归档 SHA-256 仍为 `134ba69744705bdb65ea57e25713300a6771f7cecbd5d6a74dd9472c18ac2696`。同一份新二进制同时支持共享 CPU 和线程独立 CPU；两种模式保持原有取时、收发、匹配、内存记录和释放路径。

新增可选环境参数使主线程在创建工作线程后、释放原启动条件变量前，通过 `pthread_setaffinity_np` 固定接收 CPU 13、发送 CPU 14，并用 `pthread_getaffinity_np` 回读。记录两次核对时间及统一开始时间，要求均不晚于第一条客户端发送时间；运行期间独立读取两个命名线程的 TID、亲和性及最近运行 CPU。种子阶段和正式阶段都必须有完整证据。未配置线程选项时，两个线程继续允许 CPU 13、14。

CPU 亲和性限定可运行范围，不能保证独占 CPU；相关语义见 [Linux 亲和性接口](https://man7.org/linux/man-pages/man2/sched_setaffinity.2.html)及[内核 CPU 隔离说明](https://docs.kernel.org/admin-guide/cpu-isolation.html)。来宾拓扑中 CPU 13、14 属于不同核心，仍不据此推断宿主物理核映射或 VMware 调度行为。额外记录两 CPU 的 `steal` 累计值，仅作诊断线索，零增量也不能排除宿主停顿。

继续使用旧 Unbound 1.21.1、候选 Redis 7.2.17、过期应答超时 0、内存记录、500 QPS、q64、固定种子、串行合成上游和独立角色 CPU。网络只包含私有回环接口；在用服务由独立监视单元保护，不改在用服务、全局 tracing 或 sysctl，不读取或传输历史缓存和现场查询。

## 预定顺序与停止条件

1. 核对源码、组件和构建摘要，执行 Linux 定向测试。四个错误 CPU 参数用例必须在发包前失败；随后各做一次 3 秒、100 QPS 的共享 CPU 热缓存、独立线程热缓存和独立线程 Redis 命中功能检查。所有失败均保留。
2. 相同二进制和配置做两对 60 秒热缓存诊断，顺序固定为「共享 → 独立」「独立 → 共享」，四组均记录接收线程调度。逐请求内核配对和保守状态归因沿用原工具；不以这四组作为新旧版验收，也不与旧二进制的历史绝对数值直接比较。任一诊断组无效即停止。
3. 固定独立线程方式，关闭调度追踪，对旧 Unbound 的内存热命中和真实 Redis 命中分别做三对 A/A，每组 60 秒。P95、P99 成对差值均不超过 `max(较小值 × 5%, 0.2 ms)`；输入、工具与路径一致，正确性、CPU 分配、socket／抓包丢失及资源检查全部通过。任一对失败即停止后续版本对照，保留所有组，不重测挑选。
4. 两场景 A/A 全通过后，以同一方法、Redis 和显式过期超时 0，比较旧／新 Unbound 的热缓存、Redis 命中、全冷转发及 50% 混合四场景；五对交错、每组 120 秒。沿用 CPU +5%、RSS +10%、吞吐及用户态 P95/P99 原筛选，不将内核指标替换为验收标准。
5. 版本对照完整后，在同一新版上比较过期超时 0／1800 ms，Redis 命中、全冷、50% 混合各三对交错、每组 60 秒。只测本轮合成 TTL／上游条件下的开销，不据此选择生产过期应答策略。

每组开始和运行中均核对在用服务、启动标识、监视器和磁盘余量；CPU 限流、memory max 或 OOM 增量使本组无效。任一保护或工具检查失败即停止，控制器设总体时间上限。所有单元停止并核对在用制品／配置及私有追踪实例清理后，仅导出合成证据。校准仍失败时，后续需要独立发生器或宿主侧证据，不在本轮改变配额、优先级或内核设置继续寻求通过。
