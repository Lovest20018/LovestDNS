## 1. 定位与核心决定

LovestDNS 定位为：**看清每台设备如何解析域名，并能结合 LovestGateway 判断后续连接实际如何转发的本地管理面板。**

普通用户首先关心“哪个设备访问哪个域名、返回什么地址、慢在哪里、为什么这样走、如何调整”。配置文件、组件进程和命令排在解释之后。

两种运行形态使用同一套界面：

- **独立 DNS**：解析状态、DNS 查询记录、设备视图、缓存、DNS 策略、诊断。没有网关也能完整使用 DNS 功能。
- **DNS + Gateway 联动**：在相同设备/域名页面增加网关实际连接、FakeIP、规则与出站证据；显示各自来源和采样时间。

建议首版一个 DNS 实例绑定一个网关；数据模型保留实例 ID。多个网关、跨站点统一监控不在首版范围。联动采用后端调用只读观测 API；DNS 配置仍由 DNS 管理，代理订阅/节点/网关规则仍由 Gateway 管理。

**首页默认“概览”，查询记录是核心工作页，设备是主要排障入口。** 不再把基础环境变量、TTL、多个列表文件平铺为一级导航。

## 2. 当前能力与缺口

### 2.1 LovestDNS

| 用户要看到的内容 | 当前依据 | 改版决策 |
| --- | --- | --- |
| DNS 是否运行 | runtime 组件、ready、core_healthy | 保留，但写“服务运行正常”，不能宣称所有设备上网正常 |
| 两条解析通道负载和命中率 | observer 的 Unbound 增量统计 | 可直接重排；两条通道不能相加为客户端查询总数 |
| 缓存多少 | Redis INFO 的内存、maxmemory、db0/db1 keys/TTL、淘汰计数；RDB 大小/时间 | 可直接展示原始统计；键数不是唯一域名数，RDB 不是全部缓存 |
| 某域名的回答和本次测速 | dns-test、dns-compare、响应 additional 中已有调试信息 | 可改成“结果先行”；属于主动测试，不属于某客户端真实历史 |
| 哪台设备发过哪些 DNS 请求 | 当前没有对应事件接口 | 新增入口请求/响应观测、设备归组和有界历史 |
| 每次实际 DNS 分流、缓存层和耗时 | 当前指标和主动查询不足以覆盖 | 增加可关联的逐请求证据；不能用当前配置、短耗时或 TTL 猜命中 |
| 设备级策略、清空缓存 | 当前 capabilities 显式为 false | 首版不展示可执行按钮；以后有能力再开放 |

### 2.2 LovestGateway：可以直接利用的联动基础

下面路径均相对网关 `/api/v1/`，先读取 instance/capabilities，不能根据路径存在就假定支持。

| API | 联动界面用途 | 必须保留的边界 |
| --- | --- | --- |
| instance、capabilities | 绑定身份、识别版本、模式、支持项 | 实际部署以返回能力为准；身份改变需重新核对绑定 |
| runtime、health、metrics | 网关状态、流量和连接数、可信 DNS、FakeIP 网段 | 进程/配置正常不证明出站可达；原始采样时间缺失仍为未知 |
| connections 的 recent/observed_active | 设备 IP、目标、TCP 建连、实际模式派发 | tcp_after_sniff，有容量缺口；未覆盖所有 UDP、拒绝和异常退出 |
| decisions | free/socks5/ovpn 的实际模式派发解释 | mode_dispatch 不是域名规则命中；不能标成“命中了某域名规则” |
| mihomo/connections | yaml/suburl 下展示 rule、rulePayload、chains | 是独立来源的实际快照；最终远端 IP 未验证，不能与 sniffbox 强行合并 |
| history | 已观测设备/域名的历史连接 | 持久化不代表完整；mihomo 轮询可能漏短连接，complete_history=false |
| fakeip/lookup | 从域名/IP 查看当前实际 FakeIP 映射 | 当前映射不证明历史归属；DNS TTL 不等于映射硬到期时间 |
| diagnostics/probe | 白名单站点的网关本机出站分阶段探测 | 显式触发；不证明终端透明转发成功，不支持任意 URL/指定节点/强制 IPv6 |

网关现有 API 只读权限不允许配置写入或维护。首版联动不需要新建网关管理 API，也不复制网关的订阅编辑器。

### 2.3 共同术语：拆开三件事

1. **DNS 解析路径**：本地递归、DNSCrypt、指定 DNS 转发、回退、未知。
2. **结果来源**：本次由哪个缓存层回答、实时解析、静态记录、拒绝、未知。缓存命中后，本次可能根本没请求上游。
3. **连接出口**：网关直连、SOCKS、OpenVPN、mihomo 规则/链、未观察到。

不使用一个“已分流”绿色标签囊括三者。DNSCrypt 是加密 DNS 查询，不等于网站连接走代理；返回 FakeIP 也不等于网站连接已成功。面向用户的摘要可以是：

> 这次 DNS 查询用了缓存，2 ms 返回。网关另有一条同设备、同域名的代理连接记录；与本次 DNS 查询尚未建立精确关联。

## 3. 导航和页面设计

一级导航控制在七项，按“查看、调整、维护”排序。

| 一级页面 | 首屏回答什么 | 页面内结构与主要操作 |
| --- | --- | --- |
| 概览 | 当前是否正常、哪些设备/域名需要关注 | 服务状态、近期查询指标、异常摘要、最近查询；点击指标带筛选进入记录 |
| 设备 | 谁在使用、谁遇到问题 | 名称/IP、来源、最近活动、DNS 查询量/耗时、网关连接摘要；进入设备详情 |
| 查询记录 | 这个请求怎样解析、能否找到相关连接 | 搜索与筛选、请求表、详情；“DNS 查询 / 网关连接”两个页签，各自保留来源 |
| 分流策略 | 怎样让某类域名按预期解析 | DNS 策略、规则解释、测试；网关策略摘要及“前往网关管理” |
| 缓存与性能 | 缓存占多少、帮了多少忙、哪里慢 | 命中/未命中耗时、分层缓存、容量/淘汰、持久化；TTL 在本页设置页签 |
| 诊断 | 网站打不开，问题在哪一步 | 域名诊断、设备排查、DNS 链路对照、可选网关白名单探测、报告 |
| 设置 | 接入、联动、应用与维护 | DNS 设置、网关联动、变更与历史、维护日志、API/账户、高级文件 |

### 3.1 概览：十秒内知道下一步

从上至下：

1. 标题行：实例名、观察窗口（默认最近 15 分钟）、更新时间/暂停。联动状态独立标注，网关断开不把 DNS 显示为停止。
2. 状态摘要：DNS 服务、查询观测是否完整、网关观测状态；仅有异常时显示处理建议。
3. 四项主指标：已观测活跃客户端、入口查询量、DNS 响应 P50/P95、入口可判定缓存命中率。尚无事件能力时用可用的通道统计替代，并明确统计范围，不放假数或全零。
4. “需要关注”：失败/超时、慢查询、重复回退、观测缺口、保存未应用。每项跳到具体设备/域名/变更；NXDOMAIN 单独计数，不一概宣称故障。
5. 最近查询表：时间、设备/来源 IP、域名及类型、DNS 路径、缓存、耗时、结果。网关联动用紧凑的“查看连接”入口，避免挤满首页。
6. 折叠的服务详情：组件、进程、版本与原始统计。

无查询时显示“此时间范围内未观察到查询”；未开启/不支持/断开时分别解释，不能统一成“暂无数据”。客户端数叫“已观测活跃客户端”，不叫“在线设备数”。

### 3.2 设备：先找到自己的手机、电脑和电视

表格默认列：名称与 IP、数据来源、最近活动、DNS 查询数、DNS P95、失败/超时、网关连接摘要。无 DNS 观测但存在网关连接时照常显示，DNS 列为“未观察到”。

- 名称优先使用用户备注；DNS 和网关当前都没有可直接等同于 DHCP 设备清单的接口，不能凭 IP 猜品牌、MAC 或设备名。
- 默认按 `(来源实例, 来源地址)` 识别观测对象；同一网段且管理员确认拓扑后才能建议跨来源关联。
- IPv4/IPv6、多地址、DHCP 地址复用需显式映射及有效时间；手动合并可撤销。经过路由器转发/NAT 只能看到路由器时如实标为“汇聚来源”，不展开虚构终端。
- “最近活动”只表示曾观察到 DNS 或连接，不代表当前在线。

设备详情包含“摘要 / DNS 查询 / 网关连接”，沿用列表时间范围。显示该设备的慢域名、失败记录及具体路径，点击域名可继续查。首版仅提供设备备注和筛选，不提供尚未实现的“整台设备强制代理/直连”。

### 3.3 查询记录与详情：产品主工作区

搜索支持设备备注、来源 IP、完整/后缀域名、回答 IP。IP 搜索必须区分“来源 IP / DNS 回答 IP / 网关入口目标 / 实际目标 / FakeIP”，允许用户查看匹配原因。域名规范化保留原始文本、IDNA 和结尾点语义。

筛选：时间、设备、A/AAAA 等类型、DNS 路径、缓存状态、RCODE、耗时阈值。默认 50 条分页，后端过滤；暂停列表刷新时积累“有 N 条新记录”，不移动正在阅读的行。详情有独立链接，返回后保留筛选与滚动位置。

桌面右侧详情，手机独立详情页，信息顺序：

1. **一句话结果**：哪台来源、哪个域名、本次是否得到回答、耗时。
2. **DNS 证据**：请求 → 实际规则决策 → 缓存或上游 → 回答；未知步骤显示“未取得证据”，不是补一个成功节点。
3. **回答**：A/AAAA、CNAME 链、各记录 TTL；多 IP 完整保留。FakeIP 单独标识，不作归属地/真实站点 IP 解释。
4. **网关记录**：列出候选或已精确关联的实际连接，展示来源、时间、规则/模式、链、建连状态；一对多时允许选择，不拼成虚假的单条流水。
5. **可执行下一步**：“重新诊断此域名”“解释 DNS 规则”“创建 DNS 规则”“前往网关”。创建规则先预填草稿，不立即写入。
6. 技术详情：事件 ID、boot-id、配置版本、采样覆盖、原始调试标记（折叠）。

页面记录真实历史；“重新诊断”生成新的主动测试报告，不能替换旧记录或套用旧设备身份。

### 3.4 分流策略：围绕用户意图编辑

常用入口：“按自动策略解析”“交给指定 DNS”“使用加密 DNS”“强制本地递归”。不是新增这些路径，而是将已有文件能力映射为业务名称。强制递归需解释既有回退限制；指定 DNS 未配置时先补目标。

创建流程：输入域名 → 选择精确匹配/包含子域名 → 选择解析方式 → 查看重叠规则、目标及影响 → 保存 → 按后端条件应用 → 测试。正则和关键字放高级选项。

规则列表显示域名/范围、动作、来源、有效配置状态和可解释结果。“命中次数”只有真实事件与规则 ID 绑定后才出现；静态匹配叫“按当前配置预计匹配”。规则优先级从实际核心配置生成逻辑核对，不能因拖动表格就改变不支持的跨文件优先级。

“DNS 策略”和“网关策略”保持分区。网关区展示现有观测到的规则/模式；不声称能够从观测 API 取得完整策略列表。编辑网关规则进入网关自身页面并保留可支持的筛选上下文；目前未验证支持的深链不能承诺已经可用，落地时双方补约定或提供复制域名。

### 3.5 缓存与性能：回答缓存有多少，以及是否有用

| 指标 | 明确口径 |
| --- | --- |
| Redis 当前占用/上限 | used_memory/maxmemory；maxmemory=0 显示“未设置 Redis 上限”，不能画 100% 满载 |
| 缓存条目 | 标注具体库与 Redis 键数；不换算成域名数或设备数 |
| 缓存命中率 | 现阶段分别显示两路 Unbound 的 hits/(hits+misses)；入口命中率待真实事件提供 |
| DNS 耗时 | 入口接收至返回的服务端耗时；不等于客户端 RTT 或网页加载速度 |
| P50/P95 | 同窗口真实事件分布，标注样本数；不平均两个 P95；小样本标注不足 |
| 缓存带来的效果 | 命中与未命中的实测耗时分别展示，不把两类差值宣传为严格因果收益 |
| 磁盘快照 | RDB 大小、最近保存、待保存变更、空间；明确不包含全部内存缓存和查询历史 |
| 网关 FakeIP | 独立的“域名—虚拟地址映射”，不加到 DNS 缓存总量中 |

首版提供现有快照操作，不增加一键清空缓存。按域名检查缓存、清理或预热需先补安全的服务端能力；不能靠枚举整个 Redis 键空间构造常驻列表。

### 3.6 诊断：从问题进入，而非让用户先选组件

输入域名后先显示当前配置，再让用户选择“检查 DNS”或已有允许的“检查网关出站”。DNS 和网关测试可以在同一报告分列呈现，但它们不是同一次请求的连续阶段。

报告顺序：结论 → 已验证范围 → 失败阶段 → 推荐下一步 → 技术详情。没有配置精确白名单时，网关探测按钮显示原因和设置入口；不能将用户任意输入的域名自动转成允许的 URL。

“设备打不开网站”的检查清单：是否观察到该设备 DNS 请求 → 有无回答/耗时 → 是否有网关连接证据 → 建连结果 → 必要时由用户运行网关本机探测。没有记录时先排查接入/系统缓存/浏览器加密 DNS，而不是直接提示重启。

## 4. 联动架构与证据关联

### 4.1 服务端聚合，界面统一

```text
浏览器（现有 LovestDNS 会话）
  └─ LovestDNS Web/API
       ├─ 本地 runtime 指标 / 配置 / DNS 诊断
       ├─ 新增 DNS 查询观测与有界历史
       └─ 新增 Gateway 适配器（实例绑定、只读 Token）
            └─ LovestGateway /api/v1/：状态、连接、历史、FakeIP、白名单探测
```

浏览器不持有网关 Token，不直接访问网关 API。连接设置由管理员填写固定地址和只读 Token，后端校验实例与 capabilities，返回脱敏连接状态。目标限制为管理员登记的服务地址，不做任意 URL 代理；不跟随重定向传出凭据。Token 存实例私有配置、界面仅显示是否已设置，更新/删除需明确操作。跨不可信网络使用 TLS 或受保护隧道。

绑定流程：设置 → 网关联动 → 地址/Token → 测试连接 → 展示实例名、版本、模式、可用能力 → 保存绑定。连接失败保留独立 DNS 功能；API 被关闭、凭据失效、能力不足和数据过期分别显示。

首版按需调用：概览读取 runtime/metrics；进入详情才请求该设备/域名历史或 FakeIP；不把整套网关数据每秒复制到 DNS。共用请求和短时缓存，保留原始 sampled_at。页面隐藏停止轮询；429/503 退避；重启导致 CURSOR_EXPIRED 时重建读取边界并提示缺口，不自动补成连续记录。复用网关持久历史，不另建一份无界副本。

### 4.2 证据分级：不强行画一条“端到端已验证”线

| UI 标识 | 适用条件 | 可以得出的结论 |
| --- | --- | --- |
| 实际观测 | 某条 DNS 或网关事件本身提供的字段 | 只确认该事件范围内的路径和结果 |
| 精确关联 | 有传播的关联标识，或服务端已验证的复合键 | 确认两条证据属于同一流程；仍不扩大观测范围 |
| 可能相关 | 同设备地址、域名、相近时间等匹配 | 展示候选依据和多个结果；不称已确认路径 |
| 当前映射 | fakeip/lookup 当前返回 | 只解释当前 FakeIP，不反推历史归属 |
| 预计匹配 | 当前规则解释器结果 | 只解释当前配置，不替代过去实际决策 |
| 未观察到 / 不支持 | 无记录、采集缺口、能力缺失 | 不等于直连、不等于没访问、不等于故障 |

DNS 与连接本来就不一定一一对应：预取、系统缓存、多个 IP、CNAME、重试、并行连接、直接 IP 和浏览器 DoH 都会打破一对一关系。跨来源默认仅作候选关联；避免使用同域名+时间直接合并 sniffbox 与 mihomo。

精确证据 ID 至少保留 source、instance_id、boot_id、event/connection_id。IP/域名/时间是查找条件，不单独充当全局主键。网关已有 probe 的精确 connection_id 可用于其自身报告；调用 correlation_id 并不会自动让任意终端 DNS 与连接可精确关联。

首版不为普通 DNS 包强加 trace ID。需要端到端精确关联时单独设计受控探测协议，覆盖隐私、缓存与多连接语义后再实施。

### 4.3 上游原有 DNS/FakeIP 联动的可解释性

读取 DNS 当前生效目标与网关 runtime 的可信 DNS、FakeIP 范围，展示“DNS 转发到哪里、网关真实解析依赖哪里”。配置意图和当前运行值分开。

如果 DNS 的某些规则转到 Gateway，而 Gateway 的可信 DNS 又指回 DNS，进行规则范围和回退方向检查，提示**潜在回环**。双方互相引用不必然成环，必须结合域名、路径和核心调试结果判断；不因静态地址相等就自动改配置或宣布故障。

FakeIP 查询结果与网关映射单独展示；真实连接地址可知时另列，远端代理解析时保持未知。若网关内核重启、映射被淘汰或配置版本改变，不用新状态覆盖旧证据。

## 5. 需要新增的 DNS 数据基础

先验证固定上游镜像内实际入口拓扑、可用调试字段、Unbound 构建选项及 mosdns 观测能力，再选采集方式。不能只在下游 Unbound 记录客户端地址，因为前置转发可能已经把它变成 localhost。

建议：入口请求/响应元数据是查询量、来源地址和总耗时的主记录；核心决策/缓存事件为补充证据，通过受控关联键连接。入口总耗时只能说明整体解析耗时，尚未测量的内部阶段不拆分伪造。已有 DNS additional 标记只作为所测响应的证据，原文与解释版本一并保留。

Unbound 官方提供逐回复日志和 dnstap；dnstap 依赖编译支持，而逐条文本日志会增加开销。因此将它们作为实现候选，在当前固定二进制上核对和压测后选择，不直接开启无限日志或承诺 dnstap 含有所有规则/缓存信息。参考：[Unbound 配置手册](https://unbound.docs.nlnetlabs.nl/en/latest/manpages/unbound.conf.html)。

最小事件建议字段：

| 字段组 | 内容 |
| --- | --- |
| 身份与时间 | instance_id、boot_id、event_id、received_at、completed_at、配置 revision |
| 来源与问题 | client_ip、可见时的 client_port、传输协议、qname、qtype；设备备注通过独立映射维护 |
| 回答 | rcode、answers、CNAME/TTL、timeout、response_bytes、总耗时 |
| 路径证据 | decision_source、rule_ref、resolver_path、upstream、fallback、证据等级；缺测为 null |
| 缓存证据 | hit/miss/unknown、layer、negative/stale 等可观测属性；缓存原始解析来源若未知不追溯补写 |
| 覆盖 | observation_source、sampled、dropped_count、字段缺失原因 |

入口一次请求计一次；下游重试/回退作为子事件，不重复增加入口查询量。采样后不得把保留样本数直接标为全量请求数。延迟用单调时钟计算，展示时间保留 UTC/时区；跨机器时间差不能当成阶段耗时。

建议默认保留方案：现有部署升级不自动开启详细查询历史；新安装在接入设置中明确“记录域名与来源 IP”，可选择只统计或短期记录。建议短期记录初始上限为 24 小时、10 万条、256 MiB 三者先到即淘汰，均为设计预算，需按目标主机实测后定值。停止采集与删除已存历史分开；不把网关默认 30 天历史复制为 DNS 默认值。

独立有界异步写队列，批量落盘，达到容量优先丢观测并计数，不能阻塞 DNS 转发。短时汇总独立于浏览器；浏览器关闭后数据是否继续采集由设置明确决定。导出提供脱敏选项，授权和数据保留适用于查询记录/设备备注等新接口。

新增接口为提案，不属于现有 v1 承诺：`observation/status`、`queries`、`queries/{id}`、`clients`、`analytics/summary`、`rules/explain`、`integrations/gateway/status` 及绑定管理。具体路径经契约评审确定；列表采用稳定游标、过滤上限和响应体限额。观测能力、历史读取权限、设备备注写权限和诊断权限分别声明。

共享设计语言不要求两个项目共享框架。DNS 保留 React/TypeScript，Gateway 保留自己的构建方式；先维护 token 映射、基础组件验收图和文案字典，不直接拷贝整个网关样式包。

全站状态分开：正常、部分可用、采样暂停、数据过期、请求失败、未启用、不支持、无记录。每个数据块携带来源/更新时间；网关坏了不遮住 DNS 数据，暂停时显示历史快照。

变更统一流程：**编辑草稿 → 校验 → 保存文件 → 预览/按条件应用 → 检查运行状态 → 验证目标域名**。保存、任务执行成功、规则验证成功是不同状态。复用已有 revision、草稿恢复、历史与幂等任务；认证恢复只恢复读取，不自动重放修改或探测。确认弹层只用于实际影响服务的动作，单纯查询/展开无需确认。

## 7. 实施顺序与交付门槛

不建议先花一轮只做视觉换肤。应先验证数据闭环，再落地界面主线。以下是排期建议，不是完成时间承诺。

### 阶段 A：打通证据样例与联动适配

- 在隔离实例核对 DNS 入口、实际客户端 IP、缓存命中、回退及网关 API 能力。
- 完成只读网关绑定、runtime、按域名/客户端查询历史、FakeIP 查询。
- 产出可复现的三套样例：独立 DNS、DNS+普通网关、DNS+mihomo；明确哪些字段未知。
- 门槛：一个域名能看到 DNS 主动测试和网关独立证据；无精确关联时明确分开展示。Token 不进入浏览器和日志。

### 阶段 B：第一版可用的新界面

- 统一 shell/token/状态/表格，七项导航迁移；把旧设置文件移到业务页内。
- 实现“概览 → 查询/网关连接 → 详情 → 诊断”与网关联动设置。
- 当前只有网关设备证据时显示来源，不假装有 DNS 客户端统计。缓存页先用现有可靠指标。
- 门槛：无 Gateway 时 DNS 正常可用；连接断开、401、过期、缺口、未知能力均有明确反馈；旧深链可继续打开。

### 阶段 C：完整设备与 DNS 查询观测

- 实现有界 DNS 事件、筛选、设备备注、汇总、P50/P95、分层缓存证据与规则解释。
- 在真实核心验证 NAT/IPv6、多回答、CNAME、负缓存、缓存命中、回退和采集失败。
- 门槛：选一个实际客户端请求可追到真实回答和可用的决策证据；无法观测的部分明确未知。评估开启前后吞吐、P95、CPU、内存和磁盘；观测失败不影响 DNS 服务。

### 阶段 D：任务式规则编辑与联动诊断

- 从查询创建 DNS 规则、冲突预览、应用后验证；网关管理深链双方约定。
- 增加潜在解析回环检查、主动诊断报告和证据导出；精确关联仅在支持路径开放。
- 门槛：普通用户能完成“找到问题设备 → 查看慢域名 → 理解证据 → 修改 DNS 策略 → 验证”；不要求知道文件名。

首个完整产品里程碑是阶段 C；B 只是可用过渡，不能宣称已完成逐设备 DNS 观测。长期集中监控、全网资产发现、跨产品自动改写策略、完整流量审计暂不进入首版。

## 8. 代码落点、迁移与验收

新增界面继续放 integrated/frontend，暂不改写冻结 web/。建议增加 pages 的 Devices/Queries/Cache/Policies 及 GatewayIntegration；新增共享 EntityLink、EvidenceBadge、Freshness、QueryDetail、FilterBar。通过 suiteApi 的适配层统一 DNS/Gateway 不同 envelope，保留来源信息，不把两种 JSON 生硬混成一个运行快照。

后端新增独立 gateway adapter、query observer、query store 和 aggregation；原 runtime 指标、维护执行器保持职责边界。API schema、权限、fixtures 与兼容性检查同步维护。后续再单独评估解除前端对冻结目录的构建依赖，避免与产品重构同时大改打包链。

旧路由迁移：`/status`、`/monitoring` → 概览；`/lists` → 分流策略；`/ttl` → 缓存与性能/TTL；`/env`、`/advanced`、`/config` → 设置对应页签；`/system` → 维护日志；`/deploy` → 服务信息。保留 file/component/domain 等上下文、旧书签和外部接入链接。未保存草稿跨跳转保护与现有行为一致。

验收用真实行为而非卡片数量：

1. 新用户 10 秒内看懂服务状态、数据时间与下一步；能在两次页面跳转内到设备查询详情。
2. DNS 命中缓存时不声称本次已经访问上游；DNSCrypt、FakeIP、网站代理不混用。
3. 有 DNS 无网关、有网关无 DNS、NAT 汇聚、IPv6 多地址都能显示真实范围。
4. sniffbox 模式派发和 mihomo 规则快照各自准确标识；未关联的记录不被强行合并。
5. 过期/暂停/401/游标失效/丢记录/核心重启均保留范围和时间提示；缺测不补零。
6. DNS 与网关探测分别标明起点；网关 HEAD 成功不显示“这台手机访问正常”。
7. 配置保存、应用、验证分离；重试不重复执行维护；编辑/回登录不丢草稿。
8. 320、390、768、1440px，明暗/系统主题，键盘/触屏检查通过；详情可分享且不带 Token。
9. 采集队列、存储清理和网关故障注入不阻断 DNS；性能预算由阶段 A 基线确定并验收。
