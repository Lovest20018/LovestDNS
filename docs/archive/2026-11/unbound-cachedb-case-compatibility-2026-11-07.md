# Unbound 升级的 Redis 缓存大小写兼容边界

日期：2026-11-07。状态：已在 41 的独立网络与数据目录中复现；运行实例、原始 RDB 和默认运行配置未改动。

## 结论与升级限制

Unbound 1.21.1 按原域名大小写计算 Redis cachedb 键；1.26.2 改为先转小写。旧版以混合大小写写入的条目，新版即使收到相同大小写的问题也无法直接命中，会访问上游并写入新的小写键。旧数据仍保留，RDB 可加载、DNS 答案正确，但不能宣称全部历史缓存都可直接复用。

只升级 Redis 7.2.5 → 7.2.17 不改变这个行为。根据既有方案“不能复用历史缓存时先阻止默认升级并定位”的要求，**本轮暂不批准 Unbound 1.26.2 进入可部署的默认组合**。Redis、DNSCrypt 继续独立候选验证；本记录未签署其完整部署验收。已生成的组合包仍为未部署的实验候选。

受影响比例取决于旧条目的大小写；当前实际快照样本不足以估计日常占比。小写旧条目的命中正常，不应将此边界描述为全部缓存失效或 RDB 损坏。

后续对测试机实际落盘快照的审计发现只有 6 条可确认的 DNS 缓存，全部已过期且为小写，未发现受影响条目。这说明当前样本不足以评估日常使用中的影响比例，详见下文；不撤销受控实验已确认的兼容边界。

2026-11-09 另对具有真实流量的正式机副本审计：约 191 万条可解析 DNS cachedb 中，5359 条旧键受大小写规则变化影响，约占可核对条目的 0.28%，但该已完成快照的 DNS 条目均已超过报文 TTL。另发现同名大小写旧变体可能保存不同历史地址，完整 DNS 回放尚未完成。此结果补充了真实缓存的规模和影响范围，不能据此签署新鲜缓存复用或默认升级通过；见 [正式机补充验证](component-maintenance-validation-results-2026-11-09.md)。

## 官方代码依据

[`1.21.1 cachedb.c`](https://github.com/NLnetLabs/unbound/blob/release-1.21.1/cachedb/cachedb.c) 的 `calc_hash()` 将问题名、类型、类和种子拼接后计算 SHA-256。[`1.26.2 cachedb.c`](https://github.com/NLnetLabs/unbound/blob/release-1.26.2/cachedb/cachedb.c) 在复制问题名后新增 `query_dname_tolower()`，其余键计算步骤相同。

[`1.26.2 Changelog`](https://github.com/NLnetLabs/unbound/blob/release-1.26.2/doc/Changelog) 的 2025-02-24 条目说明此修复让 cachedb 键忽略大小写，改善跨大小写查询的复用。它是上游行为修正；本轮没有撤销修复、增加旧键回退或改写缓存。下面的实际二进制实验另行确认其兼容影响，未仅依赖版本号推断。

## 复现方法

1. 原版 Redis 与实际旧 Unbound 向两个数据库分别写入四种问题名，各包含 A、AAAA；DB 0/1 的 A 应答不同。TTL 为 600 秒，保持相同 cachedb 种子。
2. 执行 SAVE 后保存原始 RDB，记录摘要。每种组合从独立副本开始，Unbound 内存为空；不复用前一个组合写入的数据。
3. 测试原版、仅 Redis、仅 Unbound、组合升级及恢复原版。每次查询核对 DNS 答案、Redis 命中/未命中计数差和受控上游请求量。
4. 共 80 次查询全部返回正确答案。结束后原始 RDB 摘要不变。

每格均在 DB 0/1、A/AAAA 四个查询中一致：

| 旧记录的问题名 → 新查询 | 原版 / 仅升级 Redis / 恢复原版 | 仅升级 Unbound / 组合升级 |
|---|---|---|
| 小写 → 相同小写 | 命中旧条目 | 命中旧条目 |
| 小写 → 混合大小写 | 重新访问上游 | 命中旧条目 |
| 混合大小写 → 相同混合大小写 | 命中旧条目 | 重新访问上游 |
| 混合大小写 → 小写 | 重新访问上游 | 重新访问上游 |

“命中”均为 Redis 恰好增加一次命中、零未命中及零上游请求；“重新访问”均为一次 Redis 未命中及一次上游请求。真实旧二进制与新版的差异与上述官方代码一致。

## 如何解释已有兼容结果

此前 RDB 加载、逐键读取摘要、DB 隔离、小写条目真实命中、新写入后重启与回退的证据仍成立。此次暴露的是**查找键语义变化**，所以 Redis 文件格式及内容可读不能替代全部历史 DNS 缓存可复用的验证。性能工具的 Redis 命中数据集也仅使用小写问题名，不覆盖此边界。

后续处理需同时考虑旧键复用、刷新后新键复用、额外条目和内存影响，以及升级后回退。下述试验补齐了自然重建和回退证据；它不改变旧混合大小写键无法直接复用的事实。当前保留旧条目和升级前快照，不静默清空、不自动迁移，也不将撤销大小写修复作为性能优化。继续固定旧 Unbound 是现阶段可恢复的处理方式。

## 自然重建、额外空间与回退验证

新增 `scripts/test-cachedb-upgrade-rewarm.py`，仅使用新建的临时数据目录、受控 loopback 上游及 RDB 副本。2026-11-07 在 41 的独立网络命名空间运行，两个数据库各 200 个问题名、A/AAAA 两种类型，TTL 600 秒；一半名字人为设置为混合大小写。每阶段核对答案、非零 TTL、Redis 命中和未命中、上游次数、数据库条目数及淘汰计数，共 **4800 次查询全部正确**。

| 阶段 | 查询数 | Redis 命中 / 未命中 | DB 0 / 1 上游请求 | DB 0 / 1 键数 |
|---|---:|---:|---:|---:|
| 原版填充并保存原快照 | 800 | 0 / 800 | 400 / 400 | 400 / 400 |
| 新版首次读取原快照 | 800 | 400 / 400 | 200 / 200 | 600 / 600 |
| 仅重启新版 Unbound | 800 | 800 / 0 | 0 / 0 | 600 / 600 |
| 新版 Redis / Unbound 重载新快照 | 800 | 800 / 0 | 0 / 0 | 600 / 600 |
| 原版恢复原快照 | 800 | 800 / 0 | 0 / 0 | 400 / 400 |
| 原版额外读取新版快照 | 800 | 800 / 0 | 0 / 0 | 600 / 600 |

本次关闭 `redis-expire-records`，所有阶段淘汰数为零。自然重建后旧混合大小写键仍保留，所以这组人工 50% 大小写样本的总键数从 800 增至 1200。它不能用于推算真实缓存的增长率；在缓存容量受限、发生淘汰或旧键已不在时，也不能保证回退原版仍能命中所有旧记录。正式回退依据仍是升级前原快照。

Redis `INFO memory` 的样本值如下；包含分配器及运行开销，跨版本差异也在其中，不能把键数增幅直接当作内存增幅。

| 阶段 | used_memory（字节） | used_memory_dataset（字节） |
|---|---:|---:|
| 原版填充后 | 1227140 | 309863 |
| 新版首次重建后 | 1466042 | 412091 |
| 新版重载新快照后 | 1441393 | 387395 |
| 原版恢复原快照后 | 1202537 | 285183 |
| 原版读取新版快照后 | 1290113 | 348563 |

这验证了新鲜受控缓存可以按需重建并持久化，不是容量压力、过期缓存、生产 DNSSEC 数据或性能验收。顺序查询用时包含测试客户端开销，不作版本速度比较。仍未取得足够大的实际新鲜缓存样本，Unbound 的默认升级限制继续保留。

复现命令（先在独立网络命名空间启用 loopback，`--work` 必须不存在）：

```sh
python3 scripts/test-cachedb-upgrade-rewarm.py \
  --baseline-home /path/to/core-baseline --bundle /path/to/components-bundle \
  --work /path/to/new-rewarm-check
```

原快照摘要在试验前后相同。结果 SHA-256：`b3684d66dcdc06bd31feba8cd0b9b7302347a5c964262726947c0c3a22263d31`；原快照 `79a799b1f861221ee6f0d7824f23bceb25b03be83ea650b9a3bcf5e900d22f0d`，重建后快照 `e5b6df13c16421ea8d76c5ea81de4a6397931e3e04422ff66cf24c5ba02a37d3`。原始结果保存在私有验收目录。
