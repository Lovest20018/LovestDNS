# DNS mixed90 丢包原因定位

日期：2026-11-07。代码基于 `9cc58db`，运行实例未升级。

## 当前结论

已经复现一条完整的失败链路：**测试端停顿 → dnsperf 恢复后集中补发 → Unbound 的 UDP 接收队列溢出 → 查询超时**。原版本和组合候选都能出现同类失败，因此已有超时记录不足以证明新版组件性能回退。

另有追踪显示，对 Unbound 发出唤醒请求至其重新运行发生明显延迟，并伴随多个客机 CPU 的独立心跳延后。客机中已确认存在调度或执行停顿；其在客机内核或虚拟化层的具体来源尚未确定。

原先 77、81、85 个超时的记录没有完整的故障瞬间追踪，不能逐次追认都属于同一原因，也不能删除失败记录后给候选补签通过。完整性能验收仍未完成。

## 为什么此前判为未通过

性能筛选要求查询无超时、答案正确。此前 mixed90 出现超时，触发停止条件；“未通过”表示这组测量不满足验收要求，并不等于已经找到了组件回归。

定向复现中的 81 个超时与服务端 UDP socket 的 81 次丢包一一对应；另一个 20ms 实验组也有 77 次超时及 77 次服务端丢包。客户端 socket 和答案抓包均未丢包，收到的 DNS 答案正确。问题首先落在服务端接收队列，而不是答案生成错误。

## 自然停顿的追踪证据

在原有 1000 QPS、256 个最大未完成请求的条件下，对“仅替换 Redis”和“组合候选 + 20ms 实验参数”各执行三轮 120 秒诊断，记录系统调用、调度事件、包的内核到达时间和 CPU 心跳。六轮共完成 **719999** 条查询，无丢包；这不是完整性能验收，追踪本身也增加开销。

其中两段队列堆积取得以下证据：

- 一条 Unbound `sendto` 调用跨越约 **188.35ms**，期间没有记录到该进程切出 CPU。请求到达中断约 **188.84ms**，恢复后相邻三个 1ms 桶共到达 **191** 条查询，服务端采样收包队列升至 **183360 字节**。四个测试 CPU 的相邻心跳间隔同时达到约 **212–215ms**，正常采样间隔为 50ms。
- 另一段中，Unbound 从唤醒请求到重新运行相隔约 **91.85ms**，队列采样达到 **82560 字节**。该窗口中没有发现 Redis 读写调用长时间阻塞的证据。这里记录的是唤醒请求到运行的间隔，不能把它全部算成已经可运行但未获调度的时间。

另在 `system.slice` 启动独立心跳，绑定客机 CPU 0、3、11、15，与 SSH 测试会话及测试 CPU 4–7 分开。只检查完整负载窗口中段、排除追踪启停附近的事件，仍发现不同 CPU、不同会话在同一窗口延后：一组相邻心跳间隔约 **203–240ms**，其中包含正常的 50ms 周期。这说明停顿范围超出单个 DNS 进程。

测试会话及其上级 cgroup 的 `cpu.max` 均未设置配额，`nr_throttled` 和 `throttled_usec` 均为零；这排除了已检查客机 cgroup 的 CPU 配额限流，不能排除宿主机侧资源限制。

## 只暂停压测器的对照实验

在独立网络命名空间内，保持 DNS、Redis 和受控上游正常运行，仅在开始发送约 2.2 秒后对本轮 dnsperf 进程暂停 **400ms**，然后恢复。每组 15 秒、目标 1000 QPS，输入及答案校验方法一致。只操作本轮创建的负载进程，不暂停运行实例。

| 组件 | 最大未完成请求 | 暂停压测器 | 发送 / 完成 | 超时 / 服务端 UDP 丢包 |
|---|---:|---|---:|---:|
| 原版本 | 256 | 400ms | 14981 / 14910 | **71 / 71** |
| 组合候选默认参数 | 256 | 400ms | 14979 / 14905 | **74 / 74** |
| 原版本 | 64 | 400ms | 14961 / 14961 | **0 / 0** |
| 组合候选默认参数 | 64 | 400ms | 14968 / 14968 | **0 / 0** |
| 原版本 | 256 | 无 | 15000 / 15000 | **0 / 0** |

所有收到的答案均正确，客户端 socket 与抓包均无丢包。两个 256 组的请求到达最大间隔约 401ms，最密集的 1ms 桶分别有 127、120 条查询。

这证明只让测试端停顿，就足以在旧版及新版中制造同类丢包。64 组的实际有效 QPS 约为 997.38、997.85，没有靠大幅降低平均负载避免失败；但它们仅是短时诊断，不能代替正式性能比较。

dnsperf 的限速维护发送时间进度和一秒窗口。当恢复时仍落后于当前窗口的发送进度，会连续发送来追赶；跨过窗口时又可能重置进度。因此相同的平均 QPS 不保证相同的瞬时请求波形，并非每次停顿都会产生同样突发。依据：[DNS-OARC dnsperf v2.14.0 发送实现](https://github.com/DNS-OARC/dnsperf/blob/v2.14.0/src/dnsperf.c)。

测试机 `net.core.rmem_default` 为 **212992 字节**，实验未修改全局内核参数。实验未显式设置 Unbound `so-rcvbuf`，本次检查的运行主配置中 `so-rcvbuf: 4m` 也保持注释状态。短时间集中补发使有限收包队列更容易溢出。

## 已确认与尚未确认的边界

已确认的是测试端补发可独立触发同类丢包，以及客机存在跨进程、跨 CPU 的停顿。现有证据支持先校准负载和排查环境，尚不能将失败直接归给 Redis 或 Unbound 的升级。

VMware Tools 的 Guest API 本可提供 VM 可运行但未获宿主机调度的时间等统计，但本机查询返回 `VMware Guest API is not enabled on the host`，原始统计入口也返回不可用。无法仅凭这些客机记录继续区分宿主机调度、VM 暂停或其他虚拟化层原因。接口语义见 [VMware 官方 GuestLib 头文件](https://github.com/vmware/open-vm-tools/blob/master/open-vm-tools/lib/include/vmGuestLib.h)。

## 后续处理

另已完成 [Unbound / Redis 官方源码核查及同步阻塞实验](dns-cachedb-source-review-2026-11-07.md)：只暂停独立 Redis 即可拖慢同线程的热缓存查询，旧版与新版均能复现。这确认了另一条可影响尾延迟的路径，但与此前单次 `sendto` 中的自然停顿不同，不能据此追认原始超时根因。

1. 保留原始失败、自然追踪和故障注入结果，分别标注，不用短时诊断补签性能通过。
2. 固定新旧版本相同的负载参数，校准最大未完成请求数并记录实际发送波形；继续检查发送量、有效 QPS、答案、两端 socket 丢包及全部重复轮次。普通固定速率比较与突发承受能力分开验证。
3. 结合宿主机同一时段的调度及暂停记录，继续确定客机公共停顿的来源。
4. 不因本次诊断修改运行实例的缓存、Redis 超时或内核缓冲参数。20ms 仍是实验值；性能关卡通过前不升级 41 当前实例。
