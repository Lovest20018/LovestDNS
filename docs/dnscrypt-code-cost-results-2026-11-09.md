# DNSCrypt 源码成本拆分结果

本阶段从 `e9db8ae` 继续，完成了可复现的源码成本工具和一个独立缓存补丁。**确认新版缓存分片把 `[32]byte` 摘要格式化成字符串是可消除的开销；补丁使本次 A/AAAA 缓存命中微基准 CPU 成本下降约 75%。这不是整个 DNS 服务加速 75%，也没有批准默认组件升级。**

未继续重跑上一阶段因逐包发送空档中止的长测，未操作 旧版正式机，未提交 PR。

## 方法与边界

- 固定源码归档、Go 工具链和补丁摘要，见 `packaging/dnscrypt-cost.lock.json`。从上游原样提取缓存插件、缓存键、TTL 和克隆辅助函数，使用对应版本的实际 vendor；最小类型只适配被测代码的依赖。所有选定文件与产物摘要有清单。
- 第一阶段为旧 2.1.5 / Go 1.22.5、旧 2.1.5 / Go 1.27.3、新 2.1.20 / Go 1.27.3，三轮轮换顺序。第二阶段将新版原实现与分片补丁交错三轮。共 180 个计量记录组，每组固定 100000 次，合计 1800 万次计量操作，不含基准框架预热。
- 查询解码、应答编解码、缓存键、深拷贝、缓存命中、同键替换分别测 A/AAAA。CPU 使用 Linux `getrusage(RUSAGE_SELF)` 的用户态加内核态时间，独立于 Go 的 wall ns/op；同时记录 B/op、allocs/op。下表是三轮中位数，没有删去慢组。
- 41 上 CPU 4–7、GOMAXPROCS=2、400% 配额、1 GiB 内存上限、低优先级、限时任务；编译与计量串行，计量进程使用独立网络命名空间且不发网络查询。宿主暂停不直接记入进程 CPU，但频率、迁移、GC、同机负载仍会影响结果。
- named-file 微基准不链接完整传输、QUIC、监控与响应校验流水线，不是可部署 DNSCrypt，也不能代替完整服务 CPU、RSS、P95/P99 或吞吐验收。第一阶段不是对旧部署 musl/PIE 制品的重构建。

## 编译器与源码差异

以下单位为 **CPU ns/op，A / AAAA**，不同路径的计量相互独立，不能简单相加成为一次完整请求：

| 路径 | 旧源码 / 旧 Go | 旧源码 / 新 Go | 新源码 / 新 Go |
|---|---:|---:|---:|
| 查询解码 | 1132 / 1005 | 1081 / 967 | 1147 / 1103 |
| 应答解码再编码 | 2812 / 2851 | 2650 / 2736 | 2134 / 2094 |
| 缓存键 | 1009 / 1033 | 1036 / 1054 | 1067 / 1174 |
| 深拷贝 | 903 / 944 | 841 / 816 | 910 / 856 |
| 缓存命中 | 2658 / 2678 | 2569 / 2538 | 9283 / 8993 |
| 同键替换 | 2231 / 2170 | 2133 / 2135 | 9538 / 9451 |

旧源码换新 Go 没有出现新版缓存路径的数倍成本增加，不能将这个局部热点归因于编译器。这个结论不排除新 Go 在完整传输或调度路径上的差异。

新版也并非所有方面都退步：应答编解码从旧版 A 的 268 B / 8 次、AAAA 的 280 B / 8 次，降到两者均 176 B / 6 次；查询解码则从 192 B / 3 次增加到 296 B / 4 次。深拷贝的必要性和报文库变化应分别评估，不能用一次整体观察概括。

## 分片哈希补丁

2.1.20 vendor 的 `go-sieve-cache/pkg/sievecache/sharded.go` 对 string、int 等类型有专用路径，但 DNSCrypt 使用的精确类型 `[32]byte` 落入 `ToString` → `fmt.Sprintf("%v", v)`。每次读取或写入在选择分片时都进行格式化。

`dnscrypt-2.1.20-cache-shard-digest.patch` 在该回退路径之前，对精确的 `[32]byte` 使用现有随机种子的 maphash 直接哈希完整字节。其他类型、完整缓存键相等判断、SHA-512/256 摘要、CD/DNSSEC 隔离、锁、淘汰算法与响应深拷贝保持原实现。补丁不引入 unsafe。

同一 Go、同一输入的第二阶段结果：

| 路径 | 原实现 CPU µs/op | 补丁 CPU µs/op | CPU 减少 | B/op 原 → 补丁 | 分配次数原 → 补丁 |
|---|---:|---:|---:|---:|---:|
| A 命中 | 8.929 | 2.281 | 74.5% | 432 → 272 | 5 → 3 |
| AAAA 命中 | 9.078 | 2.273 | 75.0% | 432 → 272 | 5 → 3 |
| A 同键替换 | 9.690 | 2.521 | 74.0% | 496 → 336 | 7 → 5 |
| AAAA 同键替换 | 9.248 | 2.534 | 72.6% | 496 → 336 | 7 → 5 |

分片选择本身从每次 2 次分配降到 0；完整插件路径每次减少 160 B、2 次分配。第二阶段六个计量进程逐组记录的 CPU 配额限流增量均为 0。未修改的路径仍有测量波动，例如 AAAA 深拷贝中位数从 955 降到 829 ns/op；这不是该补丁改变了深拷贝。因此这里只把源码直接影响的分片路径和稳定的分配差异作为归因证据。

每次读写节省约 6.6–7.2 µs，不能用来解释或抵消上一阶段未完成、测量条件无效的完整服务 CPU 差异。缓存 miss、不同容量/占用率、多客户端争用、TTL 过期及真实分流链路的性能仍未在此阶段签署。

分片映射会变化，但该缓存只在进程内存在，随新进程初始化；不能给已有缓存对象热替换哈希方法。本补丁不读写 Redis/Unbound 历史缓存。

## 正确性、普通构建与现场

- 四个诊断组合各 4 项契约检查通过：A/AAAA 编解码与克隆所有权、TTL、大小写/类型/类/DNSSEC 缓存键、实际插件命中和进程 CPU 与 sleep 的区别。旧版没有按 CD 标志隔离，新版有隔离；这是记录基线差异，没有回退新版行为。
- vendor 定向 4 项测试带 race 通过：完整摘要与随机种子哈希、零分配、其他键类型、并发键值/容量/删除/清空。原版两个反例按预期失败，明确观察到格式化路径每次 2 次分配，避免仅证明补丁测试可以运行。
- Windows Python 定向回归 21 项通过，覆盖损坏源码、工具链、补丁的提前拒绝，以及已有普通候选身份与协议/节奏检查。
- 显式 `cache` 普通制品构建成功，无 profiling 代码。HTTP/2 直连与实际 SOCKS 两种路径共 16 次查询、8 次上游访问、8 次缓存命中；实际 ALPN/HTTP、路由、A/AAAA、大小写、答案和非零 TTL 检查通过。该短功能检查不代替 HTTP/1.1、其他协议或性能验收。
- 两阶段 35 次运行中 DNS 健康探测均成功，最低可用内存约 5980 MiB。第一阶段编译时观察到任务配额限流，缺少完整逐组资源计数，因此不宣称该阶段逐组零限流。第二阶段各步骤保留了前后计数，OOM/oom_kill 均为 0。
- 两个临时任务均成功结束，无候选进程残留。在用服务仍为 PID 1047426、NRestarts=0，公开域名解析 NOERROR；当前链接、在用 DNSCrypt 包装器、真实二进制及私有库摘要与上一阶段清单一致。

## 使用与后续关卡

诊断构建使用新的工作目录，例如在 Linux 的独立网络命名空间执行：

```sh
unshare --net python3 scripts/benchmark-dnscrypt-cost.py \
  --source-archive /inputs/dnscrypt-2.1.20.tar.gz \
  --toolchain-archive /inputs/go1.27.3.linux-amd64.tar.gz \
  --work /tmp/new-shard-cost --case new-shard-fast
GOMAXPROCS=2 unshare --net /tmp/new-shard-cost/cost.test \
  -test.run='^$' -test.bench='^BenchmarkCost$' \
  -test.benchmem -test.benchtime=100000x -test.count=1
```

普通构建器可显式选择 `--variants cache`；默认仍构建原来的 upstream/buffer/udp 三组合。源码锁增加候选后摘要已变化，旧普通候选清单不能直接用于新锁的比较，应重新构建并核对二进制身份。`packaging/components.lock.json`、默认组件包入口与运行配置没有修改。

下一步将分片补丁与已有 UDP 补丁保持独立比较，先补缓存 miss、容量/争用及 TTL 场景，再在测量条件可重复的环境比较普通制品。完整服务性能、组合补丁、UDP 权限/内核配置、打包升级回退和持续运行仍是后续关卡。Redis 性能证据不足、Unbound 缓存兼容限制与 MosDNS 冻结结论保持；本阶段没有把这些关卡标为通过。

后续的 miss、容量、并发与 TTL 扩展证据见 [缓存矩阵结果](dnscrypt-cache-matrix-results-2026-11-09.md)，独立缓存候选的范围保持不变。
