## 已取得的运行证据

- 原生组件包构建成功；集成容器能用候选组件启动。MosDNS 摘要核对通过。
- 旧 Redis 与旧 Unbound 写入测试数据并保存 RDB 后，原版本、仅更新 Redis、仅更新 Unbound、组合更新和恢复原版本五组，均能真实命中旧记录。判定同时检查 DNS 答案、受控上游请求计数与 Redis `keyspace_hits`。
- DB 0/1 用相同查询名和键种子、不同答案验证隔离；历史条目 TTL 递减，短 TTL 条目触发上游刷新。
- 候选写入后执行 SAVE，完整重启 Redis 和 Unbound，再次查询不访问上游，确认新条目从 RDB 复用；原始快照摘要保持不变。
- 受控 DoH 的 TLS 校验、直连和 SOCKS5 路径、A/AAAA、缓存命中与否定答案在新旧 DNSCrypt 上通过。该证据不覆盖所有公网 DNSCrypt/DoH 服务或实际代理线路。
- 容器运行回归通过：分流开关、两层 Unbound、UDP/TCP、配置历史与恢复、实际规则应用、启动失败后的运行配置回退、Redis 快照、采集器断开与恢复，以及容器重建后的配置/RDB 保留。
- 后端与脚本共 252 项、独立版后端 46 项通过；前端类型、构建、lint 和 37 项测试通过。新增运行策略另有实际 DNSCrypt 直连/SOCKS、CNAME 和冻结 MosDNS 入口工具检查。
- Debian 13 原生载荷校验、组件启动命令与离线 Python 依赖安装通过；Debian 12 隔离环境的组件启动命令和完整缓存兼容矩阵连续三次通过。Debian 12 另用测试辅助 pip 验证包内 Python 3.11 wheel 离线安装及运行模块导入；未据此宣称完整 systemd 安装已验证。
- 运行实例已落盘 RDB 的独立副本在新旧 Redis 中逐键读取摘要一致；原件未改动。现有两份 Unbound 运行配置均通过候选 `unbound-checkconf`。

所有缓存与故障注入使用独立进程、临时 socket 和受控上游，不使用运行实例的数据文件。公网与实际线路测试不能替代受控性能比较。

## 性能实验状态

短时工具检查已跑通四种组件组合及热缓存、90%/50%/10% 目标命中场景，未丢查询。其持续时间为 3 秒，仅证明工具流程可用，不能作为性能验收或提速结论。

单独的 Redis 停顿实验中，原版本、新版默认参数、新版命令超时 20ms 的五次查询中位数分别约为 **208.38ms、208.08ms、48.01ms**，恢复 Redis 后都能继续解析。这是本地故障注入下的恢复收益，不表示正常 DNS 平均速度提升。20ms 尚未进入默认运行参数。

进一步的 [官方源码核查和同线程热查询实验](dns-cachedb-source-review-2026-11-07.md) 证实同步 cachedb 访问可拖慢内存热查询；新版重连节流不覆盖所有命令停滞情形。这是已确认的阻塞路径，尚不能解释全部原始 mixed90 失败，也没有据此修改默认超时或候选组件源码。

长轮次对照使用 dnsperf 2.14.0 的逐请求数据，按 120 秒、5 次重复、交错顺序执行，并保存输入摘要、原始记录、CPU/RSS、Redis 内存/持久化信息和上游请求量。`scripts/report-dns-benchmark.py` 拒绝把短时或缺少轮次的结果标为通过。

最初的长轮次范围是 Unbound/Redis 后端热缓存及 90% 目标命中混合场景，固定提供 1000 QPS。固定速率结果只能证明该负载的表现，不能宣称测得最大吞吐。后续补测范围和结果见当前验收概览及各独立章节；加密链路性能及面板/网关观测开销仍待验证。

第一组未完成的对照在最终协议兼容修正收口时停止，原始数据保留，未计入验收。正式矩阵从最终打包完成后重新开始。

其后一次正式尝试在首轮热缓存的 `combined-20ms` 组出现 85 个超时查询，矩阵停止。逐请求记录在超时前存在一次约 0.66 秒的集中延迟突增；该证据不能确定故障原因，也不能直接归因于 Redis 命令超时参数。原始数据保留，不计为通过。

正式矩阵的启动会等待共存编译任务结束及 60 秒冷却；测量中检测到新编译任务时，将整次尝试标为不可比较并保留数据后重跑。该编排不修改运行实例，不自动升级服务。若筛选未通过，停在结果复核阶段。

## Review 修正与复测

Review 发现并复现了三项验收误判，本轮已修正：

- 汇总核对每轮实际运行时间、发送量、有效 QPS、计数/延迟样本和资源样本，不再只相信声明的时长与相对性能。缺少实际证据的旧结果不能补签通过；不足负载的轮次不能被其他轮次的中位数掩盖。
- 独立进程旁路抓取本轮 loopback UDP 包，逐条核对输入问题和 A/AAAA 答案。空答案、错误地址、抓包丢包或数量不一致均使验收失败，不向 DNS 转发路径增加代理或探针查询。抓包进程的资源使用单列。压测需要 Linux `CAP_NET_RAW`。
- SOCKS 用例核对本轮新增连接和 DoH 实际请求路径；测试代理使用独立 loopback 源地址，服务端拒绝 SOCKS 场景中的直连，不能复用前一组计数。

复测证据：

- Linux 后端与脚本测试 **274 项通过**，其中定向测试 33 项。Windows 本地不依赖网络的定向测试 31 项通过；本机网络夹具此前超时，真实网络路径以 Linux 结果为依据。
- 新旧 DNSCrypt 的直连/SOCKS 四组均通过；每组分别记录 7 次 DoH 请求，两个 SOCKS 组各建立 1 条新代理连接，未出现不符路径。
- 负向验证：20 条冷查询全部返回 NOERROR 空答案时，逐条检出 20 个错误并拒绝通过；移除候选的代理配置后，测试拒绝直连并失败。
- 独立抓包进程下，12000 条热缓存/90% 命中短测应答全部正确，抓包与客户端 socket 无丢包。此为 3 秒工具检查，不计为性能验收。
- 全冷 1000 QPS 短测实际仅约 716–793 QPS，汇总明确判为负载不足；不据此比较组件性能或宣称最大吞吐。全冷测量还需校准受控上游与负载发生器的容量。

原有 85 个超时查询的根因仍未确定。新工具增加每轮客户端 UDP socket 丢包计数与收包队列采样。修复后的正式矩阵完成热缓存部分后，在 mixed90 场景停止；具体证据如下，未取得最终性能通过结论。

## 正式复测与原生整包验收

Review 后第一次矩阵尝试检测到共存 Rust 编译任务，整次结果被排除。第二次在没有检测到编译干扰的情况下完成热缓存全部 25 组（5 种组合 × 每组 120 秒 × 5 轮），共校验 **2,999,998** 条应答，未超时、未发现错误答案或抓包丢包。此处的“热缓存”指直接访问 Unbound 进程内缓存，不包含 MosDNS 入口或 Redis 命中延迟。

热缓存中位数如下；CPU 单位是 DNS 进程每百万个完成查询使用的 CPU 秒，RSS 为各进程采样峰值之和的中位数：

| 组合 | 有效 QPS | P95 / P99（ms） | CPU 秒 / 百万查询 | 峰值 RSS（MiB） |
|---|---:|---:|---:|---:|
| 原版本 | 1000.00 | 0.563 / 0.991 | 176.25 | 18.57 |
| 仅 Redis | 1000.00 | 0.563 / 1.025 | 174.75 | 16.11 |
| 仅 Unbound | 1000.00 | 0.563 / 0.975 | 175.42 | 19.60 |
| 组合默认参数 | 1000.00 | 0.564 / 0.985 | 176.92 | 17.18 |
| 组合命令超时 20ms | 1000.00 | 0.562 / 1.016 | 179.00 | 17.17 |

该场景通过预定筛选阈值，结果表现为大致持平，不能据此宣称正常解析提速。20ms 仍是实验参数，尚未进入默认配置。

随后 mixed90 原版本首组完成 120000 条查询、无错误或超时；仅替换 Redis 的首组发送 119993 条、完成 119916 条，出现 **77 个超时**，矩阵停止。收到的 119916 条应答全部正确，旁路抓包计数与 dnsperf 一致，客户端 UDP socket 未记录丢包；旧 Unbound 同时记录一次 Redis 读取超时。该证据无法直接区分 Redis 回归、宿主机调度停顿或服务端收包问题，不能把失败结果剔除后宣称通过。

定向诊断另存原始结果，不并入正式验收轮次：

- 在“旧 Unbound + 新 Redis”组合中再次出现 **81 个超时**，恰好对应 Unbound 服务端 UDP socket 的 **81 次丢包**；采样收包队列峰值约 213 KB。客户端和旁路抓包无丢包，收到的答案全部正确，未见新的换页、OOM 或 CPU 配额限流证据。本轮 Unbound 未记录 Redis 错误，因此不能单凭先前的 Redis 超时认定组件回归。
- 组合默认参数单轮 120000 条查询无丢包；20ms 实验组单轮出现 **77 个超时、77 次服务端 UDP 丢包**。故障不限于旧 Unbound 组合，20ms 不进入默认配置。
- 独立网络命名空间的单轮 120000 条“旧 Unbound + 新 Redis”查询全部正确、无丢包。该轮软件 CPU 采样的热点主要在内核 socket 唤醒路径；这不是故障时的采样，不能据此归因于宿主机网关规则或宣布问题已解决。
- 将负载工具、抓包、受控上游和 DNS 进程全部限制在同一 CPU 后，原版本与仅替换 Redis 两个 120 秒组均无丢包，但 P99 分别约 8.30ms、8.20ms，高于四核放置的单轮结果。因此不把单核放置作为运行参数优化，也不与原矩阵混合汇总。
- 另一次四核组为每个包记录内核到达时间，同时保留答案核验和 CPU 采样：120000 条查询全部正确、无丢包。请求流最大间隔约 24.98ms，最密集的 1ms 桶有 23 条请求；应答最大间隔约 57.85ms。本轮没有复现队列溢出，只说明平均 1000 QPS 下仍存在短时调度或到达波动，不能据此认定此前丢包的根因。

服务端接收队列溢出已有直接证据。后续已独立复现“压测器停顿后补发 → 接收队列溢出”的机制，并记录到跨 CPU、跨会话的客机停顿；完整证据及边界见 [丢包原因定位](dns-benchmark-loss-diagnosis-2026-11-07.md)。原始失败缺少完整瞬间追踪，不能逐次追认同一原因；公共停顿在客机内核或虚拟化层的来源也尚未确定。测试条件变更不用于替换失败结果或补签性能通过。

性能矩阵停止后，在 41 上创建独立的命名数据目录和网络命名空间，使用相同原生 systemd 安装器进行整包演练；固定内部端口与当前运行实例完全隔离，DNS/DoH 使用本地受控夹具：

- 已校验的原版本首次安装、离线 wheel 安装和完整原生功能回归通过。
- 候选副本注入 bootstrap 启动失败后，安装器自动恢复旧版本、配置、实例身份和 DB 0/1 人工数据，DNS 健康检查恢复。
- 正常候选整包升级成功；用户配置摘要、实例身份和 DB 0/1 数据保留，候选完整原生功能回归通过。
- 显式回退恢复旧版本及升级前数据，候选新增数据不混入恢复状态；被替换的数据归档保留。
- 演练实例已经停止并解除网络命名空间；41 当前运行实例的版本、服务配置和宿主机 resolver 文件保持不变。

以上证据来自 Debian 13 amd64，不替代 Debian 12 完整 systemd 安装验收。整包演练完成时尚未通过 mixed90，后续校准结果另列；候选始终未替换当前运行实例。

## 校准后的 mixed90 默认参数对照

按照 [固定速率校准方法](dns-performance-calibrated-protocol-2026-11-07.md)，保持运行组件和内核参数不变，仅把本次 dnsperf 最大未完成请求数固定为 64。原版、仅更新 Redis、仅更新 Unbound、组合更新采用相同设置；20ms 不混入此次默认参数比较。工具记录实际命令、两端 UDP 丢包及内核包到达摘要。

先进行四种组合各两种场景的 10 秒工具检查：8 组共 80000 条查询全部正确、无丢包。随后 mixed90 执行 20 组（4 种组合 × 120 秒 × 5 轮），共 **2,399,812** 条查询全部完成、答案正确，客户端、服务端及旁路抓包均无丢包。每轮实际 QPS 为 **999.62–1000.00**，发送量、时长及答案计数均满足检查。

| 组合 | 有效 QPS 中位数 | P95 / P99（ms） | CPU 秒 / 百万查询 | 峰值 RSS（MiB） |
|---|---:|---:|---:|---:|
| 原版本 | 999.94 | 3.383 / 5.661 | 237.17 | 29.13 |
| 仅 Redis | 999.96 | 3.328 / 5.208 | 239.17 | 26.95 |
| 仅 Unbound | 999.93 | 3.406 / 5.889 | 240.18 | 30.15 |
| 组合默认参数 | 999.95 | 3.390 / 5.529 | 241.34 | 28.05 |
