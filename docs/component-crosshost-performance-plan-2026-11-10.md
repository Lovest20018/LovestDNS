# 另一宿主机上的组件性能对照

日期：2026-11-10，基线 `95a55fb`。用户批准在现有 Debian 12 / KVM 宿主机上，用限资源隔离实例先校准旧版，通过后再比较新旧版本。[前轮失败](dns-scheduling-diagnosis-results-2026-11-10.md)继续保留，换机器不作为其原因已经确认的证据。

实际结果与最终判定见[本轮记录](component-crosshost-performance-results-2026-11-10.md)。

## 固定条件

- 使用全新试验目录和独立网络命名空间，仅启用 loopback。旧版来自在用发布的只读核心文件，候选仍为此前普通制品：Redis 7.2.17、DNSCrypt 2.1.20 upstream / combined；不重新编译以改变结果。
- 复用前轮未加发送跟踪的冻结方法源码、普通 paced-udp 和 DoH 夹具，核对来源清单及摘要。DNSCrypt 的负载程序和夹具与前轮相同；Redis 的 dnsperf 为此前已在该宿主机验证过的自带加载器包装器，记录包装器、实际程序和依赖摘要，不将跨机器的绝对差值归因于版本。
- 宿主机只有四核，试验固定 CPU 2–3、CPUQuota 150%、MemoryMax 1 GiB、Nice 10。独立监视器使用 CPU 0–1、50% 配额、64 MiB，保留心跳和每二十秒一次的生产 DNS 探测完整输出。资源条件与前轮不同，新旧版本仅在本机同条件比较。
- 主服务 PID、重启数、启动时间和 guest boot ID 须保持一致；配置、用户规则、身份、管理账户、host resolver、内核参数和原备份在前后核对。内存可用量不足 1 GiB、磁盘不足 2 GiB、主服务变化或连续两次健康探测失败，停止整轮；单次健康失败也如实保留。
- 每个性能阶段核对试验 cgroup 的 CPU 限流及 memory max / OOM 增量。任一测量或资源条件失败，停止对应组件；两个组件分别判定。无同条件重跑，不筛掉异常查询或修改门槛。

## 顺序及停止条件

沿用[组件收尾方案](component-closure-plan-2026-11-10.md)的查询、答案、Redis 命中、协议、路由、内核配对和逐包节奏条件。CPU 增量上限 5%、RSS 10%，P95/P99 增量上限 `max(基线×5%, 0.2ms)`。

1. Redis：500 QPS、q64、串行夹具；每组重新填充唯一问题并重启 Unbound，旧版 30 秒相邻 A/A 共三对。每对 P95/P99 差值须小于等于 `max(两者较小值×5%, 0.2ms)`。全部通过后，才运行旧版／仅新 Redis 每组 120 秒、五轮交错正式对照。
2. DNSCrypt：100 QPS、q64、去掉 NET_ADMIN、GOMAXPROCS=2；依次 HTTP/2 直连、HTTP/2 SOCKS、HTTP/1.1 直连、HTTP/1.1 SOCKS，各做旧版 30 秒相邻 A/A 三对，同一尾延迟门槛。逐包间距仍须 5–50ms；通过全部校准后，运行 baseline / upstream / combined 每组 30 秒、三轮交错初筛。只有对旧版和同工具链 upstream 的初筛均通过，才做每组 120 秒、五轮同矩阵正式对照。

单组校准超时 180 秒，Redis 正式阶段 3000 秒，DNSCrypt 初筛 1500 秒、正式阶段 8500 秒，整轮最多 15000 秒。使用首次完整结果；准备工具若在发送查询前出错，保留原失败后只修复工具，不把已完成测量重做为通过。心跳仅提供调度背景，不用于筛除样本。

不停止或升级正式服务，不向正式 Redis 发送命令，不修改其缓存、系统参数、默认组件锁或运行配置；不安装系统依赖、不推送或公开发布。性能通过也只进入后续最终组合验收，不自动批准正式升级。
