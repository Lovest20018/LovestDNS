## 1. 建议与版本定位

发布两个镜像，共用一套 WebUI 代码与版本号：

| 项目 | WebUI 独立版 | PaoPaoDNS 集成版 |
|---|---|---|
| 定位 | 给现有 PaoPaoDNS 增加兼容的配置与诊断工具 | 一次部署具备观测、受控管理和增强策略的 DNS 服务 |
| 建议镜像名 | 保留 `ghcr.io/lovest20018/paopaodns-webui` | 新增 `ghcr.io/lovest20018/paopaodns-suite` |
| 内容 | 前端、Web API | 固定版本的上游 DNS 核心、必要的可追踪补丁、前端、Web API、内部管理服务 |
| 运行方式 | 独立容器，共享已有核心的 `/data` | 一个容器，在内部管理多个进程 |
| DNS 核心来源 | 用户自行部署 | 发布时锁定并验证的上游版本 |
| 端口 | Web 管理端口，默认绑定宿主机回环地址 | DNS 53/UDP、53/TCP，以及 Web 管理端口 |
| 数据 | 兼容现有 `/data` | 保留上游 `/data` 布局，面板数据使用独立卷 |
| Docker socket | 不挂载 | 不挂载 |

集成版保留“非官方集成发行版”的标识和上游来源，不将自身版本号表述成 PaoPaoDNS 官方版本。

当前的 `docker-compose-web.yaml` 已经组合启动官方核心和独立 WebUI。这解决了同时安装的问题，但不会赋予面板访问核心进程、内部套接字或运行日志的能力。此次新增的集成版应同时解决部署和受限管理的问题。

单容器会增加进程管理、依赖兼容和镜像维护成本。选择它是为了提供明确的“一个镜像包含全部组件”交付方式；若上游启动机制无法可靠适配，实施时应先报告验证结果，再决定是否将集成版改为带内部管理服务的双容器套件，不能把现有 Compose 原样包装后宣称已实现增强管理。

## 2. 功能范围与优先级

| 功能 | 独立版 | 集成版 | 建议阶段 |
|---|---|---|---|
| 现有配置编辑、规则校验、生效条件提示 | 保留 | 共用 | 基础 |
| DNS 查询、TCP 回退、链路对照、报告导入导出 | 保留 | 共用；自动发现可用内部链路 | 基础 |
| ADDINFO 解析路径、更多 DNS 记录类型 | 新增；依赖目标返回信息 | 共用，加受控诊断模式 | 第一批 |
| Zones/Hosts/Swaps | 完善已有表单、关联校验与引用文件管理 | 共用，加配置生成校验与生效验证 | 第一批 |
| 配置历史、差异预览、备份下载与恢复 | 新增 | 共用 | 第一批 |
| 核心及组件版本、启动时间、组件健康状态 | 展示可获得的信息，其余标记未知 | 通过内部管理服务读取 | 第一批 |
| 实时 QPS、缓存命中、递归队列、内存 | 可继续导入宿主机离线快照 | 持续采集支持的组件指标 | 第一批 |
| 配置重载与加载结果反馈 | 继续提示用户需要执行的操作 | 对明确支持的配置提供受限重载 | 第一批 |
| 组件日志查看、诊断包导出 | 保留面板自身日志/报告能力 | 增加可获得的核心日志与组件状态 | 第一批 |
| 指定域名的缓存失效处理 | 不提供核心控制 | 在确认相关缓存层接口后实现 | 第二批 |
| 故障事件和短期趋势 | 只记录面板可观测事件 | 增加核心事件和指标历史 | 第二批 |
| 查询记录、Top 域名、客户端排行 | 不承诺核心日志接入 | 接入已编译但未启用的 query_summary，补采集与保留策略 | 第二批 |
| 域名黑白名单与订阅 | 不执行需要核心扩展的策略 | 基于现有匹配/拒绝能力新增策略层 | 第二批 |
| 数据更新中心 | 状态与外部操作说明 | 将上游脚本拆为有界后台任务 | 第二批 |
| 客户端分组与差异策略 | 不提供核心策略执行 | 先完成策略与缓存隔离，再开放 | 后续阶段 |
| 自动切换上游、网页内更新镜像 | 不纳入首发 | 不纳入首发 | 后续单独设计 |

**真正新增的价值是可观测性与配置管理闭环。** 包含上游核心不会自动产生广告拦截、家长控制、客户端策略或完整查询日志；这些需要核心支持、配置设计和额外实现。上游已有能力的可视化可以逐步补充，但应逐项核实实际支持情况。

源码已确认具备实现域名过滤、客户端匹配和查询摘要的基础，因此将这些列为集成版的后续功能差异。当前前端缓存位于策略之前、缓存键不含客户端，设备策略必须连同缓存隔离一起设计。独立版继续发展纯配置和网络诊断能力，不人为删减两版可共用的功能。

指标必须保留来源：Unbound 的缓存命中率不能称为整个 PaoPaoDNS 的缓存命中率；内部缓存转发链路的响应时间不能称为远端上游延迟。计数器重置、组件重启、采集失败时分别标记，不补零制造正常状态。现有快照脚本可作为接口适配参考，不能直接作为已经验证的常驻采集服务。

已确认递归侧存在 `/tmp/uc_raw.sock`，转发侧控制接口默认关闭；定制 MosDNS 没有可直接使用的完整统计 API。首发需要新增转发控制 socket 和 MosDNS 入口/缓存计数，不能按普通 MosDNS 文档假定接口存在。

## 3. 共用架构

```text
统一 React 前端
       │
统一 Flask Web API（现有鉴权、文件白名单、校验和备份）
       ├── 文件能力：两版共用，管理 /data 中允许的配置
       ├── DNS 探测：两版共用，使用各自可达的网络目标
       └── 运行时适配层
              ├── standalone：不具备内部控制能力
              └── integrated：通过 Unix socket 调用内部管理服务
                                      │
                           组件状态、指标、日志、允许的重载动作
                                      │
                            固定版本的 PaoPaoDNS 核心
```

新增 `GET /api/capabilities`，返回构建版本、核心版本以及实际探测到的能力。前端据此显示功能；后端同样执行能力校验，不能仅隐藏按钮。缺少控制接口时明确降级，不因为使用集成版标签就假定接口存在。

内部管理服务仅监听容器内 Unix socket，不开放宿主机端口；使用文件权限限制调用者。只接受固定操作及严格校验后的参数，不提供任意命令、任意文件路径、`docker exec` 或通用 Shell 接口。

常驻采集由单独进程负责，Web API 读取其快照，避免现有两个 Gunicorn worker 重复采集或重复执行管理动作。重载使用串行任务、操作编号、超时和结果记录；重复请求不得并发触发同一重载。

集成版使用经过验证的进程管理方案，并保留上游启动顺序、配置生成和热重载机制。WebUI 退出不能连带终止 DNS；DNS 核心故障需要有明确的恢复策略和状态反馈。容器被标记 unhealthy 本身不会自动触发 Docker 重启，必须验证进程管理器或入口进程的实际行为。

这里保留的是上游解析语义与必要依赖顺序，并不照搬其后台进程加 `tail -f /dev/null` 的管理方式。配置生成、应用、监督和数据更新应明确分工，避免旧监视器与新增管理服务同时重启组件。增强策略使用独立模型，编译为受控模板，不混入独立版原有配置格式。

## 4. 配置生效不能只看“保存成功”

统一记录以下状态：已保存、待应用、应用中、应用失败、已验证生效、无法确认。

集成版的目标流程：

1. 校验输入，记录配置差异和可恢复版本。
2. 保存后依据该文件与所选上游版本的机制，等待自动加载或执行允许的重载动作。
3. 检查动作结果、组件状态及可用的加载版本证据，再执行 DNS 验证。
4. 只有取得充分证据才显示“已验证生效”；只能确认文件或进程存活时显示对应状态，不推断配置已经加载。
5. 失败时保留诊断信息并提供恢复入口。恢复也需要重新校验、应用和验证。

需要完整容器重启才能生效的配置，首发可以继续提示外部重启，不为实现网页按钮引入 Docker socket。涉及多个文件的恢复需要核对上游文件监视行为，避免逐文件落盘期间加载到混合配置；未实现可靠批量恢复前，仅提供单文件恢复。

`custom_env.ini` 中的目标配置值与组件实际运行值分别展示。配置文件哈希相同、重载命令退出码为零或某次 DNS 查询成功，都不能单独证明所有配置已经生效。

## 5. 上游引入与构建方式

优先保留上游原有构建和运行行为，使用固定 digest 的上游镜像作为集成版基础，再加入本项目组件。实施前验证基础发行版、CPU 架构、Python/运行库、入口进程和信号处理是否兼容。

源码审阅后补充：基础原型可继承固定镜像；需要 MosDNS 计数、稳定配置生成或缓存隔离时，应从锁定提交构建对应的定制 MosDNS，并维护最小补丁集。PaoPaoDNS 提交之外，还必须锁定预构建镜像及 MosDNS/Unbound/Redis 等实际依赖，不能继续依赖浮动分支构建。不得直接换成普通 MosDNS 二进制。

若不能可靠继承镜像，则从固定上游提交构建；在独立的构建区维护必要补丁，记录补丁用途与对应版本，不将核心文件散落复制到 `web/`。发布清单记录镜像内容实际对应的源码版本，无法建立对应关系时不能声称可复现。

建议结构：

```text
web/                           # 两版共用前端与 Web API
runtime/                       # 核心适配器、受限管理服务、采集器
packaging/integrated/           # 集成版 Dockerfile、入口与进程管理配置
packaging/upstream.lock.json    # 上游提交、镜像 digest、组件信息
docker-compose.sidecar.yaml     # 已有 PaoPaoDNS 用户
docker-compose.integrated.yaml  # 新集成版用户
docker-compose-web.yaml         # 保留现有官方核心 + WebUI 的部署方式
docs/                          # 安装、迁移、兼容矩阵、升级回退
```

版本标签采用同一发布号，如两版均为 `vX.Y.Z`，核心版本单独展示。兼容信息至少包含：WebUI 发布号、核心提交/镜像 digest、内部管理协议版本、支持的平台、已验证功能及限制。稳定发行锁定上游，不在用户启动时拉取最新脚本或自行替换核心。

CI 分别构建两版。当前 WebUI 工作流目标是 `linux/amd64` 和 `linux/arm64`；集成版需要先确认上游及新增依赖支持，再对每个宣称支持的平台执行验证。保留当前独立镜像名称与标签含义，不把原来的 `latest` 静默替换成集成版。

发布附带 Compose、环境变量示例、校验和、组件清单、来源与许可证文件；如果发布修改后的上游构建，同时整理对应源码和补丁。具体分发要求以实际选定版本及各组件许可证的核查结果为准。

## 6. 数据、迁移与回退

- 两版保持相同的上游配置文件格式，面板历史、审计和指标放入独立的面板状态卷，避免影响上游扫描 `/data`。
- 首次从现有部署迁移时，记录核心镜像、环境变量、端口与卷映射，停止旧实例后备份 `/data`，再以副本试运行新版本。不要让两个核心同时写同一数据卷或争用 53 端口。
- 验证 DNS、配置加载、缓存相关持久化和重启后行为，通过后切换正式服务。保留旧镜像、原始数据备份和旧 Compose。
- 从集成版退回独立版时，用匹配的上游核心镜像配合独立 WebUI，并选择兼容的数据版本。不能假定不同核心版本的持久化缓存可任意降级。
- 集成版增强策略只导出可映射到上游的部分；设备分组、拦截等不能迁移的配置必须列出，不承诺两版全部功能与数据互换。
- 升级由宿主机 Compose/容器工具执行；网页提供版本信息和升级说明，首发不实现自更新。
- 指标历史采用固定容量或保留期限；日志分页、限量读取，诊断包过滤 Token、密钥与敏感环境变量。

## 7. 实施顺序与验收

### 发布前置要求：缓存维护与历史数据兼容

集成版首发默认采用兼容模式：保留已有递归、转发、预取、过期响应策略及 Redis 持久化链路，先增加观察和管理能力。新的设备分组、拦截、缓存分区及持久化策略显式启用；不在首次迁移时同时替换解析策略、缓存格式和依赖大版本。

缓存增强按以下顺序交付：

1. 分层统计：MosDNS、递归/转发 Unbound、Redis 和可获得的 DNSCrypt 信息分别展示，区分命中、容量、淘汰、过期响应和后台刷新；缺失的字段不推算成已知数据。
2. 持久化健康：最后成功快照时间、保存失败、加载状态、磁盘和内存余量；备份前执行有界快照任务，等待成功并检查结果。既有源码使用定期 RDB，备份已有 RDB 不代表包含所有当前内存缓存。
3. 精细维护：按域名和缓存层失效、选定域名限速预热、配置变化后的相关缓存处理；不以清空全部 Redis 代替精细维护，不承诺未经验证的层已清理。
4. 资源预算：按容器 cgroup 限额分配缓存并为 WebUI、日志和采集器预留余量；提供低内存/均衡/大缓存预设，经过压力和长期运行验证后再给出默认值。
5. 策略隔离：设备组或不同上游策略使用正确隔离的缓存。旧缓存不自动并入所有新策略组；只有经过语义兼容验证的默认路径可复用，必要时新分区冷启动。

历史数据兼容范围：

| 数据 | 兼容目标 | 处理规则 |
|---|---|---|
| `custom_env.ini`、`custom_mod.yaml`、`unbound_custom.conf`、`force_*` 等用户规则 | 优先兼容 | 原文备份，保留未知字段/引用文件，按目标版本校验；另采集 Docker 环境变量和挂载，不能只复制 `/data` |
| `/data/redis_dns_v2.rdb` | 有条件复用 | 保持逻辑 DB 0/1 和兼容的 Redis、Unbound cachedb 版本/键与值语义；先在副本验证加载和缓存复用，不仅检查文件能打开 |
| MosDNS、Unbound、DNSCrypt 内存缓存和未落盘增量 | 不承诺完整迁移 | 重启后按组件机制重建；Redis 能补充部分历史缓存，不代表恢复所有内存状态 |
| IP 库、全球标记、Tracker 数据 | 校验后保留或重建 | 分清用户自定义与下载数据，迁移时不静默覆盖用户维护内容 |
| 手工修改的 `redis.conf`、`unbound.conf`、`mosdns.yaml`、`dnscrypt.toml`、解析器目录 | 人工修改检测后迁移 | 上游首次启动有删除并重建逻辑，集成版必须在执行前识别差异、归档并给出转换结果，不能直接照搬该逻辑 |
| 旧查询日志、统计历史 | 仅导入实际存在且支持的格式 | RDB 缓存不是查询历史，不能恢复过去的客户端排行、时间线和完整请求日志；新增历史从启用采集开始 |
| 集成版自己的策略、指标、审计记录 | 独立持久化 | 使用独立状态卷、格式版本及升级迁移脚本；回退时保留原始备份 |

Redis 的 `redis-expire-records: no` 不代表可以忽略 DNS TTL；缓存数据库留存和 DNS 应答有效期是不同概念。加载 RDB 成功也不代表新 Unbound 一定能命中其中的记录。发布兼容矩阵应同时覆盖读取、实际复用和回退，未覆盖的版本标记为未验证。

迁移流程为：记录旧镜像/配置/环境与挂载 → 尽可能完成并验证缓存快照 → 停止旧核心并备份 → 使用克隆数据卷和其他测试端口试启动 → 检查规则、解析、RDB 加载与复用 → 切换正式端口。失败时恢复旧镜像和未被新版本写入的原始数据；不让旧版本直接读取可能已升级格式的数据卷。

以上均为设计与验收要求，尚未实现或验证现有部署的迁移。实施时兼容矩阵必须绑定实际镜像 digest 及组件版本，不只绑定 PaoPaoDNS Git 提交。

### 阶段 A：锁定核心并验证集成可行性

选定真实上游版本，核查源码、许可证、启动入口、内部监听地址、控制接口、日志出口和配置重载语义。完成集成镜像原型，验证进程独立恢复、信号退出、数据持久化和 DNS 两种协议。

验收：WebUI 进程故障不影响 DNS；DNS 故障不会仍显示健康；正常停止无遗留进程；重建容器后数据可用。此阶段通过前，不承诺完整内部管理功能。

### 阶段 B：形成两个可发布版本

建立统一能力接口、两个构建目标、两套安装入口、版本清单和兼容矩阵。保持独立版现有配置编辑与诊断功能，集成版增加核心版本和可用组件状态。

验收：独立版仍能接入已有数据卷；集成版能全新安装；迁移和回退演练通过；各发布架构均通过构建及相应运行验证。

### 阶段 C：完成第一批增强功能

添加单进程实时采集、分组件健康状态、受限重载与生效结果、日志和诊断包；两版共同增加配置历史和单文件恢复。

验收：用已知查询量和计数器重置场景检查统计；模拟重载失败与重复请求；测试未知版本/缺失接口降级；验证访问鉴权、参数白名单及恢复后解析。管理功能的故障不能拖垮正常 DNS 查询。

### 阶段 D：按价值追加功能

在第一批功能稳定后，再做短期趋势、按域名缓存失效与查询日志。查询日志需要明确性能开销、存储上限和保留期限，不默认开启全量记录。

查询摘要插件已确认存在，可接入检索与排行；之后增加域名黑白名单和数据更新中心。客户端分组、不同上游与过滤策略需要先完成前端及相关下层缓存隔离验证。每项使用单独能力标识，不能仅按“集成版”统一启用。

建议首个稳定集成版覆盖阶段 A—C。阶段 B 可以先交付候选版本，供真实部署验证；不把功能清单中的后续评估项计入首发承诺。
