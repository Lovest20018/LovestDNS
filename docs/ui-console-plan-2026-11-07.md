# LovestDNS 控制台改版方案（修订版）

日期：2026-11-07。本文为当时的修订方案，部分内容现已落地，见[实施记录](ui-console-implementation-2026-11-07.md)；当前差距和下一轮优先级见[2026-11-11 项目与 UI 梳理](project-next-steps-and-ui-2026-11-11.md)。本文取代同日《产品界面与 LovestGateway 联动改版方案》的产品定位、页面优先级和实施顺序。旧方案中的接口调查可供参考，不再作为默认产品结构。

## 1. 定位

**面向有自建能力的用户，把 LovestDNS 后端的运行结构、组件状态、解析行为和配置效果直接呈现在前端。**

使用者通常理解 DNS、IP、上游、缓存、日志和重启等基本概念。界面应减少理解运行状态和完成操作的成本，不需要逐页解释基础知识。技术名称可以直接使用，必要说明按需展开。

优先级明确为：

1. 当前组件与服务运行状态的可视化。
2. 解析通道、分流配置、缓存和性能的可视化。
3. 高效的配置、应用、诊断与日志操作。
4. 有数据基础后再增加设备/查询记录。
5. LovestGateway 是可选观测扩展，用户按需连接。

LovestDNS 独立安装就是完整产品。不连接网关时，没有待绑定提醒、缺失网关卡片、未完成步骤或隐藏的核心功能。与 LovestGateway 风格统一只指视觉与交互规范，不代表运行依赖或账号绑定。

## 2. 对上一版方案的调整

| 上一版方向 | 修订决定 |
| --- | --- |
| 设备 → 域名 → 网关出口作为全站主线 | 主线改为运行概览 → 组件/通道 → 配置与诊断；设备记录作为后续观察视角 |
| 组件信息正常时折叠到页面底部 | 核心组件常驻概览首屏或紧邻首屏，不因状态正常而隐藏 |
| 首版先验证并接入 Gateway | 先完成独立 DNS 控制台；网关联动可单独交付，不阻塞主线 |
| 新增完整客户端事件采集是首个完整里程碑 | 现有后端能力的完整可视化即是首个里程碑；新采集单独评估 |
| 七个业务导航，设备/查询记录居前 | 使用六个稳定入口，优先保留现有能力与用户习惯 |
| 大量解释性文字和任务式引导 | 短标签、关键数值、状态标识、就地操作；帮助按需展开 |
| DNS 和网关证据在默认详情中并列 | 连接并启用扩展后，详情才增加“网关观测”页签 |

原先希望看到“哪台设备、哪个 IP/域名、是否分流”的方向仍保留。先把当前能确认的域名诊断、分流配置和解析通道做清楚；真实客户端历史依赖新采集，不能用尚不存在的数据反过来定义整个前端。

## 3. 页面结构：六个入口

| 页面 | 默认内容 | 内部分区 |
| --- | --- | --- |
| 运行概览 | 核心状态、解析架构、组件、两路 QPS/命中率、缓存摘要 | 运行结构、性能趋势、后台任务 |
| 解析配置 | 当前解析模式、上游、分流列表和目标 | 基础与上游、域名分流、高级配置 |
| 缓存 | Redis 内存/键数、两路缓存、持久化 | 缓存统计、TTL 规则、快照 |
| 查询与诊断 | 域名查询和链路对照 | 查询、对照、报告；以后按能力增加历史记录 |
| 维护与日志 | 组件日志、任务状态和服务维护 | 日志、维护任务、配置历史与应用 |
| 设置 | 实例、账户、API、外观 | 服务信息、API、账户、可选集成 |

配置页顶部保留“待应用 N 项”入口，直达维护页的应用面板。配置历史既能从当前编辑对象进入，也能在维护页集中查看，不要求用户保存后自行寻找操作位置。

现有 `/lists`、`/env`、`/ttl`、`/advanced` 等深链保留并映射至对应页签；迁移不改变配置文件内容、核心语义和草稿保护。

## 4. 运行概览：把后端结构呈现出来

建议桌面布局：

```text
运行概览                       原生 / 容器 · 版本   更新于 14:32:08   暂停 / 刷新
服务：运行中                  配置：已记录 / 有变更 / 待确认

┌─ 当前解析结构 ───────────────────────────────┐
│ 当前监听/入口与启用路径（仅在有运行依据时显示）│
│ 分流 / 递归 / 转发 / 加密上游 / 缓存关系       │
│ 组件名 + 状态；选择组件打开指标与日志           │
└─────────────────────────────────────────────┘

递归 QPS        转发 QPS         Redis 内存/上限        RDB 状态

两路查询趋势                      两路缓存命中率

后台服务与任务：watcher · observer · manager · cron · updater · bootstrap
```

结构图表达当前配置与运行组件之间的关系，不播放模拟流量，不把静态连线称为实际请求路径。具体入口、分支与缓存连接须核对生成的运行配置；不能把所有部署固定画成“客户端 → mosdns”。前端无法取得拓扑依据时，先展示按职责分组的组件矩阵，不推断连线。

### 4.1 组件是主要信息，不只是健康检查的附录

默认使用真实组件名称，副标签只保留短职责：

| 组件 | 副标签 | 默认信息 |
| --- | --- | --- |
| mosdns | 分流 | 进程状态；当前启用状态有依据时显示 |
| unbound-raw | 递归 | 状态、QPS、命中率 |
| unbound-forward | 转发 | 状态、QPS、命中率 |
| dnscrypt | 加密上游 | 状态；目标/协议仅展示可取得的运行信息 |
| dnscrypt-socks | 代理通道 | 状态；明确未启用与异常停止的差异 |
| Redis | 共享缓存 | 状态、内存、键数、持久化状态 |

选择组件后打开就地详情：PID、启动时间/运行时长、可用计数、退出码、最近日志及关联配置入口。现有 runtime 能提供 PID/start/exitstatus；组件 CPU、RSS、每个上游实时延迟等缺少接口的指标不加入首版固定卡片。

辅助服务使用紧凑状态列表，不给每个服务放一段职责说明。bootstrap/updater 的正常完成与常驻服务停止采用不同状态语义。判断“未启用”必须有配置依据；仅看到 STOPPED 时显示“已停止”或“启用状态待确认”，不随意判健康或故障。

### 4.2 组件、采集与配置三种状态分开

- 组件：运行中、启动中、已停止、异常退出、已完成。
- 数据：更新时间、暂停、过期、采集失败。仅异常时显示具体原因。
- 配置：有未保存修改、已保存待处理、与应用记录一致、运行状态待确认；仍不将应用记录等同于所有规则已验证。

概览只保留一处全局更新时间、一处核心异常摘要；组件自身只显示本组件状态。没有异常时不占用首屏显示长提示。

## 5. 解析配置、缓存和诊断

### 5.1 解析配置

先显示当前运行模式、默认解析方式与生效上游；编辑区明确区分“当前运行值”和“已保存目标值”。域名分流维持用户熟悉的强制转发、DNSCrypt、递归等分类，列表显示规则、匹配方式、目标与状态，文件名放次级位置。

可视化和源文件编辑保留，切换不改写原文。高级用户可直接使用现有参数名称；帮助描述折叠到字段提示或说明区。解析优先级可用简洁顺序图表达，必须与核心实现一致。

“输入域名检查规则”先作为查询诊断的快捷入口。静态规则解释若新增，显示“预计匹配”；真实命中仅在有响应调试信息或逐请求证据时显示。

保存状态和下一步动作集中在编辑区同一位置：未保存 → 已保存/待应用 → 任务结果 → 验证。需要重启时说明影响；普通编辑不强制多步向导。

### 5.2 缓存

缓存页以数据为主：Redis used_memory/maxmemory、db0/db1 键数、淘汰计数、RDB 大小/时间/结果；两路 Unbound 缓存命中率与可取得的缓存内存计数分别展示。

键数标“Redis 键数”，不标“缓存域名数”。maxmemory=0 显示“未设置 Redis 上限”。Redis 与 Unbound 内存按来源分列，不能直接相加宣传为不重复的缓存总量。TTL 规则在同页页签，保留现有快照操作；没有后端能力的清理/预热按钮不出现。

### 5.3 查询与诊断

上方是紧凑查询栏：域名、记录类型、目标、协议、执行。下方按“状态 / 耗时 / 回答 / TTL / 调试信息”展示；链路对照采用并列表格，不堆叠重复说明卡片。

若响应携带可解释的核心标记，可呈现该次解析的路径；缺失则不猜测。单次主动查询耗时与持续服务统计分开。当前没有全量入口耗时分布，不在默认概览放 P50/P95 占位卡。

重新查询保留上次结果及时间，完成后更新；执行中的进度、错误与记录内容分开。技术信息可直接展开，普通成功结果不出现长篇“成功不代表什么”的说明。

## 6. 文案与信息密度

原则：**名称准确、数值清楚、说明就近可查、异常才展开。**

| 当前表达示例 | 建议表达 |
| --- | --- |
| 每秒处理多少次查询 | 查询速率（QPS） |
| 多少查询直接用了缓存 | 缓存命中率 |
| 各项服务在做什么 | 组件状态 |
| 可读取的解析通道 | 解析通道 |
| 缓存保存到磁盘 | RDB 持久化 |
| 例如 80% 表示每 10 次查询约 8 次用了本通道缓存 | 删除常驻解释，指标帮助内说明计算口径 |
| 多处重复“DNS 运行正常” | 顶部一处总状态，组件各自状态 |

基础概念和正常状态的长说明移入帮助。影响判断的边界仍就地显示：例如“按通道统计”“历史快照”“预计匹配”“采集缺口”；详细原因在点击或展开后展示。避免为减字而隐藏待应用、风险影响或错误。

主标题、页签、标签和单位构成主要信息层级。正文 14px、辅助信息通常 12px，核心信息不靠缩到 10px 换取密度。图表共享图例/时间范围，同一数据不重复出现卡片、表格和大段说明三次。

## 7. LovestGateway：可选扩展

默认关闭，入口在“设置 → 可选集成”。没有连接时主导航和概览保持完整，不显示缺失网关的提示。

用户连接成功后，可选择显示网关状态摘要；查询详情增加“网关观测”页签，按需查询实际连接、FakeIP 和可用规则证据。网关故障只影响扩展区域，不改变 DNS 服务状态，也不阻塞本地配置、日志和诊断。

首版扩展复用现有只读 API，后端保管 Token。连接/历史有来源、时间和能力范围；DNS 查询与网关连接无法精确关联时分开展示，不强行画成端到端已验证链路。网关配置继续由网关管理。

前端与后端适配器隔离为可选模块；无集成配置时不启动网关轮询、不尝试连接外部服务。保留未来其他网关适配的边界，但首版不建设复杂插件平台。

## 8. 视觉一致性

沿用 LovestGateway 的品牌橙、深蓝灰/浅灰底色、232px 桌面侧栏、系统/明/暗主题和统一圆角；技术表格、状态标签、页签、页内操作和确认方式保持一致。

DNS 有自己的运行图、组件指标和配置结构。视觉一致不要求复制网关菜单、增加连接管理或迁移技术框架。改造集中在 integrated/frontend 的共享样式和组件，继续尊重冻结 web/ 边界。

运行结构桌面横向/分组展示，移动端改为分组组件列表；关键状态、指标和日志入口不能只在悬浮时可见。点击/键盘均能展开说明，移动端无整页横向溢出。

## 9. 调整后的实施顺序

### 第一阶段：现有能力重排与文案精简

统一标题/单位/状态/间距，删除重复说明；核心组件常驻概览；合并组件指标、趋势和异常入口。复用既有 API，不要求网关或查询事件系统。

交付门槛：独立部署即可查看所有当前可观测组件、两路解析指标和 Redis 状态；一两次操作进入相关日志/配置；暂停、过期、异常退出、一次性任务完成语义正确。

### 第二阶段：解析结构与操作整合

核对运行拓扑后增加结构视图；以现有配置为基础组织上游、分流与缓存页面，保持原始文件编辑能力、历史、版本检查、任务幂等和旧链接。拓扑数据不足时补只读摘要接口，先不扩展逐请求采集。

交付门槛：能从组件状态理解当前启用路径、进入对应配置、保存并完成已有应用流程，运行值与目标值不混淆。

### 第三阶段：独立评估两项增强

- 查询/设备观测：先验证真实客户端 IP、数据字段与性能，再决定采集/保留方式和页面入口。
- 网关扩展：根据实际需求连接 Gateway，只读展示现有 API 证据。

两项可分别启用、分别交付，不互相依赖，不作为第一、二阶段验收的前置条件。今后有真实查询历史后，可再判断是否值得增加独立“查询记录”导航。

## 10. 验收重点

1. 未配置 Gateway 的全新安装没有残缺感，所有原有管理能力可独立使用。
2. 核心组件默认可见；异常可就地进入日志，正常组件也可查看详细数据。
3. 用户不用阅读长说明即可找到 QPS、命中率、缓存用量、配置状态。
4. 真实组件名保留，术语、数值单位、时间和状态统一。
5. 无数据不补零，无逐请求证据不显示实际分流，无逐设备接口不展示虚构设备。
6. 运行图只表达可核对的结构，不伪装成实时流量或端到端追踪。
7. 保存、应用、验证状态清晰；草稿、认证恢复、历史及维护任务保护不退化。
8. 主题、键盘、移动端检查通过；先验证实际可读性和操作效率，再考虑装饰效果。

本次修订仅更新规划，没有修改运行程序、配置或部署。上一版设备/网关联动示意不作为本版首页设计。
