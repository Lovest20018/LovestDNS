# DNSCrypt 源码定位与补丁验证

本轮基于 `0ac77f0`，执行 [源码优化方案](component-source-optimization-plan-2026-11-09.md)。仅在 41 的临时目录、独立网络命名空间与限时任务中诊断；没有连接 旧版正式机、修改在用组件或读写真实缓存。

后续已经完成 [普通源码候选构建与协议验证](dnscrypt-source-candidate-results-2026-11-09.md)：无采样二进制可复现，小报文分配收益得到独立微基准确认；HTTP/2/直连/SOCKS 短测通过，但初筛仍被逐包发送空档中止，尚未批准默认升级。

## 已定位并制作独立补丁

### UDP 队列被强制缩小

新旧上游的 Linux `udpListenerConfig()` 都调用 `SO_RCVBUFFORCE=4096`。具备 NET_ADMIN 时调用成功，Linux 报告实际接收队列为 8192 字节；没有该能力时调用失败且错误被忽略，现场内核默认值为 212992 字节。因此同一程序的权限也会改变积压承受能力。源码依据：[2.1.20 setsockopts_linux.go](https://github.com/DNSCrypt/dnscrypt-proxy/blob/2.1.20/dnscrypt-proxy/setsockopts_linux.go)。

首轮旧版诊断遇到约 0.6 秒的到达间隔和随后补发，4700 次中 37 包在服务端 UDP 队列丢失，原始结果保留为未通过。后续使用实际监听代码的确定性测试：不读取接收端，连续发送 128 个 256 字节包，再逐包读取。

| 实现与权限 | 实际 SO_RCVBUF | 收到 / 发送 |
|---|---:|---:|
| 原实现，有 NET_ADMIN | 8192 | 9 / 128，反例失败 |
| 接收队列补丁，有 NET_ADMIN | 425984 | 128 / 128，通过 |
| 原实现，无 NET_ADMIN | 212992 | 128 / 128，通过 |

补丁改用普通 `SO_RCVBUF=256*1024`，由内核上限约束，不改 sysctl、不要求提权。它解决已复现的队列容量问题，不证明虚拟机停顿已消失，也不解释全部 CPU / P99 波动。

### 每个小查询分配约 4KiB

新旧版 `udpListener()` 每次读取前都分配 4095 字节。新版 30 秒、100 QPS 的堆采样中，此入口分配约 11.34 MB，占估算增量总分配的 27.1%。源码依据：[2.1.20 proxy.go](https://github.com/DNSCrypt/dnscrypt-proxy/blob/2.1.20/dnscrypt-proxy/proxy.go)。

第二个补丁让监听器持有一个接收缓冲区，每次只复制实际报文长度交给处理器。并发请求继续拥有各自的字节；没有通过复用同一底层数组减少分配。

32 个异步处理器等待全部接收结束后才读取各自报文，覆盖 32 / 63 / 255 / 512 / 4095 字节。原实现和补丁都通过；将补丁中的复制故意改成共享切片后，测试因报文覆盖而失败。测试提取实际监听函数，不重新实现被测接收逻辑。

相同 3000 次查询的采样总分配为 41.88 → 32.43 MB，观察到约 22.6% 下降；UDP 入口的大块分配热点消失。但两次 HTTP 连接数分别为 6 和 1，采样自身也存在误差，**不能把总降幅全部归因于补丁，更不能当作 CPU、RSS 或项目吞吐的提升比例**。数值沿用 pprof 的 MB 单位。

## CPU、RSS 与测试夹具

旧镜像二进制为 Go 1.22.5、PIE / CGO / musl；官方候选为 Go 1.27.3、静态 / CGO 关闭。诊断按对应上游 tag 重建，并额外加入符号和采样入口；它不是镜像旧二进制的完全复刻。两版 CPU 采样主要落在系统调用与 Go 调度路径，没有证据将此前 16.8% 的直连 CPU 增幅全部归到某个 DNS 业务函数。

四个新旧版本定位阶段：CPU 各 45 秒采样、47 秒负载；heap 各 30 秒。均为 100 QPS、q64、HTTP/1.1 TLS。本阶段只让 DNSCrypt 子进程去掉 NET_ADMIN，两版实际接收缓冲区均为 212992 字节，避免小队列干扰定位。CPU 阶段连接数旧 / 新为 1 / 13，heap 为 1 / 6，不能据此签署严格源码单变量对照。heap 结束时采样存活堆都约 0.7 MiB，不能解释全部 RSS 差额或排除长期增长。

SOCKS 另做只改变夹具 TCP_NODELAY 的 10 秒短对照，旧版 / 候选二进制不变，两组都去掉 NET_ADMIN：

| 版本 | 夹具默认 P95 / P99（ms） | 开启 NODELAY 后（ms） |
|---|---:|---:|
| 旧版 | 57.690 / 60.996 | 3.503 / 4.149 |
| 候选 | 49.410 / 56.541 | 3.544 / 4.284 |

直连两组仍约 2.7–2.9ms P95；路由与 TLS 验证通过。这确认先前 SOCKS 测试延迟有显著的夹具 TCP 小报文因素，不是新版组件获得了这一幅度的真实加速。新增 `--socks-tcp-nodelay` 显式控制并记录该变量，默认保持原条件；未来使用新条件须重新建立基线，不追改既有验收。

## 验证与交付边界

- 四个原实现定位阶段、只改分配的 heap 阶段、双补丁功能 smoke 共 **19600 次查询**，答案全部正确，客户端与服务端均零丢包，受控路由通过。双补丁实际接收缓冲区为 425984 字节。
- NODELAY 八个短对照共 **8000 次查询**，答案正确、零丢包。它不是五轮正式性能验收。
- 双补丁另以 8 次 A / AAAA、大小写变化与重复查询核对答案、非零 TTL 和上游计数：四次未命中、四次命中，缓存类型隔离正确。
- Linux 定向 Python 检查 **11 项通过**。Windows 纯逻辑检查 8 项通过；早期 Windows 网络用例受 WinError 10013 阻止，网络判定依据实际 Linux 验证，没有修改测试去跳过限制。
- 两个 socket 正向条件、两个并发所有权正向条件通过；原小队列与故意共享报文的反例按预期失败，分别保存，不计入通过项。
- 41 在用 `lovestdns-validation` 始终为 PID 1047426、NRestarts=0；诊断任务已经结束，无诊断进程残留。收尾核对其实际 MosDNS 入口 15453，公开域名查询为 NOERROR、8ms；误探默认 loopback 53 的拒绝连接不代表该实例异常。旧版正式机 本轮未操作。

补丁、独立 Go 契约测试及复现方法见 [补丁目录](../packaging/components/patches/README.md)。`build-dnscrypt-diagnostic.py` 校验上游归档摘要、固定 Go 版本、使用 vendor，支持分别或组合应用补丁；所有产物标记为诊断专用，不能部署。`profile-dnscrypt.py` 校验二进制摘要、隔离命名空间、实际队列和协议，分别输出 CPU / 分配 / 存活堆证据。

本轮没有改变组件锁或默认构建流程。Unbound 仍固定旧版，其离线兼容契约已写入方案，迁移工具尚未实现；Redis 保持独立候选，没有追加原条件长压测。

下一关是把有效补丁纳入可追溯的**非诊断源码构建**，先检查严格发送节奏与 HTTP/2 夹具，再对无采样制品复核 CPU、RSS 和固定负载结果。此前 DNSCrypt 性能筛选未通过的结论继续保留，尚未批准默认升级。
