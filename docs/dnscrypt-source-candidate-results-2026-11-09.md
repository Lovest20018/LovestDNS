# DNSCrypt 普通源码候选结果

承接 `4db8dbb`，执行 [普通候选方案](dnscrypt-source-candidate-plan-2026-11-09.md)。本阶段完成普通源码制品、可复现构建及协议/缓存验证；**性能验收仍未完成，默认组件继续不变**。全部运行在 41 的新目录与独立网络命名空间，没有连接 旧版正式机，也没有提交上游 PR。

## 普通制品与分配验证

新增 `packaging/dnscrypt-source.lock.json` 与 `scripts/build-dnscrypt-source.py`，固定 DNSCrypt 2.1.20 源码、Go 1.27.3 Linux amd64 工具链、vendor 和两个补丁摘要。普通源码从归档重新解出，没有加入诊断采样代码；所有制品清单仍标记为未批准候选，默认安装器不读取这份锁。

三个独立工作目录的三种 DNSCrypt 二进制摘要均相同：

| 变体 | 改动 | 二进制 SHA-256 |
|---|---|---|
| upstream | 上游原实现 | `2bc7d43c6960307726036f6645792c31ecee7babab325ac15b055aa6b5d11184` |
| buffer | 仅 UDP 接收队列 | `e2cd67ee345f228926433174c9a96223dc33fbb829e9b45d77f09064da7be4ab` |
| udp | 接收队列与报文分配 | `dfa68a2db31326e4a3205dc9eeaca71e897756e2d0b88623f56e749c278c8a43` |

这证明现场这些受控输入和参数下的二进制可复现，不代表其他平台已经验证。旧版仍使用私有 musl/PIE 制品，新版是 CGO=0 普通静态制品；跨版本比较不等于只改变源码。

对真正从原版/补丁版 `proxy.go` 提取的 `udpListener()` 做三次所有权检查与 `-benchmem`，每个尺寸取三次中位数：

| 收到的报文 | 原实现 B/op | 双补丁 B/op | allocs/op |
|---:|---:|---:|---:|
| 32 字节 | 4228 | 164 | 均为 5 |
| 63 字节 | 4228 | 196 | 均为 5 |
| 255 字节 | 4228 | 388 | 均为 5 |
| 512 字节 | 4228 | 644 | 均为 5 |
| 4095 字节 | 4228 | 4228 | 均为 5 |

结果确认减少的是小报文分配的**字节数**，不是分配次数；大报文没有分配收益。该基准包含 loopback、goroutine 和测试替身开销，按版本分组执行，补丁组 ns/op 反而更高，不能据它签署完整 DNS 的 CPU 或吞吐改善。两种监听函数的并发所有权检查和 race 检查均通过。

## 新协议夹具与完整短测

新增 Go TLS DoH 夹具，分别实际协商 HTTP/1.1 与 HTTP/2，逐次核对 HTTP 版本及 ALPN；错误来源、协议回退和非受控域名被拒绝。夹具只处理 cache.test 的 A/AAAA 与 DNSCrypt 初始化 NS 探测，没有公网转发。实际 SOCKS 转发使用不同 loopback 源地址核对，夹具两端显式开启 TCP_NODELAY。

每个 DNSCrypt 子进程统一去掉 NET_ADMIN、固定 GOMAXPROCS=2。旧版及新版原实现实际接收队列为 212992 字节，双补丁为 425984 字节。新版两个变体采用同一源码、工具链和参数；队列大小差异由补丁保留，不能将完整路径差异全部归因于报文分配。

CPU 4–7、配额 400%、100 QPS、q64、每组 5 秒，三种实现 × 两种 HTTP 协议 × 直连/实际 SOCKS，共 **12 组、5997 次查询**：

- 答案、DNS 类型、TLS、实际路由和 HTTP/ALPN 均通过。
- 客户端、解析器 socket、抓包均零丢包；内核逐问题往返配对完整。
- 每组实际发送负载与严格节奏检查通过；任务 CPU 配额限流为零。
- 这只是协议与容量短测，不是 120 秒、五轮正式性能验收，也不覆盖 HTTP/3、DNSCrypt 加密协议、公网解析器或完整分流链路。

普通制品另做 HTTP/2 直连/SOCKS 缓存检查：三种实现共 **48 次查询，24 次上游访问、24 次缓存命中**。A/AAAA 隔离、大小写命中、答案与非零 TTL 均正确；没有用诊断二进制替代这些检查。

## 发送节奏与未通过记录

预先固定逐包条件：100 QPS 的相邻查询间隔至少 5ms、最多 50ms，每个 1ms 桶最多一包，时间顺序与计数完整。以下失败全部保存，没有提高门槛或追改旧结果。

1. 首次夹具 race 测试发现测试客户端没有显式声明 HTTP/1.1 ALPN，严格校验拒绝。修正测试客户端后通过；实际夹具也经过真实 TLS/HTTP/2 请求、错误来源和错误 ALPN 的检查。
2. 使用 dnsperf 的新夹具短测第 3 组最小到达间隔为 **4.296ms**；平均负载合格、答案和丢包正常，但发送节奏未通过，停止该轮。
3. 新增 Go 定速 UDP 发生器。使用单调时钟安排请求；落后超过半周期时将下一次发送顺延，不补发错过的时隙，并限制两次实际发送完成之间的最小间隔。CPU 配额 200% 的首次短测记录约 **263ms** 空档，发送/完成均为 474，未达到负载和节奏条件；监控同时记录到任务限流，不能将空档完全归因于它。
4. 仅将任务配额改为 400% 后，完整 12 组短测通过。随后 HTTP/2、每组 30 秒、三轮初筛在第 5 组记录约 **105.5ms** 查询空档，完成 2991 条，仍落在总负载允许范围，但逐包最大间隔未通过。该轮监控的配额限流始终为零，无法将此前空档全部解释为 CPU 配额，也不能直接认定 VMware、某个 Go 函数或组件是根因。

HTTP/2 初筛只完成 5/18 组，其中四组全部测量条件有效。答案、socket/抓包丢包和协议检查均正常，但**整轮测量无效且不完整，正式长测没有启动**。保留最先完整相邻一组三种实现的原始观察，不能作为已通过的版本性能比较：

| 实现，HTTP/2 直连 | CPU 秒/百万查询 | 峰值 RSS MiB | P99 ms |
|---|---:|---:|---:|
| 旧版 2.1.5 | 1456.25 | 19.13 | 4.011 |
| 新版原实现 | 1593.33 | 21.11 | 3.980 |
| 新版双补丁 | 1560.00 | 21.13 | 4.057 |

单组的新版 CPU/RSS 仍有增加，不能因某个延迟分位数相近就批准升级，也不能据未完成轮次给出可靠回归比例。所有新夹具试验共记录 25455 次查询（含上述无效轮次），答案正确、客户端/解析器/抓包均零丢包；这不把无效测量变成有效性能证据。

另人工 SIGSTOP 暂停发生器 250ms：461 次发送全部完成，没有追发丢失时隙，节奏验收按预期拒绝。该项是工具反例，不计入组件性能通过。
