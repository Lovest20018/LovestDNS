# DNSCrypt 普通制品 UDP 权限验证结果

从 `178cedb` 继续，执行 [本阶段方案](dnscrypt-udp-runtime-plan-2026-11-09.md)。本轮将此前提取监听函数的证据扩展到普通完整二进制：**接收队列补丁消除了当前内核下 NET_ADMIN 导致的强制小队列，并在本次有限积压中保留全部问题。** 这是明确的可靠性修复证据，未证明日常解析提速或批准默认升级。

## 20 组实测

41 上隔离 network namespace，loopback IPv4/IPv6；五种普通制品 × 两种实际进程权限 × 两个地址族，共 20 组。先预热同名 A/AAAA，再 SIGSTOP 该隔离解析进程、发送 128 个 256 字节有效 DNS 问题，确认报文入队后恢复读取。暂停只用于可控积压，不是性能计时。

以下每行在 IPv4、IPv6 的结果一致。buffer 为仅接收队列补丁，udp 为队列和报文分配双补丁，cache 为独立缓存分片补丁。

| 实现 | NET_ADMIN | 内核实际接收队列字节 | 收到 / 128 | 内核丢包 |
|---|---|---:|---:|---:|
| 旧部署 / upstream / cache | 有 | 8192 | 9 | 119 |
| 旧部署 / upstream / cache | 无 | 212992 | 128 | 0 |
| buffer / udp | 有 | 425984 | 128 | 0 |
| buffer / udp | 无 | 425984 | 128 | 0 |

**14 组无丢包，6 组是已知小队列缺陷对照。** 六组各丢 119 包不能写成“20 组都无丢包”；工具的 `passed=true` 表示符合该组预定契约。总共发送 2560 个积压问题，收到 1846 个，其余 714 个全部由解析端 socket 丢包增量解释；客户端 socket 丢包为零，没有未知丢包、重复或错答，恢复后解析端队列排空。

每组核对实际 `/proc/PID/status` 能力、`ss` socket 容量/队列/丢包和每个响应的 ID、问题名、类型、类、状态、地址、非零 TTL。每组另验证 A、AAAA 两个 4095 字节 EDNS padding 问题，共 **40 次最大接收长度查询**全部通过。最大长度复查和积压组均未回源；启动及 A/AAAA 预热期间的实际 HTTP/2、ALPN h2、直连来源另行核对，各组这段期间共 4 次上游请求，不混入积压计数。

这也确认 cache 单补丁没有改变接收队列；udp 与 cache 仍为独立候选，未构建或验证三补丁组合。只覆盖缓存命中后的 IPv4/IPv6 UDP 入口、HTTP/2 直连预热，不扩大为公网、HTTP/3、SOCKS 全路径或 DNSCrypt 加密协议验收。

## 内核边界与发送队列

host 和隔离 namespace 实测 `rmem_max=rmem_default=212992`，前后值未变。测试自身 socket 的普通 SO_RCVBUF 申请在两个地址族均得到：

| 请求字节 | 内核报告字节 |
|---:|---:|
| 4096 | 8192 |
| 65536 | 131072 |
| 262144 | 425984 |
| 1048576 | 425984 |

实际值符合 `2 × min(请求, rmem_max)`，包括 Linux 双倍报告语义。补丁不会绕过内核上限。本轮没有修改 sysctl，也没有覆盖多个 rmem_max 值或不同内核；上限更低、报文更大或积压更长时仍可能丢包，不能承诺任意环境保存任意突发。

发送队列保持原实现：有 NET_ADMIN 时实测 8192 字节，无该能力时 212992 字节，所有候选一致。本轮未遇到发送端解释不了的丢包，但不把它视为发送队列优化或高负载验收。接收队列容量是 kernel socket 限额，不能直接当作持续占用的进程 RSS。
