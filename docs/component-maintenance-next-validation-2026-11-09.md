# 组件维护候选的后续验收

日期：2026-11-09。既有 UI/网关基线已交付，组件试验沿用 `codex/dns-core-upgrade-perf`。本轮先修正工具，再分别判断 Redis 与 DNSCrypt；不预设二者必须一起交付。最终组合重新打包验收。

## 缓存准备协议 v2

`unique-question-coverage-v2` 通过受控上游的问题账本，按忽略大小写的问题名、类型、类核对唯一覆盖，分别记录 UDP/TCP 尝试。缺失、意外问题、错误答案、缺少缓存键、丢包或无法核对的额外计数均拒绝。账本及其规范化摘要随每轮保存，不以总请求数推测重复原因。

准备阶段允许已核对的同问题额外尝试，总数最多为唯一问题数的 1%；超过此值视为准备条件不合格。该上限在新测试前固定，用于防止高重试负载被当作正常准备。它不是生产超时策略，也不把额外尝试自动归因于某一种故障。

正式测量仍要求只重启 Unbound、Redis 进程不变，每条查询真实命中 Redis，零未命中、零上游访问；原延迟、CPU、RSS、负载、答案和丢包条件保持。旧结果按旧协议解释，旧失败不追补为通过。

## 有限执行与分组件判定

1. 完成纯逻辑反例、Linux 回归和实际协议 smoke；人工制造一次延迟，确认重复上游尝试被独立记录，缺失问题仍拒绝。
2. 在 41 对修正工具执行一次六组原版 A/A，每组 120 秒、500 QPS、q64、串行夹具、共享 CPU 4–7。固定相邻三对，沿用 `max(较小值 × 5%, 0.2ms)`；每组独立准备。若测量有效且三对均符合，再做原版/仅 Redis 五轮交错对照。重复性或正式对照失败后保留结果，不在原条件下反复重跑。
3. DNSCrypt 另用受控 TLS DoH 和实际 SOCKS 路径，先做 5 秒、每种组合一轮的容量 smoke，再固定 100 QPS、q64、120 秒、五轮交错比较。通过时仍仅代表受控协议和负载，不能扩大成所有公网解析器或最大吞吐。HTTP 版本等夹具限制随结果说明。
4. 每个组件分别给出通过、未通过或证据不足；可靠性不足时允许在合适的其他环境复核。单独一次 A/A 通过不代替各正式轮次的完整检查。

## 既有正式环境

用户已授权用于测试。先做只读库存与每秒一次、共 30 次公开域名 DNS 基线；只记录必要摘要。该主机为 Debian 12 amd64、opt5、旧组件组合，服务运行正常。现场地址、配置摘要、探测结果保存在私有验收目录，不纳入公共源码。

需要进一步做候选对照时，仅在新建数据目录和独立网络命名空间中使用受控域名，先检查资源余量、组件来源和生产服务状态。正式环境的现有服务不参与故障注入；隔离比较也不等同于生产实例已经升级或 Debian 12 整包安装验收。

本次 DNSCrypt 测试使用独立 systemd 临时服务，允许 CPU 2–3、CPU 配额 150%、低调度权重、512 MiB 内存上限及 70 分钟总时限。每 10 秒检查正式服务 PID/重启数、剩余内存及一次公开域名 DNS 应答；服务状态变化、可用内存低于 1 GiB 或连续两次 DNS 失败即停止测试。记录 cgroup 限流情况，受限流影响的结果不能直接作为无资源限制的性能证据。

Debian 12 的压测工具采用私有 glibc 加载器及独立依赖目录，上传包逐文件校验；不替换系统库。实际工具、候选、原版和方法摘要与现场记录共同保存。

## 交付条件

只有实际通过的组件进入最终候选；重新核对源码、组件和包摘要，补齐安装升级回退、观测开销及两小时负载、24 小时观察。新版 Unbound 的缓存迁移与性能专项继续独立记录；不将暂缓固定为永久维护策略。

## 实际流量与旧缓存补充验证

用户补充确认：测试机没有日常流量和充分的旧缓存，另一台已运行旧版的 Debian 12 正式机具备两者。本轮增加五分钟、最多一万条 UDP/53 的被动采样，排除测试健康探测；原始问题仅保存到现场私有目录，不保存客户端地址。样本用于查询类型、重复性和隔离回放，不代表全天流量。UDP 抓包不覆盖 TCP DNS。

正式机的已完成 RDB 约 702 MiB，两个数据库约有 202 万键。待当前加密测量结束后，只复制一个已完成快照，在独立网络命名空间中依次加载原版、仅 Redis、仅 Unbound 和恢复原版。逐键核对字符串值摘要，按可验证的默认种子键算法统计大小写、过期及受影响条目，再从有效期足够的实际 A/AAAA 中抽样验证缓存复用和答案。上游由本地受控夹具提供，不向生产 Redis 读写域名内容，也不向公网回放历史域名。实际快照包含的非 DNS 数据另计；未验证的种子或记录不能进入命中结论。

该阶段最多占用 2 GiB 测试内存，保留至少 1 GiB 主机可用内存及磁盘余量，延续生产健康检查。大文件采用一次副本和只读硬链接，测试关闭自动保存和 AOF，结束核对原副本摘要。

测试机的新六组 A/A 中，延迟三对均满足要求，但一条辅助内核往返配对不完整；该次完整校准仍不通过，不直接追认为组件回归。工具已发现按抓包交付先后立即判定未匹配应答的限制：新 `linux-kernel-udp-roundtrip-us-v2` 支持应答先被读取、随后才读取问题，仍依据各自内核时间戳配对；真实缺包、重复键或时钟反转继续拒绝。不从旧汇总恢复缺失的逐包证据，也不改判旧记录。

随后在正式机的隔离空间只做一次新方法 A/A：CPU 2–3、CPU 配额 150%、512 MiB 测试内存上限，500 QPS、q64、串行夹具、六组各 120 秒，原三对及原门槛。先做两种组合各 5 秒容量检查。若六组全部有效、无测量阶段限流且三对均满足，再做仅 Redis 与原版各五轮、120 秒交错对照；否则停止本轮比较。实际缓存兼容、真实流量样本与这套受控性能数据分别报告，不合并成一个提速结论。

实际盘点发现已完成快照中的可识别 DNS 条目全部超过 TTL，不能满足第一项“新鲜条目命中”前提。原尝试保留为证据不足，后续不复制第二份大文件：使用同一不可变原副本，核对原版/新 Redis 的完整字符串值摘要，并对随机实际记录、流量样本中可对应记录及大小写受影响分层样本检查过期应答、受控刷新和恢复原版。仅在隔离夹具关闭预取，以区分主动查询与后台预取；逐样本内存缓存可能复用，整体 Redis 计数只作诊断，大小写分层检查则逐条清空 Unbound 内存。该阶段不签署新鲜缓存全命中或性能通过。

过期 DNS 回放在旧版基线上发现中间 CNAME、同名大小写条目的历史地址差异，尚未构成完整版本对照。Redis 的独立全 RDB 读取已经通过，后续 A/A 按原固定条件继续；不把未完成的 Unbound 回放当作 Redis 失败，也不把 Redis 读取通过扩大为 Unbound 已兼容。现场过时文件清理由用户另行授权，待测试结束后按明确清单处理，保留在用数据和回退备份。
